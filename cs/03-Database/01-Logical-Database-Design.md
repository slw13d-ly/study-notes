# 01. 논리 데이터베이스 설계

## SECTION 060. 데이터베이스 설계

### 1. 데이터베이스 설계의 개념
- **데이터베이스 설계** - 사용자의 요구를 분석하여 그것을 컴퓨터에 저장할 수 있는 **데이터베이스 구조로 변환**한 후, 특정 DBMS로 데이터베이스를 구현하여 일반 사용자들이 사용할 수 있도록 하는 과정

> ⭐ `사용자 요구 분석 → DB 구조 설계 → 특정 DBMS로 구현`

### 2. 데이터베이스 설계 시 고려사항

| 고려사항 | 핵심 |
|---|---|
| **무결성(Integrity)** | 삽입·삭제·갱신 등의 연산 후에도 저장 데이터가 **정해진 제약 조건을 항상 만족** |
| **일관성(Consistency)** | 저장된 데이터 사이 또는 질의에 대한 응답이 **처음부터 끝까지 일정** |
| **회복(Recovery)** | 시스템 장애 발생 시 **장애 발생 전 상태로 복구 가능** |
| **보안(Security)** | 불법적인 데이터 노출·변경·손실로부터 데이터 보호 |
| **효율성(Efficiency)** | 응답 시간·시스템 생산성·저장 공간 등의 효율 고려 |
| **데이터베이스 확장** | 운영에 영향을 주지 않으면서 **지속적으로 데이터 추가 가능** |

> ⭐ 설계 고려사항 → `무·일·회·보·효·확`

### 3. 데이터베이스 설계 순서

`요구 조건 분석 → 개념적 설계 → 논리적 설계 → 물리적 설계 → 구현`

| 단계 | 핵심 |
|---|---|
| **요구 조건 분석** | 사용자 요구 수집·분석 → **요구 조건 명세서 작성** |
| **개념적 설계** | **개념 스키마 / 트랜잭션 모델링 / E-R 모델** |
| **논리적 설계** | 목표 DBMS에 맞는 **논리 스키마 설계 / 트랜잭션 인터페이스 설계** |
| **물리적 설계** | 논리 구조를 목표 DBMS에 맞는 **물리적 저장 구조로 변환** |
| **구현** | 목표 DBMS의 **DDL**로 데이터베이스 생성 / 트랜잭션·응용 프로그램 작성 |

> ⭐ `요 → 개 → 논 → 물 → 구`

### 4. 요구 조건 분석
- 데이터베이스를 사용할 사람들로부터 **필요한 용도와 요구사항을 파악**하는 단계
- 사용자별 수행 업무와 필요한 데이터의 **종류 / 용도 / 처리 형태 / 흐름 / 제약 조건** 등을 수집
- 수집한 정보를 바탕으로 **요구 조건 명세서** 작성

### 5. 개념적 설계(정보 모델링, 개념화)
- 현실 세계에 존재하는 의미 있는 내용을 사람이 이해할 수 있는 **추상적 개념으로 표현**하는 과정
- **개념 스키마 모델링 + 트랜잭션 모델링** 병행
- 요구 조건 명세서를 **DBMS에 독립적인 E-R 다이어그램**으로 작성
- DBMS에 독립적인 **개념 스키마** 설계

> ⭐ `개념적 설계 = DBMS 독립적 / E-R 모델`

### 6. 논리적 설계(데이터 모델링)
- 개념적 설계에서 얻은 구조를 컴퓨터가 이해·처리할 수 있는 **논리적 자료 구조로 변환**하는 과정
- 현실 세계를 **논리적 데이터 구조로 매핑(Mapping)**
- 사용할 데이터 모델을 결정하고 특정 DBMS에 맞는 **논리적 스키마** 설계
- **트랜잭션 인터페이스** 설계
- 관계형 데이터베이스라면 **테이블을 설계하는 단계**

> ⭐ `논리적 설계 = 데이터 모델링 / 테이블 설계`

### 7. 물리적 설계(데이터 구조화)
- 논리적 설계의 구조를 디스크 등의 **물리적 저장장치에 저장할 수 있는 구조로 변환**
- 기본적인 저장 구조와 접근 방법 설계
- 처리 성능을 파악하기 위해 **트랜잭션을 수집·분석**
- 저장 레코드의 **형식 / 순서 / 접근 경로** 등의 정보를 사용하여 설계

#### 물리적 설계 시 고려사항
- **트랜잭션 처리 시간**
- **디스크 용량**
- **저장 공간의 효율화**

> ⭐ `물리적 설계 = 저장 구조 / 레코드 형식·순서·접근 경로`

### 8. 데이터베이스 구현
- 논리적·물리적 설계에서 도출된 데이터베이스 스키마를 **특정 DBMS의 DDL**을 이용해 기술
- 데이터베이스 파일 생성
- 응용 프로그램에서 사용할 **트랜잭션 작성**
- 데이터베이스 접근을 위한 **응용 프로그램 작성**

## SECTION 061. 데이터 모델의 개념

### 1. 데이터 모델의 정의
- 현실 세계의 정보들을 컴퓨터에 표현하기 위해 단순화·추상화하여 **체계적으로 표현한 개념적 모형**
- 데이터의 **구조 / 연산 / 제약 조건** 등을 기술하기 위한 개념적 도구
- 현실 세계와 데이터베이스 사이의 **중간 과정** 역할

#### 데이터 모델의 구성 요소
- **개체(Entity)**
- **속성(Attribute)**
- **관계(Relationship)**

#### 데이터 모델의 종류
- **개념적 데이터 모델**
- **논리적 데이터 모델**
- **물리적 데이터 모델**

#### 데이터 모델에 표시할 요소
- **구조(Structure)**
- **연산(Operation)**
- **제약 조건(Constraint)**

> ⭐ `구성 요소 = 개체·속성·관계`  
> ⭐ `표시 요소 = 구조·연산·제약조건`

### 2. 데이터 모델의 구성 요소

| 구성 요소 | 의미 |
|---|---|
| **개체(Entity)** | 데이터베이스에 표현하려는 사람·사물·개념 등 현실 세계의 대상 |
| **속성(Attribute)** | 데이터의 가장 작은 논리적 단위 / 개체를 구성하는 데이터 항목 |
| **관계(Relationship)** | 둘 이상의 개체 또는 속성 사이의 논리적 연관성 |

#### 관계의 형태
| 형태 | 의미 |
|---|---|
| **1 : 1** | 한 개체 ↔ 한 개체 |
| **1 : N** | 한 개체 ↔ 여러 개체 |
| **N : M** | 여러 개체 ↔ 여러 개체 |

> ⭐ 관계 형태 → `1:1 / 1:N / N:M`

### 3. 개념적 데이터 모델
- 현실 세계에 대한 인식을 추상적 개념으로 표현하는 과정
- **개체 타입(Entity Type)**과 개체 타입 사이의 **관계 타입(Relationship Type)**을 이용해 현실 세계를 표현
- 현실 세계의 개체를 사람이 이해할 수 있는 정보 구조로 표현하므로 **정보 모델**이라고도 함
- 대표적인 개념적 데이터 모델 → **E-R 모델**

> ⭐ `개념적 데이터 모델 = 정보 모델 / E-R 모델`

### 4. 논리적 데이터 모델
- 개념적 설계에서 얻은 개념적 구조를 컴퓨터가 이해하고 처리할 수 있는 **논리적 구조로 변환**하는 과정
- 데이터 타입과 데이터 타입 간의 관계를 이용해 현실 세계를 표현
- 단순히 **데이터 모델**이라고 하면 논리적 데이터 모델을 의미하기도 함
- 특정 DBMS는 특정 논리적 데이터 모델을 선택하여 사용

#### 논리적 데이터 모델의 종류
- **관계 데이터 모델(Relational Model)**
- **계층 데이터 모델(Hierarchical Model)**
- **네트워크 데이터 모델(Network Model)**

### 5. 데이터 모델에 표시할 요소

| 요소 | 핵심 |
|---|---|
| **구조(Structure)** | 논리적으로 표현된 개체 타입 간의 **관계 / 데이터 구조** |
| **연산(Operation)** | 데이터베이스의 실제 데이터를 **처리하는 작업에 대한 명세** |
| **제약 조건(Constraint)** | 데이터베이스에 저장될 수 있는 실제 데이터의 **논리적 제한 조건** |

> ⭐ `Structure = 구조 / Operation = 처리 / Constraint = 제한`

## SECTION 062. E-R(개체-관계) 모델

### 1. E-R(Entity-Relationship, 개체-관계) 모델의 개요
- **1976년 Peter Chen**이 제안
- 현실 세계의 데이터를 **개체와 관계를 중심으로 표현**하는 대표적인 개념적 데이터 모델
- 개체 타입과 관계 타입을 이용해 현실 세계를 개념적으로 표현
- 기본 구성 요소 → **개체(Entity) / 관계(Relationship) / 속성(Attribute)**
- 특정 DBMS를 고려하지 않는 **DBMS 독립적 모델**
- `1:1 / 1:N / N:M` 등의 관계 유형을 제한 없이 표현 가능

> ⭐ `E-R 모델 = Peter Chen / 개체·관계·속성 / DBMS 독립적`

### 2. E-R 다이어그램(Entity-Relationship Diagram)
- E-R 모델의 기본 아이디어를 **기호를 이용해 시각적으로 표현**한 그림
- 개체 타입과 관계 타입 등을 도식화하여 현실 세계의 구조 표현

#### 주요 기호
| 기호 형태 | 의미 |
|---|---|
| **사각형** | 개체(Entity) 타입 |
| **마름모** | 관계(Relationship) 타입 |
| **타원** | 속성(Attribute) |
| **이중 타원** | 다중값 속성 |
| **밑줄이 있는 속성** | 기본키 속성 |
| **여러 타원으로 연결** | 복합 속성 |
| **1 / N / M 표시** | 개체 간 대응수(Cardinality) |
| **선(Link)** | 개체 타입과 속성 등을 연결 |

> ⭐ `사각형 = 개체 / 마름모 = 관계 / 타원 = 속성`

### 3. E-R 다이어그램의 관계 대응수
- 관계에 참여하는 개체들의 대응 관계를 `1:1`, `1:N`, `N:M` 등으로 표현

| 관계 | 의미 |
|---|---|
| **1 : 1** | X의 한 개체 ↔ Y의 한 개체 |
| **1 : N** | X의 한 개체 ↔ Y의 여러 개체 |
| **N : M** | X의 여러 개체 ↔ Y의 여러 개체 |

## SECTION 063. 관계형 데이터베이스의 구조

### 1. 관계형 데이터베이스의 개요
- **1970년 IBM의 E. F. Codd**가 처음 제안
- 관계형 데이터베이스를 구성하는 **개체(Entity)와 관계(Relationship)를 모두 릴레이션(Relation)**이라는 표(Table)로 표현
- 릴레이션은 개체를 표현하는 **개체 릴레이션**과 관계를 나타내는 **관계 릴레이션**으로 구성 가능

#### 장·단점
- **장점** - 간결하고 이해하기 쉬우며 다른 데이터베이스로 변환하기 용이
- **단점** - 성능이 다소 떨어질 수 있음

> ⭐ `관계형 DB = Codd / 모든 데이터를 Table(Relation)로 표현`

### 2. 관계형 데이터베이스의 Relation 구조
- **릴레이션(Relation)** - 행과 열로 구성된 2차원 테이블
- **릴레이션 스키마(Relation Schema)** - 릴레이션의 구조
- **릴레이션 인스턴스(Relation Instance)** - 특정 시점에 릴레이션에 저장된 실제 튜플들의 집합

#### 튜플(Tuple)
- 릴레이션을 구성하는 각각의 **행(Row)**
- 속성들의 모임
- 파일 구조에서 **레코드(Record)**와 같은 의미
- 튜플의 수 → **카디널리티(Cardinality), 기수, 대응수**

> ⭐ `Tuple = 행 = Record / 튜플 수 = Cardinality`

#### 속성(Attribute)
- 데이터베이스를 구성하는 **가장 작은 논리적 단위**
- 파일 구조의 **데이터 항목 또는 필드(Field)**에 해당
- 개체의 특성을 기술
- 속성의 수 → **디그리(Degree), 차수**

> ⭐ `Attribute = 열 = Field / 속성 수 = Degree`

#### 도메인(Domain)
- 하나의 속성이 취할 수 있는 **같은 타입의 원자값(Atomic Value)들의 집합**
- 실제 속성값이 허용되는 범위를 정의하여 값의 적합성을 검사하는 데 사용

> ⭐ `Domain = 속성이 가질 수 있는 값의 범위`

### 3. 릴레이션의 특징
- 한 릴레이션에는 **동일한 튜플이 존재할 수 없음**
- 튜플 사이에는 **순서가 없음**
- 삽입·삭제·갱신에 따라 릴레이션은 시간에 따라 변함
- 릴레이션을 구성하는 **속성 사이에도 순서가 없음**
- 속성 이름은 **유일**해야 하지만 속성값은 중복될 수 있음
- 튜플을 유일하게 식별하기 위해 **키(Key)** 사용
- 속성값은 **원자값(Atomic Value)**이어야 함

> ⭐ 릴레이션 특징 → `튜플 중복 X / 튜플·속성 순서 X / 속성값 원자값`

## SECTION 064. 관계형 데이터베이스의 제약 조건 - 키(Key)

### 1. 키(Key)의 개념 및 종류
- 키는 데이터베이스에서 조건을 만족하는 튜플을 찾거나 순서대로 접근할 때 기준이 되는 **속성 또는 속성들의 집합**
- 튜플을 서로 구별할 수 있는 기준

#### 키의 종류
- **후보키(Candidate Key)**
- **기본키(Primary Key)**
- **대체키(Alternate Key)**
- **슈퍼키(Super Key)**
- **외래키(Foreign Key)**

> ⭐ 키 종류 → `후보 / 기본 / 대체 / 슈퍼 / 외래`

### 2. 후보키(Candidate Key)
- 릴레이션을 구성하는 속성 중 튜플을 **유일하게 식별하기 위해 사용할 수 있는 속성들의 부분집합**
- 하나의 릴레이션에는 반드시 **하나 이상의 후보키** 존재
- 모든 튜플을 유일하게 식별하면서 **유일성 + 최소성**을 만족

#### 후보키 조건
- **유일성(Unique)** - 하나의 키 값으로 하나의 튜플만 유일하게 식별
- **최소성(Minimality)** - 튜플을 식별하는 데 꼭 필요한 최소한의 속성으로 구성

> ⭐ `후보키 = 유일성 + 최소성`

### 3. 기본키(Primary Key)
- 후보키 중에서 특별히 선택된 **주키(Main Key)**
- 한 릴레이션에서 특정 튜플을 유일하게 구별할 수 있는 속성
- 기본키 값은 **중복될 수 없음**
- 기본키로 지정된 속성에는 **NULL 값이 올 수 없음**

> ⭐ `기본키 = 후보키 중 대표 / 중복 X / NULL X`

### 4. 대체키(Alternate Key)
- 후보키가 둘 이상일 때 **기본키를 제외한 나머지 후보키**
- **보조키**라고도 함

> ⭐ `대체키 = 후보키 - 기본키`

### 5. 슈퍼키(Super Key)
- 한 릴레이션에서 튜플을 유일하게 식별할 수 있는 **하나 이상의 속성 집합**
- **유일성은 만족**하지만 **최소성은 만족하지 않을 수 있음**
- 불필요한 속성이 포함되어도 튜플을 유일하게 구별할 수 있으면 슈퍼키

> ⭐ `슈퍼키 = 유일성 O / 최소성 X 가능`

### 6. 외래키(Foreign Key)
- 다른 릴레이션의 **기본키를 참조하는 속성 또는 속성들의 집합**
- 릴레이션 사이의 **참조 관계**를 표현
- 한 릴레이션의 속성과 참조 릴레이션의 기본키가 **동일한 도메인**에 정의될 때 외래키가 될 수 있음
- 외래키로 지정되면 참조 릴레이션의 기본키에 없는 값은 입력할 수 없음

> ⭐ `외래키 = 다른 릴레이션의 기본키 참조`

## SECTION 065. 관계형 데이터베이스의 제약 조건 - 무결성

### 1. 무결성(Integrity)의 개념 및 종류
- 무결성은 데이터베이스에 저장된 데이터 값과 실제 세계의 값이 **일치하는 정확성**을 의미
- 데이터베이스에 저장된 데이터의 정확성을 보장하기 위해 부정확한 값이 저장되는 것을 방지하는 **제약 조건**

#### 무결성의 종류
- **개체 무결성**
- **도메인 무결성**
- **참조 무결성**
- **사용자 정의 무결성**

### 2. 개체 무결성(Entity Integrity, 실체 무결성)
- 기본 테이블의 **기본키를 구성하는 어떤 속성도 NULL 값이나 중복값을 가질 수 없음**

> ⭐ `개체 무결성 = 기본키 NULL X + 중복 X`

### 3. 도메인 무결성(Domain Integrity, 영역 무결성)
- 주어진 속성값이 정의된 **도메인에 속한 값이어야 한다**는 규정
- 속성에 지정된 범위·형식에 맞는 값만 저장

> ⭐ `도메인 무결성 = 지정된 값의 범위 준수`

### 4. 참조 무결성(Referential Integrity)
- **외래키 값은 NULL이거나 참조 릴레이션의 기본키 값과 동일**해야 함
- 외래키와 참조 대상 기본키는 **도메인과 속성의 개수가 같아야 함**

> ⭐ `참조 무결성 = 외래키 → 참조 기본키에 존재하는 값 또는 NULL`

### 5. 사용자 정의 무결성(User-Defined Integrity)
- 속성값이 사용자가 정의한 **제약 조건을 만족**해야 한다는 규정

### 6. 데이터 무결성 강화
- 무결성은 **애플리케이션 / 데이터베이스 트리거 / 제약 조건** 등을 이용하여 강화할 수 있음

#### 애플리케이션
- 데이터 삽입·수정·삭제 시 무결성 조건을 검증하는 코드를 **응용 프로그램 내부에 추가**
- 데이터베이스에서 수행하기 어려운 복잡한 규칙도 애플리케이션에서 처리 가능

**장점**
- 사용자 정의 같은 복잡한 무결성 규칙 구현 가능

**단점**
- 코드가 여러 곳에 분산되어 관리가 어렵고 구현 방식에 따라 일관성이 떨어질 수 있음

#### 데이터베이스 트리거(Trigger)
- 무결성 조건을 실행하는 **절차형 SQL**을 트리거 이벤트에 추가

**장점**
- 통합 관리 가능
- 복잡한 무결성 조건 구현 가능

**단점**
- 응답 시간 증가
- 시스템 복잡도 증가

#### 제약 조건(Constraint)
- 데이터베이스에 제약 조건을 설정하여 무결성 유지

**장점**
- 통합 관리 가능
- 간단한 선언으로 구현 가능
- 변경이 쉬움
- 오류 데이터 발생 방지에 효과적

**단점**
- 복잡한 제약 조건 구현과 예외적인 처리에는 한계

## SECTION 066. 관계대수 및 관계해석

### 1. 관계대수의 개요
- 관계형 데이터베이스에서 원하는 정보를 얻기 위해 하나 또는 두 개의 릴레이션에 **연산자를 적용하여 새로운 릴레이션을 유도하는 절차적 언어**
- 원하는 결과를 얻기 위해 **연산의 순서를 명시**
- 관계대수식의 결과도 하나의 **릴레이션**

#### 순수 관계 연산자
- **Select**
- **Project**
- **Join**
- **Division**

#### 일반 집합 연산자
- **UNION(합집합)**
- **INTERSECTION(교집합)**
- **DIFFERENCE(차집합)**
- **CARTESIAN PRODUCT(교차곱)**

> ⭐ `순수 = Select / Project / Join / Division`

### 2. Select(선택)
- 릴레이션의 튜플 중에서 **조건을 만족하는 튜플의 부분집합**을 구해 새로운 릴레이션을 만드는 연산
- 릴레이션의 **행(Row)**에 해당하는 튜플을 선택 → **수평 연산**
- 연산자 → **σ(시그마)**

```text
σ조건(R)
```

- 조건에는 비교 연산자 `=, ≠, <, ≤, >, ≥` 사용 가능
- 논리 연산자 `AND(∧), OR(∨), NOT(¬)` 사용 가능

> ⭐ `Select = 행 선택 / σ`

### 3. Project(프로젝트)
- 릴레이션에서 주어진 **속성 리스트에 제시된 속성값만 추출**하여 새로운 릴레이션을 만드는 연산
- 결과에 중복 튜플이 발생하면 **중복 제거**
- 릴레이션의 **열(Column)**에 해당하는 속성을 추출 → **수직 연산**
- 연산자 → **π(파이)**

```text
π속성리스트(R)
```

> ⭐ `Project = 열 선택 / π / 중복 제거`

### 4. Join(조인)
- 공통 속성을 중심으로 **두 개의 릴레이션을 하나로 합쳐 새로운 릴레이션을 만드는 연산**
- Cartesian Product를 수행한 뒤 조건에 맞는 튜플을 Select한 결과와 같은 형태
- 연산자 → **⋈**

```text
R ⋈조건 S
```

#### 자연 조인(Natural Join)
- 조인 조건이 `=`인 **동등 조인**의 결과에서 중복된 속성을 하나 제거하여 표현

> ⭐ `Join = 두 릴레이션 결합 / ⋈`

### 5. Division(디비전)
- `R(X, Y)`와 `S(Y)`가 있을 때, **S의 모든 Y값과 관련된 R의 X값**을 구하는 연산
- 연산자 → **÷**

> ⭐ `Division = S의 모든 조건을 만족하는 값 추출`

### 6. 일반 집합 연산자
- 합집합·교집합·차집합을 수행하려면 두 릴레이션이 **합병 가능(Union Compatible)**해야 함
- 대응하는 속성들의 **도메인이 같아야 함**

| 연산자 | 의미 | 핵심 |
|---|---|---|
| **UNION `∪`** | 합집합 | R 또는 S에 존재하는 튜플 |
| **INTERSECTION `∩`** | 교집합 | R과 S에 공통으로 존재하는 튜플 |
| **DIFFERENCE `-`** | 차집합 | R에는 있고 S에는 없는 튜플 |
| **CARTESIAN PRODUCT `×`** | 교차곱 | R의 각 튜플과 S의 각 튜플을 모두 결합 |

#### 카디널리티 핵심
- `|R ∪ S| ≤ |R| + |S|`
- `|R ∩ S| ≤ MIN(|R|, |S|)`
- `|R - S| ≤ |R|`
- `|R × S| = |R| × |S|`
- 교차곱의 차수 → `Degree(R) + Degree(S)`

> ⭐ `Cartesian Product = 경우의 수 모두 결합 / 카디널리티 곱`

### 7. 관계해석(Relational Calculus)
- 관계 데이터 모델의 제안자인 **E. F. Codd**가 수학의 **Predicate Calculus(술어 해석)**에 기반하여 제안
- 관계대수와 달리 원하는 정보가 **무엇인지**만 정의하는 **비절차적 언어**
- 원하는 정보를 얻는 처리 과정을 직접 명시하지 않음
- **튜플 관계해석 / 도메인 관계해석**이 있음
- 기본적인 처리 능력은 관계대수와 동일

#### 주요 논리 기호
| 기호 | 의미 |
|---|---|
| **∀** | 전칭 정량자 - 가능한 모든 튜플에 대하여(For All) |
| **∃** | 존재 정량자 - 조건에 맞는 튜플이 존재(There Exists) |

> ⭐ `관계대수 = 절차적 / 관계해석 = 비절차적`

## SECTION 067. 정규화(Normalization)

### 1. 정규화의 개요
- **함수적 종속성** 등의 종속성 이론을 이용하여 잘못 설계된 릴레이션 스키마를 더 작은 속성들의 집합으로 분해하여 **바람직한 스키마로 만드는 과정**
- 하나의 릴레이션을 다른 릴레이션으로 변환할 수 있음
- 정규형 → `1NF / 2NF / 3NF / BCNF / 4NF / 5NF`
- 단계가 높아질수록 **제약 조건이 강해짐**
- 데이터베이스의 **논리적 설계 단계**에서 수행
- 데이터 모델의 일관성·정확성·단순성·비중복성·안정성을 높임
- 지나치게 정규화하면 릴레이션 수가 많아져 조회 시 조인이 증가할 수 있음

> ⭐ `정규화 = 중복 줄이고 이상 방지 / 논리적 설계 단계`

### 2. 정규화의 목적
- 데이터 구조의 안정성·무결성 유지
- 어떠한 릴레이션이라도 데이터베이스 내에서 표현 가능하도록 함
- 효과적인 검색 알고리즘 생성 가능
- 데이터 중복을 제거하여 **이상(Anomaly) 발생 방지** 및 저장 공간 최소화
- 데이터 삽입 시 릴레이션을 재구성할 필요성 감소
- 데이터 모델을 단순하게 구성
- 속성의 배열 상태를 검증 가능
- 개체와 속성의 누락 여부 확인 가능
- 자료 검색과 발견을 쉽게 함

### 3. 이상(Anomaly)의 개념 및 종류
- 정규화를 거치지 않은 릴레이션에 데이터가 중복 저장되어 삽입·삭제·갱신 과정에서 발생하는 **비정상적인 현상**

| 이상 | 의미 |
|---|---|
| **삽입 이상(Insert Anomaly)** | 튜플 삽입 시 의도하지 않은 불필요한 값까지 함께 삽입 |
| **삭제 이상(Delete Anomaly)** | 튜플 삭제 시 의도하지 않은 다른 정보까지 함께 삭제 |
| **갱신 이상(Update Anomaly)** | 속성값 갱신 시 일부만 변경되어 정보의 불일치 발생 |

> ⭐ `이상 = 삽입 / 삭제 / 갱신`

### 4. 정규화의 원칙
- **정보의 무손실 표현** - 하나의 스키마를 다른 스키마로 변환할 때 정보 손실이 없어야 함
- **분리의 원칙** - 독립적인 관계는 독립된 릴레이션으로 분리하여 표현
- **데이터 중복성 감소**

### 5. 정규화 과정

#### 함수적 종속(Functional Dependency)
- 어떤 속성 `X`의 값이 결정되면 다른 속성 `Y`의 값이 하나로 결정될 때 `Y`는 `X`에 함수적으로 종속

```text
X → Y
```

- `X` → **결정자(Determinant)**
- `Y` → **종속자(Dependent)**

#### 완전 함수적 종속
- 복합 결정자의 **전체 속성**에 의해서만 종속 속성이 결정되는 관계

#### 부분 함수적 종속
- 복합 결정자의 **일부 속성만으로도** 종속 속성이 결정되는 관계

#### 이행적 함수적 종속
```text
X → Y, Y → Z  이면  X → Z
```

#### 다치 종속(Multi-Valued Dependency)
- 하나의 결정자에 대해 여러 개의 독립적인 값이 대응되는 종속 관계
- 표기 → `A →→ B`

#### 조인 종속(Join Dependency)
- 하나의 릴레이션을 여러 릴레이션으로 분해했다가 **조인하여 원래 릴레이션으로 복원**할 수 있는 관계

### 정규형 단계

| 정규형 | 조건 | 제거 대상 |
|---|---|---|
| **1NF(제1정규형)** | 모든 속성의 도메인이 **원자값(Atomic Value)**으로 구성 | 반복·복합 값 |
| **2NF(제2정규형)** | 1NF + 기본키가 아닌 모든 속성이 기본키에 **완전 함수적 종속** | **부분 함수적 종속** |
| **3NF(제3정규형)** | 2NF + 기본키가 아닌 모든 속성이 기본키에 **이행적으로 종속되지 않음** | **이행적 함수 종속** |
| **BCNF** | 릴레이션의 **모든 결정자가 후보키** | 후보키가 아닌 결정자 |
| **4NF(제4정규형)** | 다치 종속을 제거하여 정규화 | **다치 종속** |
| **5NF(제5정규형, PJ/NF)** | 모든 조인 종속이 후보키를 통해서만 성립 | **조인 종속** |

### 정규화 과정 암기

```text
비정규 릴레이션
  ↓ 도메인 원자값
1NF
  ↓ 부분적 함수 종속 제거
2NF
  ↓ 이행적 함수 종속 제거
3NF
  ↓ 결정자이면서 후보키가 아닌 것 제거
BCNF
  ↓ 다치 종속 제거
4NF
  ↓ 조인 종속성 이용
5NF
```

> ⭐ `도 → 부 → 이 → 결 → 다 → 조`  
> ⭐ `1NF 원자값 / 2NF 부분 / 3NF 이행 / BCNF 결정자 / 4NF 다치 / 5NF 조인`

## SECTION 068. 반정규화(Denormalization)

### 1. 반정규화의 개요
- 시스템의 **성능 향상 / 개발 및 운영의 편의성**을 위해 정규화된 데이터 모델을 **통합·중복·분리**하는 과정
- 의도적으로 정규화 원칙을 위배하는 행위
- 시스템 성능과 관리 효율은 증가할 수 있으나 **데이터의 일관성·정합성은 저하될 수 있음**
- 지나친 반정규화는 오히려 성능을 떨어뜨릴 수 있음
- 데이터의 일관성과 무결성을 우선 검토한 뒤 데이터베이스 성능을 높이는 방향으로 결정

#### 반정규화 방법
- **테이블 통합**
- **테이블 분할**
- **중복 테이블 추가**
- **중복 속성 추가**

> ⭐ `반정규화 = 성능을 위해 의도적으로 정규화 원칙 위배`

### 2. 테이블 통합
- 두 테이블이 자주 **Join**되거나 함께 사용되어 성능이 저하될 때 하나의 테이블로 합치는 방법
- 프로세스가 동일하게 자주 처리되거나 두 테이블을 이용한 조회가 많을 때 고려

#### 테이블 통합 종류
- **1 : 1 관계 테이블 통합**
- **1 : N 관계 테이블 통합**
- **슈퍼타입 / 서브타입 테이블 통합**

#### 테이블 통합 시 고려사항
- 검색은 간단해질 수 있지만 레코드 증가로 **처리량이 증가**할 수 있음
- 입력·수정·삭제 처리량 증가로 **갱신 성능이 저하**될 수 있음
- `NOT NULL / DEFAULT / CHECK` 등의 제약 조건 설계가 어려워질 수 있음

### 3. 테이블 분할
- 하나의 테이블을 **수직 또는 수평으로 분할**하는 방법

#### 수평 분할(Horizontal Partitioning)
- **레코드(Row)**를 기준으로 테이블 분할
- 사용 빈도가 다른 레코드 집합을 사용자별·업무별로 분리하는 경우 사용

#### 수직 분할(Vertical Partitioning)
- 테이블의 **속성(Column)**을 기준으로 분할
- 속성이 너무 많은 테이블에서 특정 속성군을 분리

##### 수직 분할의 예
- **갱신 위주의 속성 분할** - 자주 갱신되는 속성을 분리하여 레코드 잠금에 따른 영향 감소
- **자주 조회되는 속성 분할** - 자주 사용하는 속성만 분리하여 조회 성능 향상
- **크기가 큰 속성 분할** - 대용량 속성을 별도 테이블로 분리
- **보안을 적용해야 하는 속성 분할** - 보안이 필요한 속성을 별도 분리

#### 테이블 분할 시 고려사항
- 기본키의 유일성 관리가 어려워질 수 있음
- 데이터량이 적다면 분할 필요성을 검토
- 분할된 정보를 모두 조회할 경우 오히려 속도가 느려질 수 있음
- 데이터 접근이 집중되는 구간을 고려하여 분할 여부 결정

> ⭐ `수평 = 행 분할 / 수직 = 열 분할`

### 4. 중복 테이블 추가
- 다른 테이블에서 데이터를 자주 추출하거나 다른 서버의 데이터를 반복적으로 이용해야 할 때 **같은 데이터를 가진 테이블을 추가**하여 작업 효율 향상

#### 중복 테이블을 추가하는 경우
- 정규화로 인해 수행 속도가 느려지는 경우
- 많은 범위의 데이터를 자주 처리해야 하는 경우
- 특정 범위의 데이터를 자주 처리해야 하는 경우
- 처리 범위를 줄이지 않고서는 수행 속도를 개선하기 어려운 경우

#### 중복 테이블 추가 방법
- **집계 테이블 추가** - 집계 결과를 미리 저장하는 테이블 생성 / 원본 테이블 변경 시 갱신을 위한 트리거 등을 고려
- **진행 테이블 추가** - 이력 관리 등의 목적으로 진행 상태에 대한 테이블 추가
- **특정 부분만을 포함하는 테이블 추가** - 자주 사용하는 특정 부분만 별도 테이블로 구성

### 5. 중복 속성 추가
- 조인 시 데이터를 조회하는 경로를 단축하기 위해 **자주 사용하는 속성을 하나 더 추가**하는 방법
- 조회 경로가 단순해져 성능은 좋아질 수 있으나 **추가 저장 공간**과 데이터 일관성 관리가 필요

#### 중복 속성을 추가하는 경우
- 조인이 자주 발생하는 속성
- 접근 경로가 복잡한 속성
- 검색 조건으로 자주 사용하는 속성
- 기본키의 형태가 적절하지 않거나 여러 속성으로 구성된 경우

#### 중복 속성 추가 시 고려사항
- 테이블 중복과 속성 중복을 함께 검토
- 데이터의 일관성과 무결성에 유의
- SQL 그룹 함수로 처리할 수 있는지 검토
- 저장 공간 증가 고려

## SECTION 069. 시스템 카탈로그

### 1. 시스템 카탈로그(System Catalog)의 의미
- 시스템 그 자체에 관련된 정보와 사용자 정보를 포함하여 다양한 객체에 관한 정보를 갖는 **시스템 데이터베이스**
- DBMS가 지원하는 모든 데이터 객체에 대한 정의나 명세 정보를 유지·관리하는 **시스템 테이블**
- 카탈로그에 저장되는 정보는 **데이터 사전(Data Dictionary)**에 저장되므로 두 용어는 같은 의미로 사용되기도 함

> ⭐ `시스템 카탈로그 = DB 객체의 정보를 저장하는 시스템 DB`

### 2. 시스템 카탈로그 저장 정보
- 시스템 카탈로그에 저장된 정보 → **메타 데이터(Meta-Data)**

#### 메타 데이터의 유형
- **데이터베이스 객체 정보** - 테이블(Table), 인덱스(Index), 뷰(View) 등의 구조·통계 정보
- **사용자 정보** - 사용자 ID, 패스워드, 접근 권한 등
- **테이블 무결성 제약 조건 정보** - 기본키, 외래키, NULL 허용 여부 등
- **함수 / 프로시저 / 트리거** 등에 대한 정보

> ⭐ `카탈로그의 정보 = Metadata`

### 3. 카탈로그의 특징
- 카탈로그 자체도 **시스템 테이블**로 구성되어 일반 사용자가 SQL로 내용을 검색할 수 있음
- 사용자가 `INSERT / DELETE / UPDATE`로 카탈로그를 직접 변경하는 것은 허용되지 않음
- 데이터베이스 시스템마다 **구조가 다름**
- DBMS가 스스로 **생성하고 유지**
- 사용자가 SQL을 실행해 기본 테이블·뷰·인덱스 등에 변경을 주면 **시스템 카탈로그가 자동 갱신**
- 분산 데이터베이스의 카탈로그는 일반 객체 정보뿐 아니라 **위치 투명성·중복 투명성 제공에 필요한 제어 정보**도 포함

> ⭐ `조회는 가능 / 직접 갱신은 X / DBMS가 자동 관리`

### 4. 카탈로그 / 데이터 사전을 참조하기 위한 DBMS 내부 모듈

#### 데이터 정의어 번역기(DDL Compiler)
- DDL 명령을 **메타 데이터를 갖는 테이블(카탈로그)**로 변환하여 데이터 사전에 저장

#### 데이터 조작어 번역기(DML Compiler)
- 응용 프로그램에 삽입된 DML문을 주 언어로 표현된 **프로시저 호출**로 변환하여 질의 처리기와 상호 통신

#### Data Directory
- 데이터 사전에 수록된 데이터에 **실제로 접근하는 데 필요한 정보**를 관리·유지하는 시스템
- 시스템 카탈로그는 사용자와 시스템 모두 접근 가능하지만 **Data Directory는 시스템만 접근 가능**

#### 질의 최적화기(Query Optimizer)
- 사용자의 요구를 **가장 효율적인 형태로 변환**하고 질의를 처리할 최적의 전략을 선택

#### 트랜잭션 처리기(Transaction Processor)
- 여러 사용자가 동시에 수행하는 트랜잭션의 문제를 해결하고 데이터베이스 자원을 올바르게 사용할 수 있도록 관리

> ⭐ `DDL → 정의 / DML → 조작 / Optimizer → 최적 경로 / Transaction Processor → 동시 처리`
