# 02. 물리 데이터베이스 설계

## SECTION 070. 트랜잭션 분석 / CRUD 분석

### 1. 트랜잭션(Transaction)의 정의
- **트랜잭션** - 데이터베이스의 상태를 변화시키기 위해 수행하는 **논리적 기능 수행의 작업 단위** 또는 한꺼번에 모두 수행되어야 할 **일련의 연산들의 집합**
- 데이터베이스 시스템에서 **병행 제어 및 회복 작업의 논리적 단위**
- 사용자의 요구에 시스템이 응답하기 위한 **상태 변환 과정의 작업 단위**로 사용

> ⭐ `트랜잭션 = DB 상태를 변화시키는 논리적 작업 단위`

### 2. 트랜잭션의 상태

| 상태 | 핵심 |
|---|---|
| **활동(Active)** | 트랜잭션이 **실행 중**인 상태 |
| **실패(Failed)** | 트랜잭션 실행 중 **오류가 발생하여 중단**된 상태 |
| **철회(Aborted)** | 비정상적으로 종료되어 **Rollback 연산을 수행한 상태** |
| **부분 완료(Partially Committed)** | 트랜잭션의 모든 연산을 성공적으로 실행한 후 **Commit 실행 직전** 상태 |
| **완료(Committed)** | 트랜잭션의 모든 연산을 성공적으로 실행한 후 **Commit까지 완료**한 상태 |

> ⭐ `Active → Partially Committed → Committed`  
> ⭐ 오류 발생 → `Failed → Aborted`

### 3. 트랜잭션의 특성(ACID)

| 특성 | 핵심 |
|---|---|
| **Atomicity(원자성)** | 모든 연산이 **모두 반영(Commit)**되거나 **전혀 반영되지 않아야 함(Rollback)** |
| **Consistency(일관성)** | 트랜잭션이 성공적으로 완료되면 DB가 **일관된 상태**로 변환되어야 함 |
| **Isolation(독립성, 격리성)** | 둘 이상의 트랜잭션이 동시에 실행되더라도 **서로의 연산에 끼어들 수 없음** |
| **Durability(영속성, 지속성)** | 성공적으로 완료된 트랜잭션의 결과는 **영구적으로 반영**되어야 함 |

#### Atomicity 핵심
- 트랜잭션의 연산은 모두 데이터베이스에 반영되거나 모두 취소되어야 함
- 하나의 연산이라도 오류가 발생하면 트랜잭션 전체를 취소

#### Isolation 핵심
- 수행 중인 트랜잭션은 완료될 때까지 다른 트랜잭션에서 수행 결과를 참조할 수 없음

> ⭐ ACID → `원자성 / 일관성 / 독립성 / 영속성`

### 4. CRUD 분석
- **CRUD** - `Create / Read / Update / Delete`의 첫 글자를 모아 만든 용어
- 프로세스와 테이블 사이에서 발생하는 트랜잭션을 **생성·읽기·갱신·삭제** 관점으로 분석
- 테이블에 발생하는 트랜잭션의 유형을 파악하여 **데이터베이스 구조 및 성능 분석**에 활용
- CRUD 분석을 통해 특정 프로세스에서 트랜잭션이 몰리는 테이블을 파악할 수 있음

> ⭐ `C = 생성 / R = 읽기 / U = 갱신 / D = 삭제`

### 5. CRUD 매트릭스
- **CRUD 매트릭스** - 2차원 표 형태로 **행(Row)에 프로세스**, **열(Column)에 테이블**을 놓고 각 프로세스가 테이블에 수행하는 작업을 표시
- 프로세스와 데이터 사이의 **상관관계**를 표현
- 각 셀에 `C / R / U / D`를 표시하여 트랜잭션 종류를 확인
- 한 셀에 여러 작업이 발생하는 경우 목적에 따라 여러 문자를 함께 표시할 수 있으며, 대표 작업만 표시할 경우 **C → D → U → R** 순으로 우선순위를 적용 가능
- 모든 프로세스가 `R`만 수행하는 테이블은 **Create·Update·Delete를 수행하는 프로세스가 누락되었는지 확인**
- CRUD가 전혀 표시되지 않는 테이블이나 프로세스가 있다면 **불필요하거나 누락된 사항인지 확인**

> ⭐ `CRUD 매트릭스 = 프로세스 × 테이블`

### 6. 트랜잭션 분석
- CRUD 매트릭스를 기반으로 테이블에 발생하는 **트랜잭션 양을 분석**하여 DB의 용량을 산정하고 **DB 구조를 최적화**하는 작업
- 트랜잭션 분석은 업무 개발 담당자가 수행
- 프로세스가 과도하게 집중되는 테이블을 확인하여 **디스크 구성 및 데이터베이스 구조 개선**에 활용

### 7. 트랜잭션 분석서
- CRUD 매트릭스를 이용해 작성하며 구성 요소는 다음과 같음

| 항목 | 핵심 |
|---|---|
| **단위 프로세스** | 업무를 발생시키는 가장 작은 단위의 프로세스 |
| **CRUD 연산** | 해당 프로세스가 테이블에 수행하는 `C / R / U / D` 연산 |
| **테이블명 / 컬럼명** | 프로세스가 접근하는 테이블과 해당 컬럼 |
| **테이블 참조 횟수** | 프로세스가 테이블을 참조하는 횟수 |
| **트랜잭션 수** | 주기별로 수행되는 트랜잭션 수 |
| **발생 주기** | 연·분기·월·일·시간 등 트랜잭션 횟수를 측정하기 위한 주기 |

> ⭐ `트랜잭션 분석서 = 단위 프로세스 + CRUD + 테이블/컬럼 + 참조 횟수 + 트랜잭션 수 + 발생 주기`

## SECTION 071. 인덱스 설계

### 1. 인덱스(Index)의 개요
- **인덱스** - 데이터 레코드를 빠르게 접근하기 위해 `<키 값, 포인터>` 쌍으로 구성되는 데이터 구조
- 인덱스는 데이터가 저장된 **물리적 구조와 밀접한 관계**가 있음
- 레코드가 삽입·삭제되면 물리적 구조가 변경될 수 있음
- 인덱스를 생성하면 데이터 저장 공간 외에 **인덱스를 위한 별도의 저장 공간**이 필요
- 데이터 삽입·삭제가 자주 일어나면 인덱스 구조를 변경하는 작업이 증가하여 성능이 저하될 수 있음
- 테이블을 삭제하면 해당 테이블과 관련된 인덱스도 함께 삭제
- 인덱스가 없는 상태에서 특정 값을 찾으려면 모든 데이터 페이지를 확인하는 **TABLE SCAN**이 발생
- 기본키를 위한 인덱스를 **기본 인덱스**, 기본 인덱스가 아닌 인덱스를 **보조 인덱스**라고 하며 대부분의 관계형 DBMS는 기본키에 대한 기본 인덱스를 자동으로 생성
- 인덱스 종류 → **트리 기반 / 비트맵 / 함수 기반 / 비트맵 조인 / 도메인 인덱스**

> ⭐ `인덱스 = 검색 속도 ↑ / 저장 공간·갱신 비용 ↑`

### 2. 클러스터드 인덱스 / 넌클러스터드 인덱스

| 종류 | 핵심 |
|---|---|
| **클러스터드 인덱스(Clustered Index)** | 인덱스 키 값에 따라 **데이터가 물리적으로 정렬·저장**되는 방식 |
| **넌클러스터드 인덱스(Non-Clustered Index)** | 실제 데이터의 물리적 순서를 변경하지 않고 **별도의 인덱스에서 데이터 위치를 가리키는 방식** |

#### 클러스터드 인덱스
- 인덱스 키의 순서에 따라 데이터가 정렬되어 있으므로 검색 범위가 넓을 때 효율적
- 삽입·삭제 시 데이터 재배치가 발생할 수 있음
- 데이터의 실제 저장 위치에 영향을 주기 때문에 한 테이블에서 제한적으로 사용

#### 넌클러스터드 인덱스
- 인덱스와 실제 데이터가 별도로 구성
- 인덱스에서 검색한 뒤 실제 데이터의 위치를 찾아 접근
- 데이터의 물리적 순서를 변경하지 않으므로 여러 개 생성 가능

> ⭐ `Clustered = 데이터 자체 정렬 / Non-Clustered = 별도 인덱스 + 위치 포인터`

### 3. 트리 기반 인덱스
- 트리 기반 인덱스는 저장 블록이 **트리 구조**를 이루며 값을 찾는 방식
- 대부분의 DBMS에서 **B 트리 또는 B+ 트리**를 주로 활용

#### B 트리 인덱스
- 일반적으로 사용되는 인덱스 방식
- 루트 노드에서 하위 노드로 키 값을 비교하면서 탐색하여 **단말 노드에서 원하는 데이터를 검색**
- 키 값과 레코드 위치를 가리키는 포인터가 트리 노드에 **오름차순으로 저장**
- 루트에서 모든 단말 노드까지의 깊이가 동일

##### 블록 구성
- **브랜치 블록(Branch Block)** - 분기를 위한 목적으로 사용 / 다음 단계를 가리키는 포인터 보유
- **리프 블록(Leaf Block)** - 인덱스를 구성하는 컬럼 데이터와 해당 데이터의 행 위치를 가리키는 **레코드 식별자**로 구성

#### B+ 트리 인덱스
- B 트리를 변형한 구조로 **인덱스 세트(Index Set)**와 **순차 세트(Sequence Set)**로 구성
- 인덱스 세트의 노드는 단말 노드까지 찾아가는 **경로만 제공**
- 순차 세트에 있는 단말 노드가 실제 데이터 레코드의 주소를 가리킴
- 인덱스 세트의 키 값이 단말 노드에도 다시 나타나므로 **단말 노드만 이용한 순차 처리**가 가능

> ⭐ `B+ 트리 = 인덱스 세트(경로) + 순차 세트(실제 주소)`

### 4. 비트맵 인덱스
- 인덱스 컬럼의 데이터를 **Bit 값 0 또는 1**로 변환하여 인덱스 키로 사용하는 방식
- 키 값을 포함하는 행(Row)의 **주소를 제공**하는 것이 목적
- **분포도가 좋은 컬럼**에 적합하여 성능 향상 효과를 얻을 수 있음
- Bit로 구성되어 **저장 공간이 작음**
- 여러 조건을 만족하는 튜플을 계산하는 질의에 적합
- 데이터의 삽입·삭제가 빈번하면 성능이 저하될 수 있음

> ⭐ `비트맵 = 0/1 / 저장 공간 작음 / 조건 조합 질의에 유리`

### 5. 함수 기반 인덱스
- 컬럼의 값 대신 컬럼에 특정 **함수(Function)나 수식(Expression)을 적용한 결과**를 저장하는 방식
- 데이터를 입력하거나 수정할 때 함수를 적용해야 하므로 부하가 발생할 수 있음
- 사용자 함수가 자주 호출되면 시스템 부하가 커질 수 있음
- 대소문자·계산식 등 **함수나 표현식이 반복적으로 사용되는 조건**에 유용
- 적용 가능한 함수의 종류 → 산술식, 사용자 정의 함수, PL/SQL Function, SQL Function, Package, Callout 등

### 6. 비트맵 조인 인덱스
- 다수의 조인된 객체로 구성된 인덱스
- 단일 객체로 구성된 일반 인덱스와 접근 방식이 다름
- 비트맵 인덱스와 **물리적 구조는 동일**

### 7. 도메인 인덱스
- 개발자가 필요한 인덱스를 **직접 만들어 사용하는 방식**
- 확장형 인덱스(Extensible Index)라고도 함
- 개발자가 필요한 인덱스를 지정하고 저장·관리 방법을 정의하여 프로그램에서 사용 가능

### 8. 인덱스 설계
- 인덱스 설계 시 자주 검색되는 컬럼이나 대용량 테이블 등을 기준으로 필요한 인덱스를 판단

#### 설계 순서
1. **인덱스의 액세스 형태**를 고려
2. **기본키 컬럼**을 중심으로 Unique 인덱스 고려
3. 인덱스에 적합한 **컬럼을 선정**
4. 인덱스를 **정의·명세**

### 9. 인덱스 대상 테이블 선정 기준
- **MULTI BLOCK READ** 수를 기준으로 판단
  - 예: MULTI BLOCK READ가 16이면 테이블 크기가 **16블록 이상인 경우** 인덱스 필요 여부를 검토
- 랜덤 액세스가 빈번한 테이블
- 특정 범위 또는 특정 순서로 데이터 조회가 필요한 테이블
- 다른 테이블과 **순차적 조인**이 발생하는 테이블

### 10. 인덱스 대상 컬럼 선정 기준
- 인덱스 컬럼의 **분포도가 10~15% 이내**인 컬럼
  - `분포도 = (컬럼값의 평균 Row 수 / 테이블의 총 Row 수) × 100`
- 분포도가 10~15% 이상이어도 부분 처리를 목적으로 하는 컬럼
- 입·출력 조회 등에서 조회 및 출력 목적으로 자주 사용되는 컬럼
- 기본키 또는 `Unique` 제약 조건처럼 **인덱스가 자동 생성되는 컬럼**
- 가능한 한 **수정이 빈번하지 않은 컬럼**
- `ORDER BY / GROUP BY / UNION`이 빈번한 컬럼
- 분포도가 좋은 컬럼은 **단독 인덱스**로 생성
- 인덱스들이 자주 조합되어 사용되면 하나의 **결합 인덱스(Concatenate Index)**로 생성

> ⭐ 인덱스 컬럼 → `검색 자주 / 분포도 적절 / 수정 적음 / 정렬·그룹 자주`

### 11. 인덱스 설계 시 고려사항
- 새로 추가되는 인덱스는 기존 **액세스 경로에 영향**을 미칠 수 있음
- 인덱스를 지나치게 많이 만들면 **오버헤드** 발생
- 넓은 범위를 인덱스로 처리하면 많은 오버헤드가 발생할 수 있음
- 인덱스를 만들면 **추가적인 저장 공간**이 필요
- 인덱스 대상 테이블의 **분포도와 부하를 고려**하여 설계

## SECTION 072. 뷰(View) 설계

### 1. 뷰(View)의 개요
- **뷰** - 사용자에게 접근이 허용된 자료만 선택적으로 보여주기 위해 하나 이상의 기본 테이블로부터 유도된 **가상 테이블**
- 저장장치에 물리적으로 존재하지 않지만 사용자에게는 실제 테이블처럼 보임
- 데이터 보정 작업, 처리 과정 시험 등 **임시적인 작업**에도 활용
- 논리적 독립성 및 시스템의 **보안성 향상**에 도움
- 뷰를 생성하면 정의가 시스템에 저장되며, 뷰를 이용한 질의가 수행되면 DBMS가 뷰 정의를 바탕으로 기본 테이블에 접근

> ⭐ `뷰 = 기본 테이블에서 유도된 가상 테이블`

### 2. 뷰(View)의 특징
- 기본 테이블로부터 유도되며 기본 테이블과 같은 형태의 구조를 사용하지만 **실제 데이터를 별도로 저장하지 않음**
- 가상 테이블이므로 물리적으로 구현되어 있지 않음
- 데이터의 **논리적 독립성** 제공
- 필요한 데이터만 뷰로 정의하여 처리할 수 있어 관리가 용이하고 명령문이 간단해짐
- 데이터 접근을 제한할 수 있어 **보안성 제공**
- 하나의 기본 테이블로 구성된 뷰는 조건에 따라 삽입·삭제·갱신 연산이 가능
- 한 번 정의된 뷰는 다른 뷰를 정의하는 기초로 사용할 수 있음
- 뷰가 정의된 기본 테이블 또는 기반 뷰를 삭제하면 이를 기초로 한 다른 뷰도 **자동으로 삭제**
- 뷰 정의 → `CREATE VIEW`
- 뷰 삭제 → `DROP VIEW`

### 3. 뷰(View)의 장·단점

| 장점 | 단점 |
|---|---|
| 논리적 데이터 독립성 제공 | 독립적인 인덱스를 가질 수 없음 |
| 동일 데이터에 대해 동시에 여러 사용자의 상이한 응용·요구 지원 | 뷰의 정의를 변경할 수 없음 |
| 사용자의 데이터 관리를 간단하게 함 | 삽입·삭제·갱신 연산에 제약이 따름 |
| 접근 제어를 통한 **자동 보안** 제공 |  |

> ⭐ `뷰 장점 = 독립성·보안·질의 단순화`

### 4. 뷰 설계 순서
1. **대상 테이블 선정**
   - 외부 시스템과 인터페이스에 관여하는 테이블
   - CRUD 매트릭스를 통해 여러 프로세스에서 동시에 자주 조회되는 테이블
   - 복잡한 SQL을 단순화할 필요가 있는 테이블
2. **대상 컬럼 선정**
   - 보안을 유지해야 하는 컬럼을 고려하여 필요한 컬럼 선택
3. **정의서 작성**
   - 뷰 정의서를 작성하여 뷰 이름, 관련 테이블·컬럼, 데이터 타입 등을 명세

### 5. 뷰 설계 시 고려사항
- 테이블 구조가 단순한 경우 동일 조건이 반복되면 하나의 뷰로 설계하여 사용자에게 동일한 조건을 제공할 수 있음
- 동일한 테이블이라도 업무별로 사용하는 부분이 다르면 **사용자·업무별 뷰**를 설계하여 사용 가능
- 데이터의 **보안 유지**를 고려하여 설계
- 중요 데이터는 불필요하게 노출되지 않도록 필요한 정보만 제공

## SECTION 073. 파티션 설계

### 1. 파티션(Partition)의 개요
- **파티션** - 대용량의 테이블이나 인덱스를 작은 논리적 단위로 분할하는 것
- 대용량 DB에서 몇 개의 테이블에 데이터가 집중되면 관리가 어려워지므로 테이블을 작은 단위로 분할해 관리
- 하나의 테이블을 파티셔닝하면 파티션 또는 인덱스가 각각 물리적으로 별도 공간에 저장될 수 있음
- 데이터 처리는 테이블 단위로 수행되고, 데이터 저장은 **파티션별로 수행**

> ⭐ `파티션 = 논리적으로 하나 / 물리적으로 여러 구역`

### 2. 파티션의 장·단점

#### 장점
- 데이터 접근 시 액세스 범위를 줄여 **쿼리 성능 향상**
- 파티션별로 데이터가 분산되어 저장되므로 **디스크 성능 향상**
- 파티션별 백업 및 복구를 수행하므로 속도가 빠름
- 시스템 장애 시 데이터 손상 정도를 최소화할 수 있음
- **데이터 가용성 향상**
- 파티션 단위로 입·출력을 분산시킬 수 있음

#### 단점
- 하나의 테이블을 세분화하여 관리하므로 세심한 관리가 요구됨
- 테이블 간 조인이 많아질 수 있음
- 용량이 작은 테이블에 파티셔닝을 수행하면 오히려 성능이 저하될 수 있음

### 3. 파티션 종류

#### 범위 분할(Range Partitioning)
- 지정한 열의 값을 기준으로 **범위를 지정하여 분할**
- 날짜·숫자처럼 연속적인 값에 적합

> ⭐ `Range = 값의 범위`

#### 해시 분할(Hash Partitioning)
- **해시 함수**를 적용한 결과 값에 따라 데이터를 분할
- 특정 파티션에 데이터가 집중되는 현상을 줄이고 데이터를 **고르게 분산**할 때 유용
- 특정 데이터가 어느 파티션에 있는지 직관적으로 판단하기 어려움
- 데이터 분포를 균등하게 하고자 할 때 효과적

> ⭐ `Hash = 해시 함수 / 균등 분산`

#### 조합 분할(Composite Partitioning)
- 두 가지 이상의 파티션 방식을 **결합하여 사용**
- 예: 범위 분할 후 각 범위 파티션을 다시 해시 분할
- 하나의 파티션이 너무 커서 관리하기 어려울 때 활용

> ⭐ `Composite = 파티션 방식 2개 이상 결합`

#### 목록 분할(List Partitioning)
- 지정한 열의 값에 대해 **목록을 미리 정해 놓고 분할**
- `국가 / 지역 / 부서`처럼 값의 종류가 정해진 경우 활용

> ⭐ `List = 지정된 값 목록`

#### 라운드 로빈 분할(Round Robin Partitioning)
- 레코드를 **균일하게 분배**하는 방식
- 각 레코드가 순차적으로 분배됨
- **기본키가 필요 없음**

### 4. 파티션 선정 시 고려사항
- 파티션 전략은 **접근 유형에 따라 파티셔닝 방법을 선택**
- 데이터 관리의 용이성을 위해 이력성 데이터는 **파티션 생성 주기와 소멸 주기**를 고려
- 파티션 키는 다음과 같은 컬럼을 중심으로 선정
  - 일 단위로 생성되는 날짜 컬럼
  - 월별 기준이 되는 날짜 컬럼
  - 파티션 간 이동이 발생하지 않는 컬럼
  - I/O 병목을 줄일 수 있도록 **데이터 분포가 양호한 컬럼**

### 5. 인덱스 파티션
- **인덱스 파티션** - 파티션된 테이블의 데이터를 관리하기 위해 인덱스를 나눈 것
- 테이블 파티션과의 관계에 따라 `Local Partitioned Index`와 `Global Partitioned Index`로 구분

#### Local Partitioned Index
- 테이블 파티션과 인덱스 파티션이 **1:1로 대응**되도록 구성
- 테이블의 파티션 키를 기준으로 인덱스 파티션 구성
- Global 방식보다 데이터 관리가 쉬움

#### Global Partitioned Index
- 테이블 파티션과 **독립적으로 인덱스 파티션**을 구성
- 인덱스 자체의 분할 기준을 사용

### 6. Prefixed / Non-Prefixed Partitioned Index
- 인덱스 파티션은 파티션 키 컬럼의 위치에 따라 구분

| 유형 | 인덱스 파티션 키 | 인덱스 키 컬럼 |
|---|---|---|
| **Prefixed Partitioned Index** | 인덱스의 파티션 키와 동일 | **첫 번째 컬럼이 파티션 키** |
| **Non-Prefixed Partitioned Index** | 인덱스 파티션 키 사용 | **첫 번째 컬럼이 파티션 키와 다름** |

- Local/Global과 Prefixed/Non-Prefixed를 조합하여 인덱스 파티션 유형을 구성할 수 있음

> ⭐ `Local = 테이블 파티션과 연동 / Global = 독립`  
> ⭐ `Prefixed = 인덱스 첫 컬럼이 파티션 키`

## SECTION 074. 분산 데이터베이스 설계

### 1. 분산 데이터베이스의 정의
- **분산 데이터베이스** - 논리적으로는 하나의 시스템에 속하지만 물리적으로는 네트워크를 통해 연결된 여러 개의 컴퓨터 사이트(Site)에 분산되어 있는 데이터베이스
- 데이터베이스가 지역적으로 분산되어 있어 해당 지역에서 필요한 데이터를 처리할 수 있도록 구성

> ⭐ `분산 DB = 논리적으로 하나 / 물리적으로 여러 Site`

### 2. 분산 데이터베이스의 구성 요소

| 구성 요소 | 핵심 |
|---|---|
| **분산 처리기** | 지리적으로 분산되어 있는 컴퓨터 시스템의 처리 장치 |
| **분산 데이터베이스** | 지리적으로 분산되어 있지만 데이터베이스로서 하나의 논리적 구조를 갖는 데이터 집합 |
| **통신 네트워크** | 분산 처리기를 통신망으로 연결하여 하나의 시스템처럼 동작할 수 있도록 하는 네트워크 |

### 3. 분산 데이터베이스 설계 시 고려사항
- **작업 부하(Work Load)의 분산 정책**
- 지역의 자치성 보장 정책
- 데이터의 일관성 정책
- 사이트나 회선의 고장으로부터의 **회복 기능**
- 통신 네트워크를 통한 원격 접근 기능

### 4. 분산 데이터베이스의 목표

| 투명성 | 핵심 |
|---|---|
| **위치 투명성(Location Transparency)** | 데이터의 실제 위치를 알 필요 없이 **논리적 명칭만으로 접근** |
| **중복 투명성(Replication Transparency)** | 동일 데이터가 여러 사이트에 복제되어 있어도 사용자는 하나의 데이터처럼 사용 |
| **병행 투명성(Concurrency Transparency)** | 여러 트랜잭션이 동시에 수행되어도 결과의 **일관성 유지** |
| **장애 투명성(Failure Transparency)** | 시스템 장애가 발생해도 트랜잭션을 정확하게 처리 |

> ⭐ 분산 DB 투명성 → `위치 / 중복 / 병행 / 장애`

### 5. 분산 데이터베이스의 장·단점

#### 장점
- 지역 자율성이 높음
- 자료 공유성 향상
- 분산 제어 가능
- 시스템 성능 향상
- 중앙 컴퓨터 장애가 전체 시스템에 미치는 영향 감소
- 효용성과 융통성 향상
- 신뢰성 및 가용성 향상
- 점진적인 시스템 용량 확장이 용이

#### 단점
- DBMS가 수행해야 할 기능이 복잡
- 데이터베이스 설계가 어려움
- 소프트웨어 개발 비용 증가
- 처리 비용 증가
- 잠재적인 오류 증가

### 6. 분산 데이터베이스 설계
- 응용 프로그램이나 사용자가 분산된 데이터를 가까운 곳에서 이용할 수 있도록 설계하는 것이 목적
- 잘못 설계하면 **복잡성 증가 / 응답 속도 저하 / 비용 증가** 등의 문제가 발생
- 논리적으로 하나인 관계형 데이터베이스를 여러 개의 작은 논리 단위로 분할한 후 여러 사이트에 배치
- 주요 설계 방법 → **테이블 위치 분산 / 분할(Fragmentation) / 할당(Allocation)**

### 7. 테이블 위치 분산
- 데이터베이스의 테이블을 각각 다른 서버에 배치하는 방식
- 테이블 구조 자체는 변경하지 않고 **물리적 위치만 분산**
- 데이터베이스의 테이블을 각기 다른 위치에 배치하려면 해당 테이블이 어느 서버에 배치될지 미리 결정

### 8. 분할(Fragment)
- 하나의 테이블을 더 작은 단위로 분할하여 분산시키는 것

#### 분할 규칙
- **완전성(Completeness)** - 전체 데이터를 대상으로 분할해야 함
- **재구성(Reconstruction)** - 분할된 데이터는 관계 연산을 이용해 원래 데이터로 재구성 가능해야 함
- **상호 중첩 배제성(Disjointness)** - 분할된 데이터가 서로 다른 분할에 중복되어 속하지 않아야 함
  - 단, 수직 분할 시 각 분할에 원래 레코드를 식별할 수 있는 정보가 필요

#### 주요 분할 방법
- **수평 분할** - 특정 속성의 값을 기준으로 **행(Row) 단위**로 분할
- **수직 분할** - 데이터 컬럼(속성) 단위로 분할

> ⭐ `수평 = Row / 수직 = Column`

### 9. 할당(Allocation)
- 분할된 릴레이션을 여러 개의 사이트에 **배치하는 과정**
- 중복 여부에 따라 `비중복 할당`과 `중복 할당`으로 구분

#### 비중복 할당
- 하나의 분할이 **한 사이트에만 존재**하도록 배치
- 데이터 중복은 없지만 장애·요구 변화에 대응하기 어려울 수 있음

#### 중복 할당
- 동일 데이터를 다른 서버에도 복제하는 방식
- **부분 복제** 또는 **전체 복제** 형태로 구성 가능

> ⭐ `Allocation = 분할된 데이터를 어느 Site에 둘 것인가`

## SECTION 075. 데이터베이스 보안 / 암호화

### 1. 데이터베이스 보안의 개요
- **데이터베이스 보안** - 데이터베이스의 일부 또는 전체에 대해 권한이 없는 사용자가 액세스하는 것을 금지하기 위해 사용하는 기술
- 데이터의 손실·변경·불법 접근 등 **의도적 또는 비의도적 위협**으로부터 데이터를 보호
- 사용자마다 객체에 대해 서로 다른 **접근 권리 또는 권한**을 부여 가능

### 2. 암호화(Encryption)
- 송신자가 지정한 수신자 이외에는 내용을 알 수 없도록 **평문을 암호문으로 변환**하는 과정
- **암호화(Encryption)** - 평문 → 암호문
- **복호화(Decryption)** - 암호문 → 평문
- 암호화 기법은 **개인키 암호 방식**과 **공개키 암호 방식**으로 구분

> ⭐ `Encryption = 평문 → 암호문 / Decryption = 암호문 → 평문`

### 3. 개인키 암호 방식(Private Key Encryption) = 비밀키 암호 방식
- **동일한 키**로 데이터를 암호화하고 복호화
- 대칭 암호 방식 또는 단일키 암호 방식이라고 함
- 암호화 키를 사용자 간에 안전하게 전달하는 것이 중요하며 사용자가 증가할수록 키 관리가 어려워질 수 있음
- 종류 → **전위 기법 / 대체 기법 / 대수 기법 / 합성 기법**
- 대표 예 → `DES / LUCIFER`

> ⭐ `개인키 = 암호화 키 = 복호화 키`

### 4. 공개키 암호 방식(Public Key Encryption)
- 서로 **다른 키**로 데이터를 암호화하고 복호화
- 데이터 암호화를 위한 **공개키(Public Key)**는 사용자에게 공개
- 복호화를 위한 **비밀키(Secret Key)**는 관리자가 비밀리에 관리
- 비대칭 암호 방식이라고 함
- 대표 예 → `RSA(Rivest Shamir Adleman)`

> ⭐ `공개키 = 키 2개 / 공개키 공개 + 비밀키 비공개`

## SECTION 076. 데이터베이스 보안 - 접근통제

### 1. 접근통제
- **접근통제** - 데이터가 저장된 객체와 이를 사용하는 주체 사이의 정보 흐름을 제한하는 것
- 자원의 불법적인 접근 및 파괴를 예방하기 위해 다음과 같은 통제를 수행
  - 비인가된 사용자의 접근 금지
  - 접근 요구자의 사용자 식별
  - 접근 요구의 정당성 확인 및 기록
  - 보안 정책에 근거한 접근의 승인 또는 거부
- 접근통제 기술 → **임의 접근통제(DAC) / 강제 접근통제(MAC) / 역할기반 접근통제(RBAC)**

### 2. 임의 접근통제(DAC: Discretionary Access Control)
- 데이터에 접근하는 **사용자의 신원**을 기반으로 권한을 부여
- 데이터 소유자가 접근 권한을 지정하고 제어
- 다른 사용자에게 권한을 위임할 수도 있어 비교적 유연
- SQL의 대표 명령 → `GRANT / REVOKE`

> ⭐ `DAC = 사용자 신원 + 소유자 판단`

### 3. 강제 접근통제(MAC: Mandatory Access Control)
- 주체와 객체의 **보안 등급**을 비교하여 접근 권한을 부여
- 시스템이 미리 정의한 보안 정책에 따라 강제적으로 통제
- 사용자 임의로 권한을 변경하기 어려움
- 보안 등급이 명확한 군사·정부 등의 환경에서 활용

> ⭐ `MAC = 보안 등급 비교 / 시스템이 강제`

### 4. 역할기반 접근통제(RBAC: Role Based Access Control)
- 사용자의 신원이 아니라 **역할(Role)**에 따라 권한을 부여
- 권한을 역할에 연결하고 사용자를 해당 역할에 배정
- 조직 내 직무가 명확한 환경에서 관리가 용이
- 사용자 변경 시 역할만 조정하여 권한 관리 가능

> ⭐ `RBAC = 사용자 → 역할 → 권한`

### 5. 접근통제 보안 모델

#### 벨-라파듈라 모델(Bell-LaPadula Model)
- 군대의 보안 레벨처럼 **기밀성(Confidentiality)** 보장을 목적으로 하는 모델
- 강제 접근통제 환경에서 사용
- 대표 규칙
  - **단순 보안 규칙** - 낮은 등급 주체가 높은 등급 객체를 읽을 수 없음
  - **★-보안 규칙** - 높은 등급 주체가 낮은 등급 객체에 정보를 쓸 수 없음
  - **강한 ★ 규칙** - 동일 등급의 객체에 대해서만 읽고 쓸 수 있음

> ⭐ Bell-LaPadula → `기밀성 / No Read Up / No Write Down`

#### 비바 무결성 모델(Biba Integrity Model)
- Bell-LaPadula 모델을 보완한 **수학적 모델**로, **무결성을 보장하는 최초의 모델**
- 비인가자에 의한 **데이터 변형을 방지**
- 무결성 모델의 대표 제약 조건
  - **단순 무결성 규칙** - 주체는 자신보다 **낮은 등급의 객체를 읽을 수 없음**
  - **★-무결성 규칙** - 주체는 자신보다 **높은 등급의 객체에 정보를 쓸 수 없음**

> ⭐ Biba → `무결성 / No Read Down / No Write Up`

#### 클락-윌슨 무결성 모델(Clark-Wilson Integrity Model)
- **무결성 중심의 상업용 모델**
- 사용자가 직접 객체에 접근할 수 없고 **프로그램을 통해서만 접근 가능**

#### 만리장성 모델(Chinese Wall Model)
- 서로 **이해 충돌 관계**에 있는 객체 간의 정보 접근을 통제하는 모델

### 6. 접근통제의 구성 요소
- 접근통제는 다음 요소로 구성
  - **접근통제 정책**
  - **접근통제 메커니즘**
  - **접근통제 보안 모델**

### 7. 접근통제 정책
- 어떤 주체가(Who), 언제(When), 어디서(Where), 어떤 객체를(What), 어떤 행위로(How) 접근할 수 있는지 정의

#### 신분 기반 정책
- 주체나 그룹의 **신분(Identity)**에 근거하여 객체 접근을 제한
- `IBP(Individual-Based Policy)` - 최소 권한 정책으로 **단일 주체에게 하나의 객체에 대한 허가**를 부여
- `GBP(Group-Based Policy)` - **복수 주체에게 하나의 객체에 대한 허가**를 부여

#### 규칙 기반 정책
- 주체가 갖는 권한에 근거하여 객체 접근을 제한
- `MLP(Multi-Level Policy)` - 사용자 및 객체 간의 **수직적 관계**에 따른 정책
- `CBP(Compartment-Based Policy)` - **수평적 관계**에 따른 정책

#### 역할 기반 정책
- GBP의 변형된 정책으로 주체의 신분이 아니라 **주체가 맡은 역할(Role)**을 근거로 객체 접근을 제한
- 예 → 인사 담당자, DBA 등

### 8. 접근통제 메커니즘
- 접근통제 정책을 구현하기 위한 기술적인 방법

| 메커니즘 | 핵심 |
|---|---|
| **접근통제 목록(Access Control List)** | 객체를 기준으로 어떤 주체가 어떤 행위를 할 수 있는지 기록 |
| **능력 리스트(Capability List)** | 주체를 기준으로 자신이 접근 가능한 객체와 권한을 기록 |
| **보안 등급(Security Level)** | 주체와 객체의 등급을 비교하여 접근 허용 여부 결정 |
| **패스워드** | 주체가 자신의 신원을 증명하는 인증 방법 |
| **암호화** | 평문을 암호문으로 변환하여 인가된 사용자만 정보 확인 가능하도록 보호 |

### 9. 접근통제 행렬(Access Control Matrix)
- 임의적 접근통제를 관리하기 위한 보안 모델
- **행 = 주체 / 열 = 객체 / 셀 = 접근 권한**
- 주체 → 객체에 접근을 시도하는 사용자
- 객체 → 데이터베이스의 개체·릴레이션·테이블·뷰 등
- 권리 → 입력·수정·삭제·읽기 등 데이터베이스에서 수행 가능한 연산

> ⭐ `Access Control Matrix = Subject × Object × Right`

### 10. 접근통제 조건
- 접근통제 효과를 높이기 위해 접근 조건을 추가로 적용할 수 있음

#### 값 종속 통제(Value-Dependent Control)
- 동일한 객체라도 **저장된 값에 따라 다른 접근통제** 적용

#### 다중 사용자 통제(Multi-User Control)
- 지정된 객체에 다수의 사용자가 동시에 접근을 요구하는 경우 사용

#### 컨텍스트 기반 통제(Context-Based Control)
- 시간·네트워크 접속 경로·접속 위치 등 **접근 상황(Context)**을 기반으로 권한 부여

### 11. 감사 추적
- 사용자나 애플리케이션이 데이터베이스에 접근하여 수행한 **모든 활동을 기록**하는 기능
- 오류가 발생한 데이터베이스를 복구하거나 부적절한 데이터 조작을 파악하기 위해 사용
- 기록 정보 예 → 로그인 ID, 사용자, 날짜·시간, 접근한 데이터, 접근 결과 등

> ⭐ `감사 추적 = 누가 / 언제 / 무엇에 / 어떤 작업을 했는지 기록`

## SECTION 077. 데이터베이스 백업

### 1. 데이터베이스 백업
- **데이터베이스 백업** - 전산 장비의 장애에 대비하여 데이터베이스에 저장된 데이터를 보호하고 복구하기 위해 작업 내용을 **별도의 저장 매체에 복사**하는 작업
- 데이터베이스 관리 시스템(DBMS)은 데이터베이스 장애 및 정상 종료 여부와 관계없이 데이터를 복구할 수 있는 기능을 제공

### 2. 데이터베이스 장애 유형

| 장애 | 핵심 |
|---|---|
| **사용자 실수** | 사용자가 실수로 객체·데이터를 삭제하거나 잘못된 트랜잭션을 실행 |
| **미디어 장애** | CPU·메모리·디스크 등 하드웨어 장애로 데이터 손상 |
| **구조 장애** | 프로그램 오류나 사용 공간 부족 등으로 발생 |
| **사용자 프로세스 장애** | 프로그램의 비정상 종료 또는 세션 이상 종료 |
| **인스턴스 장애** | 하드웨어 장애·정전·시스템 과열 등으로 DB 서버 프로세스가 중단 |

### 3. 로그 파일
- **로그 파일** - 데이터베이스의 처리 내용이나 이용 상황 등 상태 변화를 시간의 흐름에 따라 기록한 파일
- 데이터베이스 복구를 위한 가장 기본적인 자료
- 로그를 기반으로 이전 상태로 되돌리는 `UNDO` 또는 변경 내용을 다시 적용하는 `REDO` 수행 가능
- 트랜잭션 시작 시점, Rollback 시점, 데이터 삽입·수정·삭제 시점 등에 기록
- 로그 기록 내용 → 트랜잭션 시작·완료 내용, 트랜잭션 레코드, 데이터의 이전 값과 이후 값인 **Before Image / After Image** 등

> ⭐ `로그 = 복구의 핵심 / Before Image + After Image`

### 4. 데이터베이스 복구 알고리즘
- 복구 알고리즘은 갱신 결과의 반영 시점에 따라 `NO-UNDO/REDO`, `UNDO/NO-REDO`, `UNDO/REDO`, `NO-UNDO/NO-REDO` 등으로 구분

| 방식 | 핵심 |
|---|---|
| **NO-UNDO / REDO** | DB 버퍼 내용을 **비동기적으로 갱신**하는 경우 / 완료 전에는 변경 내용이 DB에 기록되지 않아 UNDO가 필요 없고, 완료 후 저장 매체에 미기록된 내용은 REDO |
| **UNDO / NO-REDO** | DB 버퍼 내용을 **동기적으로 갱신**하는 경우 / 완료 전 장애 시 변경 내용을 UNDO하고, 완료된 변경은 이미 DB에 기록되어 있으므로 REDO 불필요 |
| **UNDO / REDO** | DB 버퍼 내용을 동기/비동기적으로 갱신하는 경우 / 완료되지 않은 내용은 UNDO, 완료되었지만 DB에 기록되지 않은 내용은 REDO |
| **NO-UNDO / NO-REDO** | DB 버퍼 내용을 동기적으로 저장 매체에 기록하지만 **데이터베이스와 다른 영역에 기록**하는 방식 / 변경 내용이 별도 영역에 존재하므로 UNDO·REDO 불필요 |

> ⭐ `UNDO = 이전 상태로 / REDO = 완료된 변경을 다시 적용`

### 5. 백업 종류
- 복구 수준에 따라 운영체제를 이용하는 **물리 백업**과 DBMS 유틸리티를 이용하는 **논리 백업**으로 구분

#### 물리 백업
- 데이터베이스 **파일 자체를 백업**하는 방식
- 백업 속도가 빠르고 작업이 단순하지만 문제 발생 시 **원인 파악 및 문제 해결이 어려움**
- 로그 파일 백업 실시 → **완전 복구** 가능
- 로그 파일 백업 없음 → **백업 시점까지 복구**

#### 논리 백업
- DB 내의 **논리적 객체**를 백업하는 방식
- 복원 시 데이터 손상을 막고 문제 발생 시 원인 파악 및 해결이 수월하지만 **백업/복원 시간이 많이 소요**
- DBMS 유틸리티를 이용하며 **백업 시점까지 복구**

> ⭐ `물리 백업 = 파일/장치 / 논리 백업 = DB 객체`

## SECTION 078. 스토리지

### 1. 스토리지(Storage)의 개요
- **스토리지** - 단일 디스크로 처리할 수 없는 대용량의 데이터를 저장하기 위해 서버와 저장장치를 연결하는 기술
- 대표적인 저장 방식 → `DAS / NAS / SAN`

> ⭐ `DAS = 직접 연결 / NAS = 네트워크 파일 저장 / SAN = 전용 스토리지 네트워크`

### 2. DAS(Direct Attached Storage)
- 서버와 저장장치를 **전용 케이블로 직접 연결**하는 방식
- 일반 가정에서 컴퓨터와 외장 하드디스크를 연결하는 것과 유사
- 서버가 저장장치를 직접 관리

#### 특징
- 저장장치를 직접 연결하므로 속도가 빠르고 설치·운영이 쉬움
- 초기 구축 비용과 유지보수 비용이 비교적 낮음
- 직접 연결 방식이므로 다른 서버에서 접근할 수 없고 파일 공유가 어려움
- 확장성 및 유연성이 상대적으로 떨어짐
- 저장 데이터가 많지 않고 공유가 필요 없는 환경에 적합
- 사용 프로토콜 → `SATA / eSATA / SCSI / SAS`

> ⭐ `DAS = Server ↔ Storage 직접 연결`

### 3. NAS(Network Attached Storage)
- 서버와 저장장치를 **네트워크를 통해 연결**하는 방식
- 별도의 파일 관리 기능을 가진 NAS Storage가 내장된 저장장치를 직접 관리
- Ethernet 스위치를 통해 여러 서버가 스토리지에 접근 가능
- 저장장치 공유가 가능하고 스토리지를 추가하여 저장 공간 확장 가능
- 데이터 공유 및 관리가 용이
- 접속이 증가하면 성능이 저하될 수 있음
- 사용 프로토콜 → `NFS / SMB(CIFS)`

> ⭐ `NAS = LAN 기반 / 파일 공유에 유리`

### 4. SAN(Storage Area Network)
- DAS의 빠른 처리와 NAS의 파일 공유 장점을 결합한 방식
- 서버와 저장장치를 연결하는 **전용 네트워크**를 별도로 구성
- 광 채널(FC) 스위치를 이용하여 네트워크 구성 가능

#### 특징
- 서버와 저장장치를 광케이블 등으로 연결하여 처리 속도가 빠름
- 여러 서버가 저장장치를 공유하여 사용할 수 있음
- 확장성·유연성·가용성이 뛰어남
- 저장 공간을 대규모로 확장하기 용이
- 기존 시스템의 장비 업그레이드 및 별도 네트워크 구성이 필요해 초기 비용이 높을 수 있음
- 사용 프로토콜 → `iSCSI / FC / FCoE`

> ⭐ `SAN = 전용 Storage Network / 빠름·확장성 좋음 / 비용 높음`
