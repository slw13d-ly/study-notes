## SECTION 001. 소프트웨어 생명 주기

### 1. 소프트웨어 생명주기

> **소프트웨어를 개발하기 위한 설계·운용·유지보수 등의 전체 과정을 단계별로 나눈 것**

| 문제 키워드 | 정답 |
|---|---|
| 가장 오래됨 / 전통적 / 순차적 / 되돌아가기 어려움 | **폭포수** |
| 견본을 먼저 만듦 / 요구사항 불명확 | **프로토타입** |
| Boehm / 위험 분석 / 반복 | **나선형** |
| 변화 대응 / 고객 협력 / 짧은 반복 | **애자일** |

**암기:** `폭순 / 프견 / 나위 / 애변`

#### 나선형 순서
**계획 → 위험 분석 → 개발·검증 → 고객 평가**

- 나선형에서 **위험(Risk)** 이 보이면 거의 정답

## SECTION 002. 스크럼(Scrum) 기법

### 2. Scrum

> **팀 중심의 애자일 개발 방법**으로, 팀이 스스로 구성되고 개발 작업을 협업하여 해결한다.

#### Scrum 구성원

##### Product Owner
- 요구사항
- Product Backlog
- 우선순위 결정
- 최종 의사결정

→ **요구사항·우선순위 = PO**

##### Scrum Master
- 가이드
- 조력자
- 장애 제거
- 일일 스크럼 주관

→ **관리자가 아니라 조력자**

##### Development Team
- 실제 개발 참여자
- 디자이너·테스터 등 포함

#### Scrum 순서

**제품 백로그 → 스프린트 계획 → 스프린트 → 일일 스크럼 → 검토 → 회고**

**암기:** `백계스일검회`

#### 키워드

| 키워드 | 정답 |
|---|---|
| 모든 요구사항 + 우선순위 | Product Backlog |
| 이번 Sprint에서 할 일 | Sprint Backlog |
| 2~4주 | Sprint |
| 매일 약 15분 | Daily Scrum |
| 남은 작업량 | Burn-down Chart |
| 결과물 시연 | Sprint Review |
| 개선점 확인 | Sprint Retrospective |

## SECTION 003. XP(eXtreme Programming) 기법

### 3. XP

> **짧고 반복적인 개발 주기 + 단순한 설계 + 고객 참여 + 테스트 강조**로 변화하는 요구사항에 빠르게 대응하는 애자일 기법

#### XP 5대 가치

**의사소통 / 단순성 / 용기 / 존중 / 피드백**

**암기:** `의·단·용·존·피`

#### XP 프로세스

**사용자 스토리 → 릴리즈 계획 → 스파이크 → 이터레이션 → 승인 검사 → 소규모 릴리즈**

#### XP 실천법

| 지문 키워드 | 정답 |
|---|---|
| 2명이 같이 코딩 | **Pair Programming** |
| 모든 팀원이 소스 공동 소유 | **Collective Ownership** |
| 테스트 케이스 먼저 | **TDD** |
| 고객을 팀에 포함 | **Whole Team** |
| 지속적으로 코드 통합 | **Continuous Integration** |
| 기능 변경 없이 내부 구조 개선 | **Refactoring** |
| 짧은 릴리즈 반복 | **Small Releases** |

- **TDD = 테스트 먼저**
- **Refactoring = 기능은 그대로, 구조만 개선**

## SECTION 004. 현행 시스템 파악

### 4. 현행 시스템 파악

순서:

**구성 → 기능 → 인터페이스 → 아키텍처·SW → HW·Network**

#### 바로 연결

- 구성 → **기간 업무와 지원 업무를 구분하고, 단위 업무 시스템의 명칭·주요 기능 파악**
- 기능 → **주요 → 하부 → 세부 기능 계층화**
- 인터페이스 → **데이터 종류·형식·프로토콜·주기**
- 아키텍처 → **기술 요소 계층 구조**
- SW → **제품명·용도·라이선스**
- HW → **서버 사양·수량·이중화**
- Network → **서버 위치·연결 방식**

## SECTION 005. 개발 기술 환경 파악

### 5. 개발 기술 환경

> 개발하려는 소프트웨어와 관련된 **OS·DBMS·미들웨어 등의 요구사항을 식별하고 적용 가능성을 판단**하는 단계

- **OS** → 컴퓨터 자원을 효율적으로 관리하고 사용 환경을 제공하는 시스템 소프트웨어
- **DBMS** → 사용자와 데이터베이스 사이에서 정보를 생성하고 DB를 관리하는 소프트웨어

#### OS 고려사항

**가용성 / 성능 / 기술 지원 / 주변 기기 / 구축 비용**

**암기:** `가·성·기·주·비`

#### DBMS 고려사항

**가용성 / 성능 / 기술 지원 / 상호 호환성 / 구축 비용**

**암기:** `가·성·기·호·비`

차이:
- OS → **주변기기**
- DBMS → **호환성**

#### WAS

**동적 콘텐츠 + 데이터 접근 + 세션 + 트랜잭션**

예:
- Tomcat
- WebLogic
- WebSphere
- JEUS
- Jetty

#### Open Source

무료만 보는 것이 아님.

확인:
- 라이선스
- 사용자 수
- 기술 지속 가능성
- 안정성
- 커뮤니티
- 업데이트

## SECTION 006. 요구사항 정의

### 6. 요구사항

#### 기능 요구사항

> **시스템이 무엇을 해야 하는가(What)**

- 로그인
- 검색
- 주문
- 입력
- 출력
- 처리

#### 비기능 요구사항

> **얼마나 잘 / 어떤 조건으로**

- 성능
- 보안
- 품질
- 제약
- 인터페이스

**시험 포인트:** 성능·보안 = **비기능 요구사항**

#### 사용자 요구사항 vs 시스템 요구사항

- **사용자 요구사항** → 사용자 관점, 쉬운 표현
- **시스템 요구사항** → 개발자 관점, 전문적·기술적 표현


### 7. 요구사항 개발 프로세스

**도출 → 분석 → 명세 → 확인**

**암기:** `도분명확`

#### 도출
인터뷰, 설문, 브레인스토밍, 워크숍, 프로토타이핑 등으로 **수집**

#### 분석
모순·불완전·불명확 요구사항 제거

#### 명세
**요구사항 명세서 작성**

#### 확인
정확성·완전성·일관성 검토


### 8. 요구사항 명세 기법

#### 정형 명세

**수학적 원리**

- 정확
- 간결
- 명확
- 작성·이해 어려움

종류:
- VDM
- Z
- Petri-net
- CSP

#### 비정형 명세

**자연어·그림**

- 작성·이해 쉬움
- 모호성 발생 가능

종류:
- FSM
- Decision Table
- ER 모델링
- State Chart

**암기:** 정형 = **수학 / 정확하지만 어려움**


### 9. SRS

**Software Requirement Specification**

→ 요구사항을 공식적으로 기록한 문서

좋은 SRS:
- 정확성
- 명확성
- 완전성
- 일관성
- 수정 용이성
- 추적 가능성

## SECTION 007. 요구사항 분석

### 10. 구조적 분석

> **자료의 흐름과 처리를 중심으로 요구사항을 분석하고, 하향식으로 시스템을 세분화하는 기법**

키워드:

**DFD + DD + Mini-Spec + ERD + STD**


### 11. DFD

**자료 흐름도 / 버블 차트**

> 시스템에서 데이터가 **어디서 발생하고 어떤 처리를 거쳐 어디로 이동하는지** 표현

#### 4대 구성요소

| 의미 | 답 |
|---|---|
| 자료 처리 | Process |
| 자료 이동 | Data Flow |
| 자료 저장 | Data Store |
| 외부 발생·도착 | Terminator |

**암기:** `P / F / S / T`


### 12. 자료 사전 DD 기호

> **DFD에 표현된 자료의 의미·구성 등을 더 자세하게 정의하고 기록하는 도구**

| 기호 | 의미 |
|---|---|
| `=` | 정의 |
| `+` | 연결 AND |
| `( )` | 생략 가능 |
| `[ ]` | 선택 OR |
| `{ }` | 반복 |
| `* *` | 설명 |

## SECTION 008. 요구사항 분석 CASE와 HIPO

### 13. CASE

**소프트웨어 개발 과정 자동화**

요구사항 분석·설계·구현·검사 등을 컴퓨터로 지원.

#### CASE 이름 문제

##### SADT
- SoftTech
- 블록 다이어그램

##### SREM
- TRW
- **RSL + REVS**
  - **RSL** → 요구사항 명세 언어
  - **REVS** → 요구사항 분석기

##### PSL/PSA
- 미시간 대학
- 문제 명세 언어 + 문제 분석기

##### TAGS
- 개발 주기 전 과정
- 통합 자동화

**암기:** `SREM = RSL + REVS`


### 14. HIPO

**Hierarchy Input Process Output**

> 시스템 기능을 고유 모듈로 나누고 **기능·자료의 의존 관계와 인터페이스를 계층 구조로 표현하는 하향식 문서화 도구**

키워드:
- 계층적
- 하향식
- Input / Process / Output

종류:
- **가시적 도표** → 시스템 전체 기능과 흐름을 **계층 구조**로 표현
- **총체적 도표** → 기능별 **입력·처리·출력의 전반적 정보** 표현
- **세부적 도표** → 총체적 도표의 기능을 구성하는 **기본 요소를 상세히 기술**

## SECTION 009. UML(Unified Modeling Language)

### 15. UML

UML = 객체지향 **표준 모델링 언어**

- OMG 표준

3요소:

**사물 + 관계 + 다이어그램**

#### 사물

| 사물 | 개념 |
|---|---|
| **구조 사물** | 시스템의 개념적·물리적 요소(Class, Use Case, Component 등) |
| **행동 사물** | 시간과 공간에 따른 시스템의 행위 |
| **그룹 사물** | 요소들을 그룹으로 묶는 사물(Package) |
| **주해 사물** | 부가 설명·제약조건을 표현하는 사물(Note) |


### 16. UML 관계

#### Association 연관
→ 그냥 서로 관련

- **실선**

#### Aggregation 집합
→ 전체-부분인데 **부분이 독립적으로 존재 가능**

- **빈 마름모**

#### Composition 포함
→ 강한 전체-부분

- **전체가 사라지면 부분도 사라짐**
- **채운 마름모**

**핵심**
- Aggregation = 독립 가능
- Composition = 생명주기 종속

#### Generalization 일반화
→ **상속**

- 빈 삼각형 화살표

#### Dependency 의존
→ 일시적으로 사용

- 점선 화살표

#### Realization 실체화
→ **Interface 구현**

- 점선 + 빈 화살표


### 17. UML 다이어그램

#### 구조적 = 정적 구조

- Class
- Object
- Component
- Deployment
- Composite Structure
- Package

#### 행위 = 동적 행동

- Use Case
- Sequence
- Communication
- State
- Activity
- Interaction Overview
- Timing

## SECTION 013. 품질 요구사항

### 22. 소프트웨어 품질

> 소프트웨어의 기능·성능·만족도 등 **요구사항을 얼마나 충족하는지를 나타내는 특성**

#### ISO/IEC 9126

### 23. 품질 속성 세부 문제

#### 기능성

> 소프트웨어가 사용자의 요구사항을 **정확하게 만족하는 기능을 제공하는 정도**

| 세부 속성 | 개념 |
|---|---|
| **적합성** | 지정된 작업과 사용자 목적에 적절한 기능 제공 |
| **정확성** | 사용자가 요구하는 결과를 정확하게 산출 |
| **상호운용성** | 다른 시스템과 상호 교환할 수 있는 능력 |
| **보안성** | 정보 접근을 권한에 따라 허용·차단 |
| **준수성** | 기능 관련 표준·규정을 준수 |

#### 신뢰성

> 소프트웨어가 요구된 기능을 **정확하고 안정적으로 수행할 수 있는 정도**

| 세부 속성 | 개념 |
|---|---|
| **성숙성(Maturity)** | 결함으로 인한 고장을 피할 수 있는 능력 |
| **고장 허용성(Fault Tolerance)** | 결함·인터페이스 오류에도 지정된 성능 수준 유지 |
| **회복성(Recoverability)** | 고장 발생 후 성능 수준과 데이터를 복구 |

키워드:
- 결함 있어도 성능 유지 → **고장 허용성**
- 고장 후 데이터 복구 → **회복성**

#### 사용성

> 사용자가 소프트웨어를 **이해·학습·운용하고 선호할 수 있는 정도**

| 세부 속성 | 개념 |
|---|---|
| **이해성** | 사용 방법을 이해할 수 있는 정도 |
| **학습성** | 사용 방법을 학습하기 쉬운 정도 |
| **운용성** | 사용자가 소프트웨어를 운용·제어하기 쉬운 정도 |
| **친밀성** | 사용자가 소프트웨어를 선호할 수 있도록 하는 능력 |

#### 효율성

> 한정된 시간과 자원으로 요구 기능을 **얼마나 빠르고 효율적으로 처리하는지**

- **시간 효율성** → 적절한 반응 시간과 처리율 제공
- **자원 효율성** → 적절한 자원의 양과 종류 사용

**암기:** `시간 + 자원`

#### 유지보수성

> 환경 변화나 새로운 요구사항 발생 시 소프트웨어를 **개선·확장할 수 있는 정도**

- **분석성** → 결함·고장 원인이나 수정할 부분 식별
- **변경성** → 결함 제거 또는 변경을 쉽게 수행
- **안정성** → 변경으로 인한 예상치 못한 결과 최소화
- **시험성** → 변경된 소프트웨어를 검증하기 쉬움

문제:
- 고장 원인 파악 → **분석성**
- 수정하기 쉬움 → **변경성**
- 수정 후 예상 못한 영향 최소 → **안정성**
- 변경 후 검증 쉬움 → **시험성**

#### 이식성

> 소프트웨어가 **다른 환경에서도 얼마나 쉽게 적용될 수 있는지**

| 세부 속성 | 개념 |
|---|---|
| **적용성** | 원래 목적과 다른 환경에서도 적용 가능 |
| **설치성** | 지정된 환경에 쉽게 설치 |
| **대체성** | 동일 환경에서 다른 소프트웨어를 대신할 수 있음 |
| **공존성** | 동일 환경에서 다른 소프트웨어와 자원을 공유하며 공존 |

## SECTION 020. 모듈

### 36. 결합도

좋은 모듈:

> **결합도 ↓ / 응집도 ↑**

결합도 약 → 강:

**자료 → 스탬프 → 제어 → 외부 → 공통 → 내용**

**암기:** `자·스·제·외·공·내`

| 결합도 | 개념 |
|---|---|
| **자료** | 필요한 자료 요소만 매개변수로 전달 |
| **스탬프** | 배열·레코드 등 자료 구조 전체를 전달 |
| **제어** | 다른 모듈의 논리 흐름을 제어하는 요소 전달 |
| **외부** | 외부 선언 데이터나 통신 프로토콜 등을 공유 |
| **공통** | 여러 모듈이 공통 데이터 영역을 사용 |
| **내용** | 다른 모듈의 내부 기능·자료를 직접 참조·수정 |

#### 가장 좋은 결합도
**자료 결합도**

필요한 자료만 매개변수로 전달

#### 가장 나쁜 결합도
**내용 결합도**

다른 모듈 내부를 직접 참조·수정


### 37. 응집도

약 → 강:

**우연 → 논리 → 시간 → 절차 → 통신 → 순차 → 기능**

**암기:** `우·논·시·절·통·순·기`

| 응집도 | 개념 |
|---|---|
| **우연적** | 서로 관련 없는 요소들이 한 모듈에 모임 |
| **논리적** | 유사한 성격의 기능들을 한 모듈로 구성 |
| **시간적** | 특정 시간에 함께 처리되는 기능들을 모음 |
| **절차적** | 정해진 순서에 따라 수행되는 기능들이 모임 |
| **통신적** | 동일한 입력·출력을 사용하는 기능들이 모임 |
| **순차적** | 한 기능의 출력이 다음 기능의 입력이 됨 |
| **기능적** | 모든 기능이 하나의 목적을 수행 |

#### 가장 좋음

**기능적 응집도**

모든 요소가 하나의 목적 수행


### 38. 결합도/응집도 낚시 정리

- 배열·레코드 전체 전달 → **스탬프 결합도**
- 제어 플래그 전달 → **제어 결합도**
- 전역 데이터 공동 사용 → **공통 결합도**
- 같은 시간에 실행되는 작업 → **시간적 응집도**
- 같은 입력/출력 사용 → **통신적 응집도**
- 앞 작업 출력 → 다음 작업 입력 → **순차적 응집도**


### 39. Fan-In / Fan-Out

#### Fan-In
> **나를 호출하는 모듈 수**

#### Fan-Out
> **내가 호출하는 모듈 수**

#### 키워드 문제

### 45. 구조 패턴 7개

- Adapter
- Bridge
- Composite
- Decorator
- Facade
- Flyweight
- Proxy

#### 키워드

- 호환 안 되는 인터페이스 변환 → **Adapter**

- 트리 / 부분-전체 → **Composite**
- 동적으로 기능 추가 → **Decorator**
- 복잡한 시스템에 단순 인터페이스 → **Facade**
- 공통 데이터 공유 / 메모리 절약 → **Flyweight**
- 대리 객체 → **Proxy**


### 46. 행위 패턴

#### Chain of Responsibility
요청을 **Chain 따라 전달**

#### Command
요청 자체를 **객체로 캡슐화**

#### Interpreter
언어 문법·해석

#### Iterator
내부 구조 노출 X, 요소 순차 접근

#### Mediator
중재자

#### Memento
**상태 저장 → 이전 상태 복구**

#### Observer
상태 변경 → 의존 객체에 **자동 통지**

#### State
객체 **상태에 따라 행동 변경**

#### Strategy
알고리즘을 캡슐화하여 **교환**

#### Template Method
상위에서 알고리즘 골격, 일부를 하위에서 구현

#### Visitor
객체 구조 변경 없이 **새 연산 추가**

## SECTION 024. 시스템 인터페이스 요구사항 분석

### 47. 인터페이스 요구사항

인터페이스 =

> **독립 시스템 간 연동 규칙**

주요 내용:
- 인터페이스 이름
- 연계 시스템
- 연계 범위
- 연계 방식
- 송·수신 데이터
- 주기


### 48. 인터페이스 요구사항 분석 순서

**선별 → 자료 준비 → 분류 → 분석·구체화 → 공유**

- **선별** → 전체 요구사항에서 인터페이스 관련 요구만 추출
- **자료 준비** → 요구사항 정의서·현행 시스템 자료·인터페이스 목록 준비
- **분류** → 기능적 / 비기능적 요구사항으로 구분
- **분석·구체화** → 의미·타당성·구현 가능성을 분석하고 필요 시 구체화
- **공유** → 분석된 요구사항을 관계자에게 전달

### 50. 요구사항 검토 방법

#### Walk Through
> **미리 배포 → 사전 검토 → 짧은 회의**

#### Inspection
> **작성자를 제외한 전문가가 검토**

**암기:** `피어=작성자 설명 / 워크=미리 읽음 / 인스=작성자 제외`


### 51. 요구사항 검증 항목

| 항목 | 개념 |
|---|---|
| **완전성** | 사용자의 모든 요구사항이 빠짐없이 반영되었는가 |
| **일관성** | 요구사항끼리 모순·충돌하지 않는가 |
| **명확성** | 모든 참여자가 같은 의미로 이해할 수 있는가 |
| **기능성** | `How`보다 필요한 `What`에 중점을 두는가 |
| **검증 가능성** | 개발 완료 후 요구 만족 여부를 확인할 수 있는가 |
| **추적 가능성** | 요구사항 명세와 설계의 관계를 추적할 수 있는가 |
| **변경 용이성** | 요구사항 명세를 쉽게 변경할 수 있도록 작성되었는가 |

#### 기능성 검증

문제에서:

> **How보다 What에 중점**

→ 기능성

## SECTION 027. 미들웨어 솔루션 명세

### 56. 미들웨어

> **서로 다른 시스템·SW 사이를 연결**

종류:

**DB / RPC / MOM / TP-Monitor / ORB / WAS**

#### DB Middleware
> **Client ↔ DB**

보통 **2-Tier**

예:
- ODBC
- IDAPI
- Oracle Glue

#### RPC
> **원격 Procedure를 Local Procedure처럼 호출**

#### MOM
> **Message 기반 + 비동기**

#### TP-Monitor
> **Transaction 처리 + 감시**

항공·철도 예약 등의 온라인 트랜잭션

#### ORB
> **객체 지향 / CORBA**

분산 객체 간 메시지

#### WAS
> **동적 Web Content + Business Logic**

예:
- WebLogic
- WebSphere
