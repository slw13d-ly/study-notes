# 01. 요구사항 확인

## SECTION 001. 소프트웨어 생명 주기

### 1. 소프트웨어 생명 주기(Software Life Cycle)
- **소프트웨어 생명 주기** - 소프트웨어를 개발하기 위한 **설계·운용·유지보수 등의 과정을 각 단계로 나눈 것**
- 소프트웨어 개발 단계와 각 단계별 주요 활동 및 산출물을 체계적으로 정의
- 소프트웨어 생명 주기를 표현하는 형태 → **소프트웨어 생명 주기 모형**
- 대표적인 생명 주기 모형
  - **폭포수 모형(Waterfall Model)**
  - **프로토타입 모형(Prototype Model)**
  - **나선형 모형(Spiral Model)**
  - **애자일 모형(Agile Model)**

> ⭐ `소프트웨어 생명 주기 = 개발 → 운용 → 유지보수까지의 전체 과정`

### 2. 폭포수 모형(Waterfall Model)
- **가장 오래되고 가장 폭넓게 사용된 전통적인 생명 주기 모형**
- 한 단계가 끝난 후 다음 단계로 넘어가는 **선형 순차적 모델**
- 이전 단계로 되돌아가기 어려움
- 각 단계가 끝난 후 **결과물이 명확하게 산출**
- 매뉴얼 작성 필요
- 두 개 이상의 과정이 병행되어 수행되지 않음

#### 개발 과정
  ```text
  타당성 검토
  → 계획
  → 요구 분석
  → 설계
  → 구현(코딩)
  → 시험(검사)
  → 유지보수
  ```

> ⭐ `폭포수 = 단계별 순차 진행 / 되돌아가기 어려움`

### 3. 프로토타입 모형(Prototype Model, 원형 모형)
- 사용자의 요구사항을 정확하게 파악하기 위해 **실제 개발될 소프트웨어의 견본(Prototype)을 만들어 최종 결과물을 예측**
- 개발 중간에 요구사항을 반영하기 쉬움
- 사용자와 개발자 사이의 **의사소통 도구**로 활용
- 요구사항이 불명확할 때 유용
- 프로토타입은 실제 소프트웨어 구현 시 참고 대상이 되거나 일부가 재사용되기도 함
- 단점
  - 프로토타입에만 집중해 전체 품질을 놓칠 수 있음
  - 사용자가 프로토타입을 최종 제품으로 오해할 수 있음

> ⭐ `Prototype = 견본을 먼저 만들어 요구사항 확인`

### 4. 나선형 모형(Spiral Model, 점진적 모형)
- **Boehm**이 제안
- 폭포수 + 프로토타입의 장점에 **위험 분석 기능**을 추가한 모형
- 여러 번의 개발 과정을 반복하여 점진적으로 완성
- 개발 과정에서 발생할 수 있는 **위험을 관리하고 최소화**하는 것이 핵심

#### 반복 과정
```text
계획 수립
→ 위험 분석
→ 개발 및 검증
→ 고객 평가
→ 다시 반복
```

> ⭐ `나선형 = 계획 → 위험 분석 → 개발·검증 → 고객 평가`  
> ⭐ 핵심 = **위험 관리**

### 5. 애자일 모형(Agile Model)
- 고객의 요구사항 변화에 **유연하게 대응**할 수 있도록 일정한 주기를 반복하면서 개발
- 좋은 것을 빠르게 개발하여 지속적으로 고객과 소통
- 고객과의 소통, 협업, 변화 대응을 중요하게 생각
- 문서보다 **실행되는 소프트웨어**
- 계약 협상보다 **고객과의 협력**
- 계획 준수보다 **변화에 대응**
- 대표적인 애자일 방법론
  - Scrum
  - XP(eXtreme Programming)
  - Kanban
  - Lean
  - 기능 중심 개발(FDD)
  - Crystal
  - ASD
  - DSDM 등

> ⭐ `Agile = 변화 대응 + 고객 협력 + 반복 개발`

### 6. 폭포수 / 프로토타입 / 나선형 / 애자일 비교

| 모형 | 핵심 |
|---|---|
| **폭포수** | 순차적 / 단계 종료 후 다음 단계 / 전통적 |
| **프로토타입** | 견본 제작 → 사용자 요구 확인 |
| **나선형** | 반복 개발 + **위험 분석** |
| **애자일** | 짧은 주기 반복 + 변화·고객 대응 |

> ⭐ `폭순 / 프견 / 나위 / 애변`

## SECTION 002. 스크럼(Scrum) 기법

### 1. 스크럼의 개요
- **Scrum** - 팀 중심의 애자일 소프트웨어 개발 방법
- 팀원 스스로가 팀을 구성(**Self-Organizing**)
- 개발 작업에 관한 모든 것을 스스로 해결(**Cross-Functional**)
- 제품 책임자, 스크럼 마스터, 개발팀으로 구성

### 2. 스크럼 팀의 구성

#### 제품 책임자(Product Owner)
- 요구사항이 담긴 **제품 백로그(Product Backlog)**를 작성
- 개발될 제품에 대한 이해도가 높고 요구사항을 책임지는 사람
- 이해관계자들의 의견을 종합하여 제품에 대한 요구사항 작성
- 요구사항의 우선순위를 지정
- 스프린트 중에는 요구사항 우선순위를 변경하지 않는 것이 원칙
- 제품 백로그에 대한 최종 의사결정 책임

> ⭐ `Product Owner = 요구사항 + Product Backlog + 우선순위`

#### 스크럼 마스터(Scrum Master)
- 스크럼 팀이 스크럼을 잘 수행하도록 **가이드 역할**
- 일일 스크럼 회의를 주관
- 팀의 장애 요소를 제거
- 개발 과정에 직접적인 명령을 내리는 관리자와는 다름

> ⭐ `Scrum Master = 조력자 / 가이드 / 장애 제거`

#### 개발팀(Development Team)
- Product Owner와 Scrum Master를 제외한 모든 팀원
- 개발자뿐 아니라 디자이너, 테스터 등 제품 개발에 참여하는 사람들
- 일반적으로 **7~8명 정도**로 구성

### 3. 스크럼 개발 프로세스

```text
제품 백로그
→ 스프린트 계획 회의
→ 스프린트
→ 일일 스크럼 회의
→ 스프린트 검토 회의
→ 스프린트 회고
```

#### 제품 백로그(Product Backlog)
- 제품 개발에 필요한 **모든 요구사항을 우선순위에 따라 나열한 목록**
- 제품이 개발되는 동안 지속적으로 갱신
- 사용자 스토리를 기반으로 작성 가능

#### 스프린트 계획 회의(Sprint Planning Meeting)
- 제품 백로그에서 이번 스프린트 동안 수행할 작업을 선정
- 선정된 작업을 **스프린트 백로그(Sprint Backlog)**로 작성
- 태스크 단위로 작업 분할

#### 스프린트(Sprint)
- 실제 개발 작업을 수행하는 기간
- 보통 **2~4주 정도의 짧은 기간**
- 스프린트 도중에는 개발 목표를 쉽게 변경하지 않음

#### 일일 스크럼 회의(Daily Scrum Meeting)
- 매일 약 **15분 정도**
- 모든 팀원이 진행 상황 점검
- 보통 다음 내용을 공유
  - 어제 한 일
  - 오늘 할 일
  - 문제점 / 장애 요소
- **소멸 차트(Burn-down Chart)**로 남은 작업량 확인

#### 스프린트 검토 회의(Sprint Review)
- 스프린트 결과물에 대해 사용자가 포함된 참석자 앞에서 시연
- 보통 **스프린트당 1시간 정도**

#### 스프린트 회고(Sprint Retrospective)
- 스프린트가 끝난 시점 또는 일정 주기로 수행
- 정해놓은 규칙을 잘 준수했는지, 개선할 점은 없는지 확인

> ⭐ `Scrum 순서 = 백계스일검회`  
> `백로그 → 계획 → 스프린트 → 일일회의 → 검토 → 회고`

## SECTION 003. XP(eXtreme Programming) 기법

### 1. XP(eXtreme Programming)
- 고객의 요구사항에 **유연하게 대응**
- 비교적 작은 규모의 인원이 소프트웨어를 개발할 때 효과적
- 짧고 반복적인 개발 주기
- 단순한 설계
- 고객의 적극적인 참여를 통해 빠르게 개발
- 릴리즈 기간을 짧게 반복하여 요구사항 반영에 대한 가시성을 높임
- 테스트를 강조하여 소프트웨어 품질 향상
- XP의 핵심 가치
  - **의사소통(Communication)**
  - **단순성(Simplicity)**
  - **용기(Courage)**
  - **존중(Respect)**
  - **피드백(Feedback)**

> ⭐ `XP 5대 가치 = 의·단·용·존·피`

### 2. XP 개발 프로세스
```text
사용자 스토리
→ 릴리즈 계획 수립
→ 스파이크
→ 이터레이션
→ 승인 검사
→ 소규모 릴리즈
```

#### 사용자 스토리(User Story)
- 고객의 요구사항을 **간단한 시나리오 형태**로 표현
- 기능 단위로 작성

#### 릴리즈 계획 수립(Release Planning)
- 몇 개의 스토리를 어떤 릴리즈에 포함할지 결정
- 부분 혹은 전체 개발 완료 시점을 결정

#### 스파이크(Spike)
- 요구사항의 신뢰성을 높이고 기술 문제의 위험을 감소시키기 위해 작성하는 **간단한 프로그램**
- 처리할 문제 외의 다른 조건은 무시

#### 이터레이션(Iteration)
- 하나의 릴리즈를 더 세분화한 단위
- 일반적으로 **1~3주 정도**
- 새로운 스토리가 들어오면 우선순위를 고려하여 반영 가능

#### 승인 검사(Acceptance Test)
- 하나의 이터레이션 안에서 계획된 릴리즈 단위의 부분 완료 제품이 구현되면 수행
- 사용자 스토리 작성 시 함께 작성한 테스트 사항에 대해 고객이 직접 수행
- 오류가 발견되면 다음 이터레이션에 포함하여 수정

#### 소규모 릴리즈(Small Release)
- 고객의 반응을 기능별로 확인할 수 있도록 작은 단위로 릴리즈
- 요구사항에 유연하게 대응 가능

### 3. XP의 주요 실천 방법(Practice)

| 방법 | 핵심 |
|---|---|
| **Pair Programming** | 다른 사람과 함께 프로그래밍 / 공동 책임 |
| **Collective Ownership** | 모든 팀원이 소스 코드를 공동으로 소유 / 누구든 수정 가능 |
| **Test-Driven Development(TDD)** | 코드 작성 전 테스트 케이스를 먼저 작성 |
| **Whole Team** | 개발 효율을 위해 고객을 프로젝트 팀의 구성원으로 포함 |
| **Continuous Integration** | 모듈 단위로 개발된 코드를 하나의 작업이 끝날 때마다 지속적으로 통합 |
| **Refactoring** | 기능 변경 없이 프로그램을 쉽게 이해·수정할 수 있도록 내부 구조 개선 |
| **Small Releases** | 릴리즈 기간을 짧게 반복 |

> ⭐ `Pair = 2명 공동 개발`  
> ⭐ `TDD = 테스트 먼저`  
> ⭐ `Refactoring = 기능 변화 없이 구조 개선`

## SECTION 004. 현행 시스템 파악

### 1. 현행 시스템 파악
- 개발하려는 시스템의 요구사항을 정의하기 전에 **현재 운영 중인 시스템의 구성·기능·인터페이스 등을 파악**
- 주요 파악 항목
  - 시스템 구성
  - 시스템 기능
  - 시스템 인터페이스
  - 아키텍처
  - 소프트웨어
  - 하드웨어
  - 네트워크

### 2. 현행 시스템 파악 절차

#### 1단계
- 시스템 구성 파악
- 시스템 기능 파악
- 시스템 인터페이스 파악

#### 2단계
- 아키텍처 구성 파악
- 소프트웨어 구성 파악

#### 3단계
- 하드웨어 구성 파악
- 네트워크 구성 파악

> ⭐ `현행 시스템 파악 = 구성·기능·인터페이스 → 아키텍처·SW → HW·Network`

### 3. 시스템 구성 파악
- 조직의 주요 업무를 담당하는 기간 업무와 이를 지원하는 지원 업무로 구분하여 기술
- 각 업무에 속하는 단위 업무 정보 시스템의 명칭, 주요 기능 등을 명시

### 4. 시스템 기능 파악
- 현행 시스템의 기능을 **주요 기능 → 하부 기능 → 세부 기능** 순서로 계층화
- 계층 구조로 기능을 정리하여 업무의 전체 흐름을 쉽게 파악

### 5. 시스템 인터페이스 파악
- 단위 업무 시스템 간에 주고받는 데이터의 종류·형식·프로토콜·연계 유형·주기 등을 파악
- 주요 확인 항목
  - 송·수신 시스템
  - 연계 방식
  - 데이터 형식
  - 통신 규약
  - 연계 주기

### 6. 아키텍처 구성 파악
- 현행 시스템의 기술 요소들이 어떤 방식으로 구성되어 있는지 **계층별로 표현**
- 예
  - Presentation Layer
  - Business Layer
  - Data Layer

> ⭐ `Architecture = 시스템 기술 요소의 계층 구조`

### 7. 소프트웨어 구성 파악
- 단위 업무 시스템별로 설치되어 있는 소프트웨어의
  - 제품명
  - 용도
  - 라이선스 적용 방식
  - 라이선스 수

  등을 확인

### 8. 하드웨어 구성 파악
- 단위 업무 시스템이 운용되는 서버의 주요 사양·수량·이중화 적용 여부 등을 확인
- 서버 이중화 여부는 시스템 서비스의 연속성과 관련

### 9. 네트워크 구성 파악
- 업무 시스템을 구성하는 서버의
  - 위치
  - 서버 간 네트워크 연결 방식
  - 네트워크 구성

  을 파악
- 네트워크 구성도를 작성하여 물리적 위치와 논리적 연결 관계 확인

## SECTION 006. 요구사항 정의

### 1. 요구사항의 개념 및 특징
- **요구사항** - 소프트웨어가 어떤 문제를 해결하기 위해 제공하는 서비스에 대한 설명과 정상적으로 운영하는 데 필요한 제약조건
- 개발 과정의 기준과 근거를 제공
- 이해관계자 간의 의사소통을 원활하게 함
- 요구사항이 명확하면
  - 개발 비용·일정 산정
  - 개발 기준
  - 검증 기준을 수립하기 쉬움

### 2. 요구사항의 유형

| 구분 | 설명 |
|---|---|
| **기능 요구사항(Functional Requirements)** | 시스템이 무엇을 해야 하는지 / 어떤 기능을 제공해야 하는지 |
| **비기능 요구사항(Non-functional Requirements)** | 성능, 보안, 품질, 제약조건 등 시스템 기능 외 요구 |
| **사용자 요구사항(User Requirements)** | 사용자 관점에서 이해하기 쉽게 작성 |
| **시스템 요구사항(System Requirements)** | 개발자 관점에서 전문적·기술적으로 작성 |

> ⭐ `기능 = What`  
> ⭐ `비기능 = 성능·보안·품질·제약`  
> ⭐ `사용자 = 쉬운 표현 / 시스템 = 기술적 표현`

### 3. 기능 요구사항
- 시스템의
  - 입력
  - 출력
  - 처리
  - 저장
  - 수행 기능 등을 명시
- 예) 로그인 기능, 데이터 검색 기능, 주문 처리 기능

### 4. 비기능 요구사항
- 시스템이 기능을 수행하면서 만족해야 하는 제약사항·품질 조건
- 주요 비기능 요구사항
  - 시스템 장비 구성
  - 성능
  - 인터페이스
  - 데이터
  - 테스트
  - 보안
  - 품질
  - 프로젝트 관리
  - 프로젝트 지원 등

> ⭐ `비기능 = 기능 자체가 아니라 "얼마나 잘, 어떤 조건에서" 수행할지`

### 5. 요구사항 개발 프로세스
```text
도출(Elicitation)
→ 분석(Analysis)
→ 명세(Specification)
→ 확인(Validation)
```

#### 요구사항 도출(Elicitation)
- 시스템, 사용자, 개발자 등 이해관계자 간의 **의사소통을 통해 요구사항 수집**
- 인터뷰, 설문, 브레인스토밍, 워크숍, 프로토타이핑, 유스케이스 등을 활용

#### 요구사항 분석(Analysis)
- 요구사항 중
  - 명확하지 않거나
  - 모순되거나
  - 불완전한 부분을 발견하고 걸러냄
- 비용·일정 등에 대한 제약 설정
- 요구사항의 타당성을 조사
- 필요 시 우선순위 부여

#### 요구사항 명세(Specification)
- 분석된 요구사항을 바탕으로 **요구사항 명세서 작성**
- 사용자가 이해하기 쉽고 개발자가 효과적으로 설계할 수 있도록 작성

#### 요구사항 확인(Validation)
- 개발 자원을 요구사항에 할당하기 전 요구사항 명세서가
  - 정확한지
  - 완전한지
  - 일관성이 있는지

  검토
- 요구사항 관리 도구를 이용해 추적 가능

> ⭐ `요구사항 개발 = 도분명확`

### 6. 요구사항 명세 기법

| 구분 | 정형 명세 기법 | 비정형 명세 기법 |
|---|---|---|
| 기법 | 수학적 원리·표기법 | 자연어 / 그림 중심 |
| 장점 | 정확·간결 / 명세가 명확 | 작성·이해 쉬움 |
| 단점 | 작성·이해 어려움 | 모호성 발생 가능 |
| 종류 | VDM, Z, Petri-net, CSP 등 | FSM, Decision Table, ER 모델링, State Chart 등 |

> ⭐ `정형 = 수학적 / 정확하지만 어려움`  
> ⭐ `비정형 = 자연어·그림 / 쉽지만 모호 가능`

### 7. 요구사항 명세서(SRS; Software Requirement Specification)
- 사용자가 요구한 내용을 분석한 후 **요구사항을 명확하게 기록한 문서**
- 요구사항 명세서에는 기능·비기능 요구사항을 빠짐없이 기술
- 시스템이 수행할 모든 기능과 제약조건을 정의

#### 좋은 요구사항 명세서의 특성
- 정확성
- 명확성
- 완전성
- 일관성
- 수정 용이성
- 추적 가능성

> ⭐ `SRS = 요구사항을 공식적으로 기록한 문서`

## SECTION 007. 요구사항 분석

### 1. 요구사항 분석
- 개발 대상에 대한 사용자의 요구사항 중
  - 명확하지 않거나
  - 모순되거나
  - 불완전한 부분

  을 발견하고 수정하는 과정
- 요구사항의 타당성 조사
- 비용·일정 제약 설정
- 요구사항 간의 우선순위 설정
- UML, 자료 흐름도(DFD), 자료 사전(DD), 개체 관계도(ERD) 등 사용 가능

### 2. 구조적 분석 기법
- 자료의 흐름과 처리를 중심으로 요구사항을 분석
- 도형 중심의 분석 도구를 이용하여 사용자와 의사소통하기 쉬움
- 하향식 방법으로 시스템을 세분화
- 주요 도구
  - **자료 흐름도(DFD)**
  - **자료 사전(DD)**
  - **소단위 명세서(Mini-Spec)**
  - **개체 관계도(ERD)**
  - **상태 전이도(STD)**
  - **제어 명세서**

> ⭐ `구조적 분석 = DFD + DD + Mini-Spec + ERD + STD`

### 3. 자료 흐름도(DFD; Data Flow Diagram)
- 시스템 안에서 데이터가 **어디에서 발생하고, 어떤 과정을 거쳐 어디로 이동하는지** 표현
- 자료 흐름 그래프 또는 버블 차트라고도 함
- 자료 흐름과 기능을 중심으로 시스템을 시각화

#### DFD 기본 요소

| 기호 | 의미 |
|---|---|
| **Process** | 자료를 변환시키는 처리 과정 |
| **Data Flow** | 자료 흐름 |
| **Data Store** | 자료 저장소 |
| **Terminator** | 시스템 외부의 데이터 발생·도착 대상 |

> ⭐ `DFD = Process / Flow / Store / Terminator`

### 4. 자료 사전(DD; Data Dictionary)
- 자료 흐름도에 있는 자료를 **더 자세하게 정의하고 기록**
- 데이터의 의미·구성 등을 정의

#### 자료 사전 기호

| 기호 | 의미 |
|---|---|
| `=` | 자료의 정의 |
| `+` | 자료의 연결(And) |
| `( )` | 생략 가능(Optional) |
| `[ ]` | 선택(Or) |
| `{ }` | 반복 |
| `* *` | 설명(Comment) |

> ⭐ `= 정의 / + 연결 / ( ) 생략 / [ ] 선택 / { } 반복 / * * 설명`

## SECTION 008. 요구사항 분석 CASE와 HIPO

### 1. 요구사항 분석을 위한 CASE
- **CASE(Computer Aided Software Engineering)** - 소프트웨어 개발 과정에서 사용되는 요구사항 분석, 설계, 구현, 검사 등의 과정을 **컴퓨터와 전용 소프트웨어 도구로 자동화**
- 요구사항 분석용 CASE는 요구사항을 자동으로 분석하고 명세서를 작성하는 도구

#### 대표적인 요구사항 분석 CASE
- **SADT**
- **SREM**
- **PSL/PSA**
- **TAGS**
- **EPOS**

> ⭐ `CASE = 소프트웨어 개발 과정 자동화`

### 2. 대표적인 CASE 도구

#### SADT(Structured Analysis and Design Technique)
- SoftTech사가 개발
- 구조적 요구 분석을 위해 블록 다이어그램 사용
- 시스템 정의, 소프트웨어 요구사항 분석, 시스템/소프트웨어 설계 등에 활용

#### SREM(Software Requirements Engineering Methodology)
- TRW사가 개발
- RSL과 REVS를 사용
  - **RSL(Requirement Statement Language)** - 요구사항 명세 언어
  - **REVS(Requirement Engineering and Validation System)** - 요구사항 분석기

#### PSL/PSA
- 미시간 대학에서 개발
- **PSL** - 문제 명세 언어
- **PSA** - 문제 분석기

#### TAGS
- 시스템 공학 방법 응용에 대한 자동 접근 방법
- 개발 주기의 전 과정에 이용할 수 있는 통합 자동화 도구

> ⭐ `SREM = RSL + REVS`  
> ⭐ `PSL/PSA = 문제 명세 언어 + 분석기`


### 3. HIPO(Hierarchy Input Process Output)
- 시스템의 분석 및 설계 또는 문서화에 사용되는 **계층적 표현 도구**
- 기능과 자료의 의존 관계를 동시에 표현
- 시스템의 기능을 여러 개의 고유 모듈로 분할하여 이들 간의 **인터페이스를 계층 구조로 표현**
- 하향식 소프트웨어 개발을 위한 문서화 도구
- 보기 쉽고 이해하기 쉬움

> ⭐ `HIPO = 계층적 + Input / Process / Output`

### 4. HIPO Chart 종류

#### 가시적 도표(Visual Table of Contents)
- 시스템 전체 기능과 흐름을 **계층 구조**로 나타냄
- 기능별로 번호 부여

#### 총체적 도표(Overview Diagram)
- 프로그램을 구성하는 기능을 기술
- 입력, 처리, 출력에 대한 전반적인 정보 제공

#### 세부적 도표(Detail Diagram)
- 총체적 도표에 표시된 기능을 구성하는 **기본 요소들을 상세히 기술**

> ⭐ `HIPO = 가시적 / 총체적 / 세부적`

## SECTION 009. UML(Unified Modeling Language)

### 1. UML의 개요
- **UML(Unified Modeling Language)** - 시스템 개발 과정에서
  - 시스템 분석
  - 설계
  - 구현

  등 시스템 개발자와 고객 또는 개발자 상호 간의 의사소통을 원활하게 하기 위해 만든 **표준화된 객체지향 모델링 언어**
- OMG에서 표준으로 지정
- 대표 구성 요소
  - **사물(Things)**
  - **관계(Relationships)**
  - **다이어그램(Diagrams)**

> ⭐ `UML = 사물 + 관계 + 다이어그램`

### 2. 사물(Things)
- 모델을 구성하는 가장 중요한 기본 요소
- 다이어그램 안에서 관계가 형성될 수 있는 대상

| 사물 | 핵심 |
|---|---|
| **구조 사물(Structural Things)** | 시스템의 개념적·물리적 요소 / Class, Use Case, Component 등 |
| **행동 사물(Behavioral Things)** | 시간과 공간에 따른 시스템의 행위 |
| **그룹 사물(Grouping Things)** | 요소들을 그룹으로 묶음 / Package |
| **주해 사물(Annotation Things)** | 부가적인 설명·제약조건 표현 / Note |

> ⭐ `사물 = 구조 / 행동 / 그룹 / 주해`

### 3. 관계(Relationships)

#### 연관 관계(Association)
- 2개 이상의 사물이 서로 관련되어 있음을 표현
- 실선으로 연결
- 방향성은 화살표로 표시 가능
- 다중도(Multiplicity) 표현

#### 집합 관계(Aggregation)
- 하나의 사물이 다른 사물에 포함되어 있는 **전체-부분 관계**
- 부분 객체가 전체 객체와 **독립적으로 존재 가능**
- 빈 마름모 표시

> ⭐ `Aggregation = 포함되지만 독립 가능`

#### 포함 관계(Composition)
- 집합 관계보다 더 강한 전체-부분 관계
- 부분 객체가 전체 객체에 **종속**
- 전체 객체가 없어지면 부분 객체도 사라짐
- 채워진 마름모 표시

> ⭐ `Composition = 강한 포함 / 생명주기 종속`

#### 일반화 관계(Generalization)
- 하나의 사물이 다른 사물에 비해 더 일반적·구체적인 관계
- 객체지향의 **상속(Inheritance)**과 유사
- 속이 빈 화살표 사용

> ⭐ `Generalization = 일반 ↔ 구체 / 상속`

#### 의존 관계(Dependency)
- 서로 연관은 있으나 필요에 의해 **짧은 시간 동안만 관계 유지**
- 한 사물의 변화가 다른 사물에 영향을 줄 수 있음
- 점선 화살표 사용

> ⭐ `Dependency = 일시적 사용 관계`

#### 실체화 관계(Realization)
- 사물이 할 수 있거나 해야 하는 기능으로 서로를 그룹화할 수 있는 관계
- **인터페이스와 구현 클래스**의 관계
- 점선 + 빈 화살표

> ⭐ `Realization = Interface 구현`

### 4. 다이어그램(Diagram)
- 사물과 관계를 도형으로 표현한 것
- 여러 관점에서 시스템을 가시화

#### 구조적(Structural) 다이어그램
- Class Diagram
- Object Diagram
- Component Diagram
- Deployment Diagram
- Composite Structure Diagram
- Package Diagram

#### 행위(Behavioral) 다이어그램
- Use Case Diagram
- Sequence Diagram
- Communication Diagram
- State Diagram
- Activity Diagram
- Interaction Overview Diagram
- Timing Diagram

> ⭐ `구조적 = 정적 구조`  
> ⭐ `행위 = 동적 행동`

## SECTION 010. 주요 UML 다이어그램

### 1. 유스케이스(Use Case) 다이어그램
- 개발될 시스템과 관련된 **외부 요소와 시스템 사이의 상호 작용을 확인**
- 사용자의 요구사항을 분석하기 위한 도구
- 시스템의 범위를 파악하는 데 도움

#### 구성 요소
| 요소 | 의미 |
|---|---|
| **System / System Scope** | 시스템 범위 |
| **Actor** | 시스템과 상호 작용하는 외부 요소 / 사람 또는 다른 시스템 |
| **Use Case** | 사용자가 시스템을 통해 수행하는 기능 |
| **Relationship** | Actor와 Use Case 또는 Use Case 간 관계 |

#### 유스케이스 관계
- 연관(Association)
- 포함(Include)
- 확장(Extend)
- 일반화(Generalization)

> ⭐ `Use Case Diagram = Actor + Use Case + Relationship`

### 2. 클래스(Class) 다이어그램
- 시스템을 구성하는 **클래스와 클래스 간 관계를 표현**
- 시스템의 구조를 파악하고 구조상의 문제점을 도출
- 클래스의 속성(Attribute), 오퍼레이션(Operation), 제약조건 등을 표현

#### 클래스 구성
```text
클래스 이름
──────────
속성(Attribute)
──────────
오퍼레이션(Operation)
```

#### 접근 제어 기호
| 기호 | 의미 |
|---|---|
| `-` | Private |
| `+` | Public |
| `#` | Protected |
| `~` | Package |

> ⭐ `Class = 이름 + 속성 + Operation`


### 3. 순차(Sequence) 다이어그램
- 시스템이나 객체들이 **메시지를 주고받으며 시간의 흐름에 따라 상호 작용하는 과정**을 표현
- 동적 모델링에 사용
- 객체 간 메시지 전달 순서를 쉽게 파악 가능

#### 주요 요소
- **Actor** - 외부 사용자
- **Object** - 메시지를 주고받는 객체
- **Lifeline** - 객체가 존재하는 시간
- **Activation** - 객체가 수행 중인 기간
- **Message** - 객체 간 상호 작용

> ⭐ `Sequence = 시간 순서에 따른 Message 흐름`

### 4. 기타 주요 구조적 다이어그램

| 다이어그램 | 핵심 |
|---|---|
| **Object Diagram** | 특정 시점의 객체와 관계 표현 |
| **Component Diagram** | 실제 구현 모듈인 컴포넌트 간 관계 표현 |
| **Deployment Diagram** | 물리적 요소(노드)들의 구성·배치 표현 |
| **Composite Structure Diagram** | 클래스·컴포넌트 내부 구조 표현 |
| **Package Diagram** | 패키지 간 관계 표현 |

### 5. 기타 주요 행위 다이어그램

| 다이어그램 | 핵심 |
|---|---|
| **Communication Diagram** | 객체 간 메시지뿐 아니라 객체 간 연관까지 표현 |
| **State Diagram** | 하나의 객체가 상태 변화 또는 상호 작용에 따라 상태가 어떻게 변하는지 표현 |
| **Activity Diagram** | 시스템 기능 수행 과정의 처리 흐름을 순서대로 표현 |
| **Interaction Overview Diagram** | 여러 상호작용 다이어그램 간 제어 흐름 표현 |
| **Timing Diagram** | 객체 상태 변화와 시간 제약을 명시적으로 표현 |

> ⭐ `Sequence = 시간 순 메시지`  
> ⭐ `State = 상태 변화`  
> ⭐ `Activity = 처리 흐름`
