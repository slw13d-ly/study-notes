# 04. 인터페이스 설계

## SECTION 024. 시스템 인터페이스 요구사항 분석

### 1. 시스템 인터페이스 요구사항 구성
- **시스템 인터페이스** - 독립적으로 떨어져 있는 시스템들끼리 서로 연동하여 **상호 작용하기 위한 접속 방법이나 규칙**
- 시스템 인터페이스 요구사항은 개발할 시스템과 외부 시스템을 연동하는 데 필요한 **시스템 인터페이스의 이름과 목적을 정의한 요구사항**
- 요구사항 명세서에는 인터페이스에 필요한 내용을 구체적으로 작성

#### 시스템 인터페이스 요구사항에 포함되는 주요 내용
- 인터페이스 이름
- 연계 대상 시스템
- 연계 범위 및 내용
- 연계 방식
- 송·수신 데이터
- 인터페이스 주기
- 기타 고려사항

> ⭐ `시스템 인터페이스 요구사항 = 시스템 간 연동에 필요한 규칙과 데이터 정의`


### 2. 요구사항 명세서
- 요구사항 명세서는 프로젝트 수행 시 **기준이 되는 문서**
- 개발해야 하는 시스템의 요구사항을 구체적으로 기록
- 시스템 개발 과정에서 의사소통과 검증의 기준으로 사용
- 인터페이스 요구사항도 전체 시스템 요구사항 명세에 포함하여 관리

#### 요구사항 명세서 예시 항목
- 요구사항 분류
- 요구사항 고유 번호
- 요구사항 명칭
- 정의
- 요구사항 상세 설명
- 산출 정보
- 관련 요구사항
- 요구사항 출처

> ⭐ `요구사항 명세서 = 개발·검증의 기준 문서`


### 3. 시스템 인터페이스 요구사항 분석
- 요구사항 명세서에서 **인터페이스 관련 요구사항만 선별**
- 요구사항을 기능적 요구사항과 비기능적 요구사항으로 분류
- 요구사항의
  - 내용
  - 관련 자료
  - 인터페이스 목적

  등을 분석하여 필요한 기능을 구체화

#### 분석 시 유의사항
- 요구사항의 의미가 명확한지 확인
- 서로 모순되는 요구사항은 없는지 확인
- 요구사항의 누락 여부 확인
- 요구사항이 실제 구현 가능한지 확인
- 요구사항에 대한 상대적 중요도 고려

> ⭐ `인터페이스 요구사항 분석 = 명세서에서 인터페이스 관련 요구만 추출·분석`


### 4. 시스템 인터페이스 요구사항 분석 절차

```text
요구사항 선별
→ 관련 자료 준비
→ 요구사항 분류
→ 요구사항 분석 및 명세서 구체화
→ 요구사항 명세서 공유
```

#### ① 요구사항 선별
- 소프트웨어 요구사항 목록에서 **시스템 인터페이스 관련 요구사항을 선별**
- 별도의 시스템 인터페이스 요구사항 목록 작성

#### ② 관련 자료 준비
- 시스템 인터페이스 요구사항과 관련된
  - 요구사항 정의서
  - 현행 시스템 자료
  - 관련 시스템 인터페이스 목록

  등을 준비

#### ③ 요구사항 분류
- 기능적 요구사항과 비기능적 요구사항으로 구분

#### ④ 요구사항 분석 및 구체화
- 요구사항의
  - 의미
  - 타당성
  - 구현 가능성

  을 분석
- 필요하면 요구사항을 보다 구체적으로 명세

#### ⑤ 요구사항 명세서 공유
- 분석된 시스템 인터페이스 요구사항을 관계자에게 전달·공유

> ⭐ 절차 → `선별 → 자료 → 분류 → 분석·구체화 → 공유`


### 5. 기능적 / 비기능적 인터페이스 요구사항

#### 기능적 요구사항
- 시스템이 **무엇을 수행해야 하는지**에 관한 요구사항
- 예
  - 데이터 송신
  - 데이터 수신
  - 특정 정보 조회
  - 특정 기능 연계

#### 비기능적 요구사항
- 인터페이스가 어떤 품질과 조건을 만족해야 하는지에 관한 요구사항
- 예
  - 처리 속도 및 시간
  - 보안
  - 시스템 장애 대응
  - 신뢰성 등

> ⭐ `기능 = 무엇을 할 것인가`  
> ⭐ `비기능 = 어떤 조건·품질로 수행할 것인가`

## SECTION 025. 인터페이스 요구사항 검증

### 1. 요구사항 검증(Requirements Verification)
- 인터페이스 설계 및 구현 전에 사용자의 요구사항이 **요구사항 명세서에 정확하고 완전하게 기술되었는지 검토**
- 개발 범위의 기준인 **베이스라인(Baseline)**을 설정하는 작업
- 요구사항에 오류가 있으면 이후 단계의 비용이 커질 수 있으므로 초기 검증이 중요

> ⭐ `요구사항 검증 = 명세서가 정확·완전한지 확인 → Baseline 설정`


### 2. 인터페이스 요구사항 검토 계획 수립
- 프로젝트 이해관계자와 관련 자료를 참고하여 검토 계획 수립

#### 검토 계획에 포함되는 주요 항목

| 항목 | 핵심 |
|---|---|
| **검토 기준 및 방법** | 요구사항 검토 기준과 검토 방법 정의 |
| **참여자** | 프로젝트 관리자, 품질 관리자, 인터페이스 분석가, 시스템 사용자 등 |
| **체크리스트** | 요구사항 검토 시 확인할 내용을 목록화 |
| **관련 자료** | 인터페이스 요구사항 명세서, 관련 시스템 자료 등 |
| **일정** | 인터페이스 요구사항 검증 일정 |

> ⭐ `검토 계획 = 기준·방법 / 참여자 / 체크리스트 / 자료 / 일정`


### 3. 인터페이스 요구사항 검토 및 오류 수정
- 체크리스트의 항목에 따라 인터페이스 요구사항 명세서를 검토
- 오류가 발견되면
  - 오류 목록 작성
  - 시정 조치 수행
- 오류 수정 후 승인 절차를 진행할 수 있도록 **검토 결과를 관계자에게 전달**
- 시정 조치가 완료되었는지 확인한 후 검토 작업 종료

> ⭐ `검토 → 오류 발견 → 수정 → 시정 조치 확인`


### 4. 인터페이스 요구사항의 베이스라인 설정
- 검토가 완료된 인터페이스 요구사항을 프로젝트 관리자가 **공식적으로 승인**
- 승인된 인터페이스 요구사항을 **베이스라인(Baseline)**으로 설정
- 이후 변경이 필요한 경우 정해진 변경 관리 절차에 따라 관리

> ⭐ `Baseline = 공식적으로 승인된 요구사항 기준선`


### 5. 요구사항 검증 방법

#### 동료 검토(Peer Review)
- 요구사항 명세서 작성자가 내용을 직접 설명
- 동료들이 설명을 들으면서 결함을 발견

#### 워크스루(Walk Through)
- 검토 회의 전에 요구사항 명세서를 **미리 배포**
- 사전 검토 후 짧은 검토 회의를 통해 오류 확인

#### 인스펙션(Inspection)
- 요구사항 명세서 작성자를 제외한 **다른 전문가 또는 팀**이 검토
- 검토를 통해 결함을 발견하고 수정

> ⭐ `Peer Review = 작성자가 설명`  
> ⭐ `Walk Through = 사전 배포 후 검토 회의`  
> ⭐ `Inspection = 작성자 제외 전문가 검토`


### 6. 기타 요구사항 검증 방법

#### 프로토타이핑(Prototyping)
- 사용자의 요구사항을 정확히 파악하기 위해 실제 개발될 소프트웨어의 **견본(Prototype)**을 만들어 요구사항 확인

#### 테스트 설계
- 요구사항을 기반으로 테스트 케이스를 작성할 수 있는지 확인
- 테스트 가능한 요구사항인지 검증

#### CASE 도구 활용
- 요구사항 분석용 CASE 도구를 이용하여
  - 일관성
  - 추적성

  등을 자동으로 검증


### 7. 인터페이스 요구사항 검증의 주요 항목

| 검증 항목 | 확인 내용 |
|---|---|
| **완전성(Completeness)** | 사용자의 모든 요구사항이 빠짐없이 반영되었는가 |
| **일관성(Consistency)** | 요구사항끼리 모순되거나 충돌하지 않는가 |
| **명확성(Unambiguity)** | 모든 참여자가 요구사항을 명확하게 이해할 수 있는가 |
| **기능성(Functionality)** | 요구사항이 `어떻게(How)`보다 필요한 `무엇(What)`에 중점을 두고 있는가 |
| **검증 가능성(Verifiability)** | 요구사항이 사용자의 요구를 만족하는지 개발 완료 후 확인할 수 있는가 |
| **추적 가능성(Traceability)** | 요구사항 명세서와 설계서를 추적할 수 있는가 |
| **변경 용이성(Easily Changeable)** | 요구사항 명세서를 쉽게 변경할 수 있도록 작성했는가 |

## SECTION 026. 인터페이스 방법 명세화

### 1. 인터페이스 방법 명세화의 개념
- 내·외부 시스템을 연계하여 작동할 때
  - 인터페이스별 송·수신 방법
  - 송·수신 데이터
  - 오류 식별 및 처리 방안

  등에 대한 내용을 **문서로 명확하게 정의하는 것**
- 인터페이스별로 다음 정보가 필요
  - 시스템 연계 기술
  - 인터페이스 통신 유형
  - 처리 유형
  - 발생 주기

> ⭐ `인터페이스 명세화 = 어떻게 연결·통신·처리할지 문서화`


### 2. 시스템 연계 기술

| 기술 | 핵심 |
|---|---|
| **DB Link** | DB에서 제공하는 DB Link 객체를 이용하여 DB 간 연결 |
| **API / Open API** | 송신 시스템의 DB에서 데이터를 읽어 제공하는 애플리케이션 프로그래밍 인터페이스 |
| **연계 솔루션** | EAI 서버와 각 시스템에 설치되는 클라이언트(Client)를 이용해 시스템 간 연계 |
| **Socket** | 서버가 통신용 Socket을 생성하고 Port를 할당하여 클라이언트 요청을 연결 |
| **Web Service** | 웹 서비스에서 WSDL, UDDI, SOAP 등을 이용하여 시스템 연계 |

> ⭐ 시스템 연계 기술 → `DB Link / API / EAI / Socket / Web Service`


### 3. 인터페이스 통신 유형

#### 단방향
- 시스템에서 거래를 요청하고 **응답이 필요 없는 방식**

#### 동기(Synchronous)
- 시스템에서 거래를 요청하고 **응답이 올 때까지 기다리는 방식**
- 대표 형태 → **Request-Reply**

#### 비동기(Asynchronous)
- 시스템에서 거래를 요청하고 **다른 작업을 수행하다가 응답을 확인**
- 대표 형태
  - Send-Receive
  - Send-Receive-Acknowledge
  - Publish-Subscribe 등

> ⭐ `단방향 = 응답 X`  
> ⭐ `동기 = 요청 후 응답 대기`  
> ⭐ `비동기 = 요청 후 다른 작업 가능`


### 4. 인터페이스 처리 유형
- 송·수신 데이터를 어떤 형태로 처리할지 결정

#### 실시간 방식
- 사용자가 요청한 내용을 **바로 처리**

#### 지연 처리 방식
- 데이터를 일정 시간 동안 모아 두었다가 **나중에 처리**

#### 배치 방식
- 대량 데이터를 **일괄 처리**

> ⭐ `처리 유형 = 실시간 / 지연 / 배치`


### 5. 인터페이스 발생 주기
- 개발할 시스템과 내·외부 시스템 간 송·수신 데이터의 **발생 빈도와 주기**
- 업무 성격과 송·수신 데이터 전송량 등을 고려하여 정의
- 예
  - 매일
  - 수시
  - 주간
  - 월간 등

> ⭐ `발생 주기 = 업무 성격 + 데이터 전송량을 고려`


### 6. 송·수신 방법 명세화
- 인터페이스 목록에 있는 각각의 인터페이스에 대해
  - 연계 방식
  - 통신 유형
  - 처리 유형
  - 발생 주기

  등을 정의

#### 주요 명세 항목
- 인터페이스 ID
- 인터페이스명
- 송신 시스템
- 수신 시스템
- 연계 방식
- 통신 유형
- 연계 처리 유형
- 연계 주기

> ⭐ `송·수신 명세 = 누가 → 누구에게 / 어떤 방식 / 언제 / 어떻게 처리`


### 7. 송·수신 데이터 명세화
- 내·외부 인터페이스 목록에 있는 각각의 인터페이스에 대해 **인터페이스 시 필요한 송·수신 데이터 항목을 정의**
- 인터페이스별 테이블 정의서와 파일 레이아웃에서 연계하고자 하는 데이터 항목을 정의

#### 데이터 명세의 주요 항목
- Field
- Key 여부
- Type
- Size
- Null 허용 여부
- Description
- Condition

> ⭐ `데이터 명세 = Field / Key / Type / Size / Null / 설명 / 조건`


### 8. 오류 식별 및 처리 방안 명세화
- 인터페이스 수행 중 발생할 수 있는 **예외·오류 상황을 정의**
- 시스템 간 연계 과정에서
  - 송신 시스템
  - 연계 서버
  - 수신 시스템

  의 오류 상황을 고려

#### 오류 처리 항목
- 오류 코드
- 오류 메시지
- 오류 설명
- 해결 방법

> ⭐ `오류 명세 = Error Code + Message + 설명 + 해결 방법`

## SECTION 027. 미들웨어 솔루션 명세

### 1. 미들웨어(Middleware)의 개념
- **미들웨어** - 운영체제와 소프트웨어 사이 또는 서로 다른 응용 소프트웨어 사이에서 **연결 역할을 수행하는 소프트웨어**
- 서로 다른 하드웨어·프로토콜·통신 환경을 연결
- 운영체제와 응용 프로그램, 응용 프로그램과 응용 프로그램 사이에서 다양한 서비스를 제공
- **표준화된 인터페이스**를 제공하여 시스템 간 데이터 교환의 일관성을 보장
- **위치 투명성(Location Transparency)** 제공
- 사용자가 미들웨어 내부 동작을 확인하려면 별도의 응용 소프트웨어를 사용
- 시스템 연결 방식
  - `1:1`
  - `1:N`
  - `N:M`

#### 미들웨어의 종류
- DB
- RPC
- MOM
- TP-Monitor
- ORB
- WAS

> ⭐ `Middleware = 서로 다른 시스템·SW 사이의 연결 역할`  
> ⭐ 종류 → `DB / RPC / MOM / TP-Monitor / ORB / WAS`


### 2. DB(DataBase) 미들웨어
- 클라이언트에서 원격의 데이터베이스와 연결하기 위한 미들웨어
- DB를 이용하여 시스템을 구축하는 경우 보통 **2-Tier 아키텍처**
- 대표 예
  - Microsoft **ODBC**
  - Borland **IDAPI**
  - Oracle **Glue**

> ⭐ `DB Middleware = Client ↔ DB 연결 / 2-Tier`


### 3. RPC(Remote Procedure Call)
- 응용 프로그램의 프로시저를 사용하여 **원격 프로시저를 로컬 프로시저처럼 호출**
- 네트워크 상의 다른 컴퓨터에 있는 프로시저를 호출할 수 있도록 함
- 대표 예
  - Entera
  - ONC/RPC

> ⭐ `RPC = 원격 Procedure를 Local처럼 호출`


### 4. MOM(Message Oriented Middleware)
- **메시지 기반의 비동기형 메시지 전달 방식**
- 서로 다른 플랫폼에서 독립적으로 실행되는 소프트웨어 간 상호작용 지원
- 이기종 분산 데이터 시스템의 데이터 동기 등에 많이 사용

> ⭐ `MOM = Message 기반 + 비동기`


### 5. TP-Monitor(Transaction Processing Monitor)
- 항공기·철도 예약 업무 등과 같은 **온라인 트랜잭션 업무에서 트랜잭션을 처리·감시하는 미들웨어**
- 사용자 수가 증가해도 빠른 응답 속도를 유지해야 하는 업무에 사용
- 대표 예
  - Oracle **tuxedo**
  - Tmax **tmax**

> ⭐ `TP-Monitor = Transaction 처리 + Monitoring`


### 6. ORB(Object Request Broker)
- 객체 지향 미들웨어
- **CORBA 표준 스펙을 구현한 미들웨어**
- 분산 환경에서 객체 간 메시지 전달과 상호작용을 지원
- 대표 예
  - Micro Focus Orbix
  - OMG CORBA

> ⭐ `ORB = Object 기반 / CORBA`


### 7. WAS(Web Application Server)
- 정적인 콘텐츠가 아니라 **동적인 콘텐츠를 처리**하기 위한 미들웨어
- 사용자의 요구에 따라 동적인 콘텐츠 처리
- 웹 서버 기능뿐만 아니라 업무 로직을 수행
- 일반적으로 HTTP 세션 처리 기능뿐 아니라
  - 미션 크리티컬한 기업 업무
  - JAVA
  - EJB

  컴포넌트 기반으로 구현
- 대표 예
  - Oracle WebLogic
  - IBM WebSphere

> ⭐ `WAS = 동적 Web Content + Business Logic`


### 8. 미들웨어 솔루션 식별
- 개발 및 운영 환경에 사용할 미들웨어 솔루션을 확인하고 목록 작성
- 소프트웨어 아키텍처에서 정의한 시스템 구조와 구축 예정 소프트웨어를 바탕으로 선정
- 선정한 미들웨어 솔루션에는 다음 정보를 기록
  - 시스템
  - 구분
  - 솔루션명
  - 버전
  - 제조사

> ⭐ `미들웨어 식별 = 아키텍처·운영환경에 맞는 솔루션 목록 작성`


### 9. 미들웨어 솔루션 명세서 작성
- 미들웨어 솔루션 목록의 각 제품에 대한 **관련 정보를 상세하게 기록**
- 제품 정보와 특징을 분석하여 프로젝트 환경에 적합한지 검토
- 작성한 명세서는 관련 개발자에게 전달하여 **오류 및 누락 여부를 확인하고 수정**

#### 명세서에 포함할 주요 내용
- 제품명 및 버전
- 제품 사용 목적
- 시스템 요구사항
- 제품 사용 환경
- 제품의 주요 특징
- 구성 및 기능
- 제약 사항
- 기타 참고 사항

> ⭐ `솔루션 명세 = 제품 정보 + 환경 + 기능 + 제약사항`
