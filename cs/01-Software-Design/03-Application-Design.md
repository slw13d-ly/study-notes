# 03. 애플리케이션 설계

## SECTION 016. 소프트웨어 아키텍처

### 1. 소프트웨어 아키텍처의 설계
- **소프트웨어 아키텍처(Software Architecture)** - 소프트웨어의 골격이 되는 **기본 구조**
- 소프트웨어를 구성하는
  - 요소
  - 요소 간 관계
  - 제약사항

  등을 나타냄
- 소프트웨어 개발에 적용되는 **원칙과 지침**이며 이해관계자의 의사소통 도구로 활용
- 기본적으로 좋은 품질을 유지하면서 사용자의 **비기능적 요구사항**을 반영하고, 기능적 요구사항을 구현하는 방법을 찾는 해결 과정
- 애플리케이션의 분할 방법과 분할된 모듈에 할당될 기능, 모듈 간 인터페이스 등을 결정
- 기본 원리
  - **모듈화**
  - **추상화**
  - **단계적 분해**
  - **정보 은닉**

> ⭐ `소프트웨어 아키텍처 = 시스템의 기본 골격 + 구성 요소 간 관계`  
> ⭐ 기본 원리 → `모·추·단·정`  
> `모듈화 / 추상화 / 단계적 분해 / 정보 은닉`

---

### 2. 상위 설계와 하위 설계

| 구분 | 상위 설계 | 하위 설계 |
|---|---|---|
| **별칭** | 아키텍처 설계, 예비 설계 | 모듈 설계, 상세 설계 |
| **설계 대상** | 시스템 전체 구조 | 시스템 내부 구조 및 행위 |
| **세부 내용** | 구조, DB, 인터페이스 | 컴포넌트, 자료 구조, 알고리즘 |

> ⭐ `상위 설계 = 전체 구조`  
> ⭐ `하위 설계 = 모듈 내부의 상세 구현`

---

### 3. 모듈화(Modularity)
- 시스템의 기능을 **모듈 단위로 분해**하여 소프트웨어의 성능 향상, 유지관리 등을 쉽게 하는 기법
- 자주 사용되는 계산·기능을 하나의 모듈로 만들어 재사용 가능
- 모듈의 크기를 너무 작게 나누면
  - 모듈 수 증가
  - 통합 비용 증가
- 모듈의 크기를 너무 크게 만들면
  - 모듈 하나의 개발 비용 증가
- 적절한 크기의 모듈로 구성하는 것이 중요
- 모듈화를 통해 기능 분리가 가능해지고 **인터페이스가 단순해짐**
- 모듈을 통해 프로그램의 효율적인 관리와 성능 향상 가능

> ⭐ `모듈화 = 기능을 작은 단위로 분리 → 재사용·유지보수 용이`

---

### 4. 추상화(Abstraction)
- 문제의 전체적이고 포괄적인 개념을 먼저 설계한 뒤 **구체화해 나가는 과정**
- 인간이 복잡한 문제를 다룰 때 사용하는 기본적인 방법
- 세부 내용을 숨기고 중요한 부분만 표현하여 시스템의 구조와 구성을 이해하기 쉽게 함

#### 추상화의 유형

| 유형 | 핵심 |
|---|---|
| **과정 추상화(Process Abstraction)** | 자세한 수행 과정을 정의하지 않고 **전반적인 흐름만 파악**할 수 있도록 설계 |
| **데이터 추상화(Data Abstraction)** | 데이터의 세부적인 구조를 정의하지 않고 **데이터 연산 중심**으로 정의 |
| **제어 추상화(Control Abstraction)** | 이벤트 발생의 정확한 절차·방법을 정의하지 않고 **대표적인 표현으로 대체** |

> ⭐ `추상화 = 과정 / 데이터 / 제어`

---

### 5. 단계적 분해(Stepwise Refinement)
- **Niklaus Wirth**가 제안한 하향식 설계 전략
- 문제를 상위의 중요 개념에서 **하위 개념으로 단계적으로 구체화**
- 추상화의 반복에 의해 세분화
- 소프트웨어 기능에서 시작하여
  - 절차적으로 구체화
  - 알고리즘
  - 자료 구조

  등을 상세하게 표현

> ⭐ `Stepwise Refinement = Niklaus Wirth + 하향식 + 단계별 구체화`

---

### 6. 정보 은닉(Information Hiding)
- **Parnas**가 제안
- 한 모듈 내부에 포함된 정보가 다른 모듈에서 **접근하거나 변경되지 못하도록 감추는 기법**
- 각 모듈의 내부 절차와 자료를 숨겨 다른 모듈이 접근하지 못하도록 함
- 필요한 정보만 **인터페이스를 통해 전달**
- 정보 은닉을 통해
  - 수정
  - 시험
  - 유지보수

  가 쉬워짐
- 모듈 변경 시 다른 모듈에 미치는 영향을 최소화

> ⭐ `정보 은닉 = Parnas + 내부 정보 숨김 + Interface로 필요한 정보만 공개`

---

### 7. 소프트웨어 아키텍처의 품질 속성

#### 시스템 측면

| 품질 속성 | 핵심 |
|---|---|
| **성능** | 사용자의 요청과 이벤트를 처리하고 응답하는 시간 |
| **보안** | 허용되지 않은 접근을 막고 허용된 접근만 제공 |
| **가용성** | 장애 없이 정상적으로 서비스를 사용할 수 있는 정도 |
| **기능성** | 사용자가 요구한 기능을 만족스럽게 수행하는 정도 |
| **사용성** | 사용자가 소프트웨어를 쉽게 이해하고 사용할 수 있는 정도 |
| **변경 용이성** | 소프트웨어를 얼마나 쉽게 수정할 수 있는지 |
| **확장성** | 시스템의 용량·처리 능력을 확장할 수 있는 정도 |
| **기타** | 테스트 용이성, 배치성, 안정성 등 |

#### 비즈니스 측면
- **시장 적시성** - 적절한 시점에 제품을 출시할 수 있는가
- **비용과 혜택** - 개발 비용과 얻을 수 있는 효과
- **예상 시스템 수명** - 시스템을 얼마나 오랫동안 사용할 것인가
- **목표 시장** - 어떤 사용자를 대상으로 하는가
- **공개 일정** - 제품 출시 및 업그레이드 일정

#### 아키텍처 측면
- **개념적 무결성** - 전체 시스템이 일관된 하나의 구조를 유지
- **정확성·완전성** - 요구사항과 기능이 정확하고 완전하게 반영
- **구축 가능성** - 실제로 구현 가능한 구조인지
- 기타 품질 속성

> ⭐ 품질 속성은 `시스템 / 비즈니스 / 아키텍처` 측면으로 구분

---

### 8. 소프트웨어 아키텍처의 설계 과정

```text
설계 목표 설정
→ 시스템 타입 결정
→ 아키텍처 패턴 적용
→ 서브시스템 구체화
→ 검토
```

#### ① 설계 목표 설정
- 시스템의 개발 방향을 명확하게 정의
- 설계에 영향을 주는 비즈니스·기술·품질 요구사항 등을 분석

#### ② 시스템 타입 결정
- 시스템과 서브시스템의 타입을 결정
- 설계 목표와 함께 고려하여 아키텍처 패턴을 선택

#### ③ 아키텍처 패턴 적용
- 아키텍처 패턴을 참고하여 시스템의 표준 아키텍처 설계

#### ④ 서브시스템 구체화
- 서브시스템의 기능 및 서브시스템 간 상호작용을 위한 동작·인터페이스 정의

#### ⑤ 검토
- 아키텍처 설계 목표에 부합하는지
- 요구사항이 잘 반영되었는지
- 설계 원리를 만족하는지 검토

> ⭐ 설계 과정 → `목·타·패·서·검`

## SECTION 017. 아키텍처 패턴

### 1. 아키텍처 패턴(Pattern)의 개요
- **아키텍처 패턴** - 아키텍처를 설계할 때 참조할 수 있는 **전형적인 해결 방식 또는 예제**
- 소프트웨어 시스템의 구조를 구성하기 위한 **기본적인 윤곽**
- 서브시스템과 각 구성 요소 간의 **관계**를 설명
- 아키텍처 스타일 또는 표준 아키텍처라고도 함

#### 아키텍처 패턴의 장점
- 검증된 구조를 사용하여 개발 시간 단축
- 고품질 소프트웨어 생산 가능
- 안정적인 개발 가능
- 시스템 구조를 이해하기 쉬워 개발에 참여하지 않은 사람도 유지보수 가능
- 시스템 특성을 개발 전에 예측 가능
- 공통 언어처럼 사용되어 개발자 간 의사소통이 쉬움

> ⭐ `Architecture Pattern = 검증된 시스템 구조의 재사용`

---

### 2. 레이어 패턴(Layers Pattern)
- 시스템을 여러 **계층(Layer)**으로 구분하여 구성
- 각 계층은 하위 계층의 서비스를 사용하고 상위 계층에 서비스를 제공
- 서로 마주보는 두 계층 사이에서만 상호작용
- 특정 계층 변경 시 인접 계층에만 영향
- 대표 예 → **OSI 7계층**

> ⭐ `Layers = 계층별 분리 / 인접 계층끼리 상호작용`

---

### 3. 클라이언트-서버 패턴(Client-Server Pattern)
- 하나의 서버와 다수의 클라이언트로 구성
- **클라이언트** - 서버에 서비스를 요청
- **서버** - 클라이언트 요청을 처리하여 서비스 제공
- 서버는 항상 대기 상태
- 클라이언트와 서버는 요청·응답 관계
- 일반적으로 서버는 독립적으로 존재

> ⭐ `Client = 요청 / Server = 응답·서비스 제공`

---

### 4. 파이프-필터 패턴(Pipe-Filter Pattern)
- 데이터 스트림을 생성하고 처리하는 시스템에서 사용
- 각 처리 단계 → **Filter**
- 필터 사이의 데이터 이동 통로 → **Pipe**
- 필터를 재배치하여 다양한 파이프라인 구성 가능
- 데이터 변환·버퍼링·동기화 등에 적합
- 대표 예 → **UNIX Shell**

```text
Source → Filter1 → Filter2 → ... → Sink
```

> ⭐ `Pipe = 데이터 이동 / Filter = 데이터 처리`

---

### 5. 모델-뷰-컨트롤러 패턴(MVC Pattern)

| 요소 | 역할 |
|---|---|
| **Model** | 데이터와 핵심 기능 관리 |
| **View** | 사용자에게 정보 표시 |
| **Controller** | 사용자 입력을 받아 Model에 전달하고 View를 제어 |

- 각 요소는 서로 분리되어 있어 독립적인 개발 가능
- 여러 개의 View를 만들 수 있어 하나의 Model을 다양한 화면에서 표현 가능
- 대화형 애플리케이션에 적합

> ⭐ `MVC = Model(데이터) / View(화면) / Controller(제어)`

---

### 6. 기타 아키텍처 패턴

| 패턴 | 핵심 |
|---|---|
| **Master-Slave** | Master가 동일한 작업을 수행하는 Slave에게 작업을 분배하고 결과를 종합 |
| **Broker** | 분리된 컴포넌트 사이의 요청·응답을 **Broker가 중재** |
| **Peer-to-Peer** | 각 Peer가 **Client와 Server 역할을 모두 수행** |
| **Event-Bus** | Source가 Event를 특정 Channel에 발행하고 Listener가 구독 |
| **Blackboard** | 여러 컴포넌트가 **공유 데이터 저장소(Blackboard)**를 참조하여 문제 해결 |
| **Interpreter** | 특정 언어로 작성된 프로그램을 해석하기 위한 아키텍처 / 문법·해석기 사용 |

#### Event-Bus의 주요 요소
- **Source** - 메시지 발행
- **Listener** - 메시지 수신
- **Channel** - 메시지 통로
- **Bus** - 메시지 관리

> ⭐ `Broker = 중재자`  
> ⭐ `P2P = 모두 Client + Server`  
> ⭐ `Blackboard = 공유 저장소`

## SECTION 018. 객체지향(Object-Oriented)

### 1. 객체지향의 개요
- 현실 세계의 개체(Entity)를 기계의 부품처럼 하나의 **객체(Object)**로 만들어
  - 객체들을 조립하여 소프트웨어를 개발하는 방법
- 구조적 기법의 문제점을 해결하기 위해 등장
- 소프트웨어 재사용 및 확장이 쉬움
- 유지보수가 쉬움
- 복잡한 구조를 단계적·계층적으로 표현
- 멀티미디어 데이터와 병렬 처리 지원에 적합
- 주요 구성 요소
  - 객체
  - 클래스
  - 메시지
- 주요 특징
  - 캡슐화
  - 상속
  - 다형성
  - 연관성

> ⭐ `객체지향 = 객체 + 클래스 + 메시지`  
> ⭐ 특징 = `캡·상·다·연`

---

### 2. 객체(Object)
- **데이터 + 데이터를 처리하는 함수**를 하나로 묶은 소프트웨어 모듈

#### 객체의 구성
- **데이터**
  - 객체가 가지고 있는 정보
  - 속성(Attribute), 상태, 변수, 자료 구조 등
- **함수**
  - 객체가 수행하는 기능
  - 메소드(Method), 행위(Behavior), 연산(Operation), 서비스(Service) 등

#### 객체의 특징
- 객체는 **독립적인 이름**을 가짐
- 객체는 일정한 **상태(State)**를 가짐
- 객체의 상태는 시간에 따라 변할 수 있음
- 객체와 객체는 **상호 연관 관계**를 가짐
- 객체는 행위를 수행할 수 있음
- 객체는 다른 객체와 **메시지(Message)**를 주고받음

> ⭐ `Object = Data + Method`  
> ⭐ 객체 간 상호작용 = **Message**

---

### 3. 클래스(Class)
- **공통된 속성과 연산을 갖는 객체의 집합**
- 객체의 일반적인 유형(Type)
- 객체들이 갖는 속성과 연산을 정의한 **틀**
- 클래스에 의해 실제 객체가 만들어지는 과정 → **인스턴스화(Instantiation)**
- 실제 생성된 객체 → **인스턴스(Instance)**
- 상위 클래스 → **Super Class**
- 하위 클래스 → **Sub Class**

> ⭐ `Class = 객체를 만드는 틀`  
> ⭐ `Instantiation → Instance 생성`

---

### 4. 캡슐화(Encapsulation)
- 데이터와 데이터를 처리하는 함수를 하나로 묶는 것
- 외부에서는 인터페이스를 통해서만 접근하도록 함
- 객체 내부 정보와 구현을 숨겨 **정보 은닉** 가능

#### 장점
- 외부 모듈의 변경으로 인한 부작용 감소
- 재사용성 향상
- 인터페이스가 단순해짐
- 객체 간 결합도가 낮아짐

> ⭐ `Encapsulation = Data + Method 묶기 + 내부 정보 숨기기`

---

### 5. 상속(Inheritance)
- 이미 정의된 상위 클래스의 모든 속성과 연산을 **하위 클래스가 물려받는 것**
- 하위 클래스는 상위 클래스의 기능을 재사용하거나 새로운 기능 추가 가능
- 소프트웨어 재사용을 높임
- 여러 상위 클래스에서 상속받는 것 → **다중 상속(Multiple Inheritance)**

> ⭐ `Inheritance = 상위 클래스의 속성·연산을 하위 클래스가 재사용`

---

### 6. 다형성(Polymorphism)
- 하나의 메시지에 대해 **각 객체가 서로 다른 방법으로 응답할 수 있는 능력**
- 같은 메소드 이름을 사용하면서도 상황이나 객체에 따라 다른 기능 수행

#### 오버로딩(Overloading)
- 같은 클래스 안에서 **같은 메소드 이름**을 사용하지만
  - 매개변수 개수
  - 매개변수 타입

  등을 다르게 정의

#### 오버라이딩(Overriding)
- 상위 클래스에서 정의한 메소드를 하위 클래스에서 **재정의**

> ⭐ `Overloading = 같은 이름, 매개변수 다름`  
> ⭐ `Overriding = 상위 메소드를 하위에서 재정의`

---

### 7. 연관성(Relationship)
- 두 개 이상의 객체가 서로 관련되어 있음을 의미

| 관계 | 영어 | 의미 |
|---|---|---|
| **연관화** | is member of | 두 객체가 서로 관련됨 |
| **분류화** | is instance of | 객체가 클래스의 인스턴스임 |
| **집단화** | is part of | 한 객체가 다른 객체의 일부 |
| **일반화** | Generalization | 공통 성질을 상위 객체로 정의 |
| **특수화** | Specialization | 상위 객체를 구체화하여 하위 객체 구성 |

> ⭐ 객체 관계 → `연관 / 분류 / 집단 / 일반화 / 특수화`

---

## SECTION 019. 객체지향 분석 및 설계

### 1. 객체지향 분석(OOA)의 개념
- 사용자의 요구사항을 분석하여
  - 관련된 객체
  - 속성
  - 연산
  - 관계

  등을 정의하는 과정
- 객체를 중심으로 모델링
- 객체와 클래스의 구조적·동적 특성을 분석

---

### 2. 객체지향 분석 방법론

| 방법론 | 핵심 |
|---|---|
| **Rumbaugh** | 객체 모델링 → 동적 모델링 → 기능 모델링 |
| **Booch** | 미시적(Micro)·거시적(Macro) 개발 프로세스 사용 / 클래스와 객체를 분석·식별 |
| **Jacobson** | **Use Case**를 강조하여 분석 |
| **Coad-Yourdon** | E-R 다이어그램을 사용하여 객체의 행위를 모델링 |
| **Wirfs-Brock** | 분석과 설계의 구분이 없고 고객 명세서를 평가하여 설계 작업까지 연속 수행 |

> ⭐ `Rumbaugh = 객체·동적·기능`  
> ⭐ `Booch = 미시/거시`  
> ⭐ `Jacobson = Use Case`  
> ⭐ `Coad-Yourdon = E-R`  
> ⭐ `Wirfs-Brock = 분석·설계 구분 X`

---

### 3. 럼바우(Rumbaugh)의 분석 기법
- 모든 소프트웨어 구성 요소를 그래픽 표기법을 이용하여 모델링
- **객체 모델링 기법(Object Modeling Technique)**이라고도 함

#### 수행 순서
```text
객체 모델링
→ 동적 모델링
→ 기능 모델링
```

| 모델링 | 핵심 |
|---|---|
| **객체 모델링(Object Modeling)** | 객체와 클래스의 관계를 표현 / **정보 모델링**이라고도 함 |
| **동적 모델링(Dynamic Modeling)** | 시간의 흐름에 따른 객체 상태 변화·상호작용 표현 / **상태 다이어그램** 활용 |
| **기능 모델링(Functional Modeling)** | 자료 흐름을 중심으로 처리 과정 표현 / **DFD** 활용 |

> ⭐ `럼바우 = 객 → 동 → 기`  
> ⭐ `객체 = 정보 / 동적 = 상태 / 기능 = DFD`

---

### 4. 객체지향 설계 원칙(SOLID)

| 원칙 | 핵심 |
|---|---|
| **단일 책임 원칙(SRP)** | 객체는 **단 하나의 책임만** 가져야 함 |
| **개방-폐쇄 원칙(OCP)** | 기존 코드는 변경하지 않고 **확장할 수 있어야 함** |
| **리스코프 치환 원칙(LSP)** | 자식 클래스는 부모 클래스를 **대체할 수 있어야 함** |
| **인터페이스 분리 원칙(ISP)** | 사용하지 않는 인터페이스에 의존하지 않도록 **작은 인터페이스로 분리** |
| **의존 역전 원칙(DIP)** | 구체적인 클래스보다 **추상화에 의존**해야 함 |

> ⭐ SOLID → `단·개·리·인·의`  
> ⭐ `SRP 1책임 / OCP 확장 O 수정 X / LSP 자식=부모 대체 / ISP 작은 Interface / DIP 추상화 의존`

---

## SECTION 020. 모듈

### 1. 모듈(Module)의 개요
- 프로그램을 효율적으로 관리할 수 있도록 기능 단위로 분해한 것
- 서브루틴, 서브시스템, 함수, 프로시저, 객체 등
- 독립적인 기능을 수행
- 재사용 가능
- 여러 모듈을 조합하여 하나의 프로그램을 구성

#### 좋은 모듈
- **결합도(Coupling)는 낮게**
- **응집도(Cohesion)는 높게**
- 모듈의 크기는 가능한 작게
- 독립성이 높아야 함

> ⭐ `좋은 모듈 = 결합도 ↓ + 응집도 ↑`

---

### 2. 결합도(Coupling)
- 모듈과 모듈 사이의 **상호 의존 정도**
- 결합도가 낮을수록 독립성이 높아지고 좋은 설계

#### 결합도 약 → 강
```text
자료 결합도
→ 스탬프 결합도
→ 제어 결합도
→ 외부 결합도
→ 공통 결합도
→ 내용 결합도
```

| 결합도 | 핵심 |
|---|---|
| **자료 결합도(Data Coupling)** | 필요한 **자료 요소만 매개변수**로 전달 |
| **스탬프 결합도(Stamp Coupling)** | 배열·레코드 등 **자료 구조 전체**를 전달 |
| **제어 결합도(Control Coupling)** | 다른 모듈의 내부 논리 흐름을 제어하기 위한 **제어 요소** 전달 |
| **외부 결합도(External Coupling)** | 외부의 다른 모듈에서 선언된 데이터나 통신 프로토콜 등을 공유 |
| **공통 결합도(Common Coupling)** | 여러 모듈이 **공통 데이터 영역**을 사용 |
| **내용 결합도(Content Coupling)** | 한 모듈이 다른 모듈의 **내부 기능·자료를 직접 참조·수정** |

> ⭐ 결합도는 `자·스·제·외·공·내` 순으로 강해짐  
> ⭐ **자료 결합도 가장 좋음 / 내용 결합도 가장 나쁨**

---

### 3. 응집도(Cohesion)
- 모듈 내부의 구성 요소들이 서로 **얼마나 밀접하게 관련되어 있는지**
- 응집도가 높을수록 독립성이 높은 좋은 모듈

#### 응집도 약 → 강
```text
우연적
→ 논리적
→ 시간적
→ 절차적
→ 통신적
→ 순차적
→ 기능적
```

| 응집도 | 핵심 |
|---|---|
| **우연적(Coincidental)** | 서로 관련 없는 요소들이 하나의 모듈에 모임 |
| **논리적(Logical)** | 유사한 성격의 기능들을 하나의 모듈로 구성 |
| **시간적(Temporal)** | 특정 시간에 함께 처리되는 기능들을 모음 |
| **절차적(Procedural)** | 정해진 순서에 따라 수행되는 기능들이 모임 |
| **통신적(Communication)** | 동일한 입력·출력을 사용하는 기능들이 모임 |
| **순차적(Sequential)** | 한 기능의 출력이 다음 기능의 입력이 됨 |
| **기능적(Functional)** | 모듈 내부 모든 기능이 **하나의 목적을 수행** |

> ⭐ 응집도 → `우·논·시·절·통·순·기` 순으로 강해짐  
> ⭐ **기능적 응집도 가장 좋음**

---

### 4. 팬인(Fan-In) / 팬아웃(Fan-Out)

#### Fan-In
- 어떤 모듈을 **호출하는 모듈의 수**
- Fan-In이 높다
  - 재사용 측면에서는 좋음
  - 해당 모듈의 장애가 여러 모듈에 영향을 줄 수 있어 집중 관리 필요

#### Fan-Out
- 어떤 모듈이 **호출하는 다른 모듈의 수**
- Fan-Out이 높다
  - 불필요하게 많은 모듈을 제어하는지 검토
  - 복잡성이 증가할 수 있음

> ⭐ `Fan-In = 나를 호출하는 수`  
> ⭐ `Fan-Out = 내가 호출하는 수`

---

### 5. N-S 차트(Nassi-Schneiderman Chart)
- 논리의 기술에 중점을 둔 **도형식 표현 방법**
- 박스 다이어그램, Chapin Chart라고도 함
- 순차, 선택, 반복 등의 제어 논리 구조 표현
- **GOTO나 화살표를 사용하지 않음**
- 조건이 복합되어 있는 경우 처리를 시각적으로 명확하게 표현
- 선택과 반복 구조를 시각적으로 이해하기 쉬움
- 이해하기 쉽고 코드 변환이 용이
- 읽기는 쉽지만 작성하기는 어려울 수 있음

> ⭐ `N-S Chart = 구조적 제어 논리 / GOTO X / 화살표 X`

---

## SECTION 021. 공통 모듈

### 1. 공통 모듈의 개요
- 여러 프로그램에서 **공통적으로 사용할 수 있는 모듈**
- 자주 사용하는 계산·기능을 하나의 모듈로 만들어 재사용 가능
- 공통 모듈의 명세는 다른 개발자가 이해할 수 있도록 **명확하게 작성**

#### 공통 모듈 명세 원칙

| 원칙 | 핵심 |
|---|---|
| **정확성(Correctness)** | 시스템 구현 시 해당 기능이 필요하다는 것을 알 수 있도록 정확히 작성 |
| **명확성(Clarity)** | 해당 기능을 일관되게 이해하고 하나로 해석할 수 있도록 작성 |
| **완전성(Completeness)** | 시스템 구현에 필요한 모든 내용을 빠짐없이 작성 |
| **일관성(Consistency)** | 공통 기능 간 상호 충돌이 발생하지 않도록 작성 |
| **추적성(Traceability)** | 기능에 대한 요구사항의 출처와 관련 시스템 간 관계를 파악할 수 있도록 작성 |

> ⭐ 공통 모듈 명세 → `정·명·완·일·추`

---

### 2. 재사용(Reuse)
- 이미 개발된 기능을 새로운 시스템 개발에 다시 사용
- 개발 시간과 비용 절감
- 재사용 가능한 기능을 중심으로 모듈을 구성해야 함
- 재사용성을 높이기 위해
  - 독립성 높은 모듈
  - 범용적인 기능
  - 명확한 인터페이스

  로 설계

#### 재사용 규모에 따른 분류

| 재사용 규모 | 핵심 |
|---|---|
| **함수와 객체** | 클래스나 메소드 등 작은 단위의 소프트웨어 재사용 |
| **컴포넌트** | 독립적인 업무·기능을 수행하는 실행 코드 기반으로 재사용 / 인터페이스를 통해 통신 |
| **애플리케이션** | 공통 기능을 제공하는 애플리케이션을 공유하여 재사용 |

> ⭐ `재사용 규모 = 함수·객체 → 컴포넌트 → 애플리케이션`

---

### 3. 효과적인 공통 모듈 설계 방안
- **결합도는 낮추고 응집도는 높여** 독립성과 재사용성을 높임
- 모듈 간 상호 의존도를 줄여 다른 모듈 변경의 영향을 최소화
- 복잡도와 중복성을 줄이고 일관성 유지
- 모듈 기능은 예측 가능하고 명확해야 함
- **유지보수가 쉬워야 함**
- 모듈 크기는 너무 크지 않고 이해하기 쉬운 수준으로 구성
- 하나의 입구와 하나의 출구를 갖도록 설계
- 인터페이스를 통해 결합도를 낮춤
- 모듈 이름으로 기능을 이해할 수 있도록 명확하게 작성
- 효과적인 재사용을 위해 자주 사용하는 기능은 공통 모듈로 구성

> ⭐ `공통 모듈 = 독립성↑ / 재사용성↑ / 결합도↓ / 응집도↑`

---

## SECTION 022. 코드

### 1. 코드(Code)의 개요
- 컴퓨터를 이용하여 자료를 처리하는 과정에서
  - 분류
  - 조합
  - 집계

  등을 쉽게 하고 특정 자료의 추출을 쉽게 하기 위해 사용하는 **기호**
- 일정한 규칙에 따라 작성
- 기계 처리에 적합해야 함
- 코드의 주요 기능
  - 식별
  - 분류
  - 배열
  - 표준화
  - 간소화

#### 코드의 기능

| 기능 | 핵심 |
|---|---|
| **식별 기능** | 데이터 간 성격에 따라 구분 가능 |
| **분류 기능** | 특정 기준에 따라 그룹화 |
| **배열 기능** | 의미를 부여하여 나열 가능 |
| **표준화 기능** | 다양한 데이터를 일정한 기준에 맞게 표현 |
| **간소화 기능** | 복잡한 데이터를 간단하게 표현 |

> ⭐ 코드 기능 → `식·분·배·표·간`

---

### 2. 코드의 종류

| 코드 | 핵심 | 예시 |
|---|---|---|
| **순차 코드(Sequence Code)** | 일정 기준에 따라 **일련번호를 순서대로 부여** | 1, 2, 3, 4 ... |
| **블록 코드(Block Code)** | 공통성이 있는 것끼리 **블록으로 구분**하고 블록 내 일련번호 부여 | 100~110, 200~210 |
| **10진 코드(Decimal Code)** | 10진수 체계를 이용해 대분류→중분류→소분류 | 도서 분류 코드 |
| **그룹 분류 코드(Group Classification Code)** | 대분류·중분류·소분류 등 **계층별 숫자** 부여 | 1-01-001 |
| **연상 코드(Mnemonic Code)** | 대상 명칭이나 약호와 관계있는 문자·숫자를 사용 | TV-40 |
| **표의 숫자 코드(Significant Digit Code)** | 물리적 수치인 길이·넓이·부피 등을 코드에 직접 표현 | 120-720-1500 |
| **합성 코드(Combined Code)** | 두 개 이상의 코드 방식을 조합 | 연상 코드 + 순차 코드 |

> ⭐ `순·블·십·그·연·표·합`

---

### 3. 코드 부여 체계
- 코드 부여 전 **코드의 사용 목적과 적용 범위**를 명확히 정의
- 각 단위 시스템의 고유한 코드와 개체를 표현하도록 설계
- 코드만으로도 대상을 쉽게 식별할 수 있도록 함
- 코드 설계 담당자는 코드의
  - 자릿수
  - 구조
  - 구분자
  - 사용 범위

  등을 명확히 정의

#### 예시
```text
PJC-COM-003
```
- `PJC` → 시스템·업무 구분
- `COM` → 세부 분류
- `003` → 순차 번호

> ⭐ 좋은 코드 = `간단 + 유일 + 식별 쉬움 + 확장 가능`

## SECTION 023. 디자인 패턴

### 1. 디자인 패턴(Design Pattern)의 개요
- 모듈의 세분화된 역할이나 모듈 간 인터페이스와 같은 코드를 설계할 때 **참조할 수 있는 전형적인 해결 방식 또는 예제**
- 한 패턴을 변형하거나 여러 패턴을 조합하여 사용 가능
- 문제 해결을 위한 검증된 설계를 재사용하여 개발 시간 단축
- 바퀴를 다시 발명하지 말라(**Don't reinvent the wheel**)는 개념과 관련
- 디자인 패턴은 문제와 해결 방법을 구조화하여 재사용할 수 있게 함
- **GoF(Gang of Four)**가 대표적인 23개의 디자인 패턴을 정리
- 생성 / 구조 / 행위 패턴으로 분류

> ⭐ `Design Pattern = 반복되는 설계 문제의 검증된 해결 방법`  
> ⭐ `GoF = 23개 패턴`

---

### 2. 디자인 패턴 사용의 장·단점

#### 장점
- 범용적인 코딩 스타일 적용
- 구조 파악이 쉬움
- 객체지향 설계와 구현의 생산성 향상
- 검증된 구조를 사용하여 품질 향상
- 개발자 간 의사소통이 쉬움
- 설계 변경 요청에 유연하게 대응
- 개발 시간 단축

#### 단점
- 객체지향 설계·구현 위주로 사용
- 초기 투자 비용과 시간이 필요
- 패턴을 이해하고 적절하게 적용할 경험이 필요

> ⭐ `디자인 패턴 = 재사용·유지보수·의사소통 ↑`

---

### 3. 생성 패턴(Creational Pattern)
- 객체의 **생성 과정**을 캡슐화하여 시스템이 특정 클래스에 의존하지 않도록 함
- 객체 생성·조합 방법을 독립적으로 관리

| 패턴 | 핵심 |
|---|---|
| **Abstract Factory** | 구체적 클래스를 지정하지 않고 **서로 연관된 객체들의 집합을 생성** |
| **Builder** | 객체의 생성 과정과 표현 방법을 분리하여 **동일한 생성 절차로 다양한 결과** 생성 |
| **Factory Method** | 객체 생성을 서브클래스가 결정 / **Virtual Constructor** 패턴 |
| **Prototype** | 원본 객체를 **복제(Clone)**하여 새로운 객체 생성 |
| **Singleton** | 클래스의 인스턴스가 **하나만 존재**하도록 보장 |

> ⭐ 생성 패턴 → `추·빌·팩·프·싱`

---

### 4. 구조 패턴(Structural Pattern)
- 클래스나 객체를 조합하여 **더 큰 구조를 만드는 방법**
- 서로 독립적으로 개발된 클래스·라이브러리를 결합

| 패턴 | 핵심 |
|---|---|
| **Adapter** | 호환되지 않는 클래스의 **인터페이스를 변환**하여 함께 사용 |
| **Bridge** | 구현부에서 추상층을 분리하여 **독립적으로 확장** |
| **Composite** | 객체를 **트리 구조**로 구성하여 부분-전체 계층 표현 / 단일 객체와 복합 객체 동일하게 처리 |
| **Decorator** | 객체에 **동적으로 새로운 책임·기능을 추가** |
| **Facade** | 복잡한 서브시스템에 대해 **단순하고 통합된 인터페이스** 제공 |
| **Flyweight** | 여러 객체가 공통 데이터를 공유하여 **메모리 사용량 감소** |
| **Proxy** | 실제 객체를 대신하는 **대리 객체**를 두어 접근 제어 |

> ⭐ 구조 패턴 → `어·브·컴·데·퍼·플·프`

---

### 5. 행위 패턴(Behavioral Pattern)
- 클래스나 객체들이 서로 상호작용하는 **방법과 책임 분배**를 정의
- 객체 간 결합도를 최소화하는 데 중점

| 패턴 | 핵심 |
|---|---|
| **Chain of Responsibility** | 요청을 처리할 객체를 직접 지정하지 않고 **처리 객체를 연결한 Chain을 따라 전달** |
| **Command** | 요청을 **객체로 캡슐화**하여 매개변수화·취소·로그 등을 지원 |
| **Interpreter** | 언어의 문법 표현과 **해석 방법**을 정의 |
| **Iterator** | 내부 구조를 노출하지 않고 집합 객체의 요소를 **순차적으로 접근** |
| **Mediator** | 객체 간 복잡한 상호작용을 **중재자 객체**가 처리 |
| **Memento** | 객체의 내부 상태를 저장하여 **이전 상태로 복원** |
| **Observer** | 한 객체의 상태가 변하면 의존 객체들에게 **자동 통지** |
| **State** | 객체의 **상태에 따라 행동이 변경** |
| **Strategy** | 동일 계열 알고리즘을 캡슐화하여 **상호 교환 가능**하게 함 |
| **Template Method** | 상위 클래스에서 알고리즘의 **골격을 정의**하고 일부 단계를 하위 클래스에서 구현 |
| **Visitor** | 객체 구조는 변경하지 않고 **새로운 연산을 별도 객체로 추가** |

> ⭐ 행위 패턴 → `책·커·인·이·미·메·옵·스·스·템·비`
