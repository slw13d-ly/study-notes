# 02. 통합 구현

## SECTION 034. 단위 모듈 구현

### 1. 단위 모듈(Unit Module)의 개요
- **단위 모듈(Unit Module)** - 소프트웨어 구현에 필요한 여러 동작 중 **한 가지 동작을 수행하는 기능**을 모듈로 구현한 것
- 단위 모듈로 구현되는 하나의 기능 → **단위 기능**
- 단위 모듈은 사용자가 다른 모듈로부터 값을 전달받아 시작되는 **작은 프로그램**이라고도 함
- 두 개의 단위 모듈이 합쳐져 **하나의 기능**을 구현할 수도 있음
- 단위 모듈의 독립성
  - **결합도(Coupling) ↓**
  - **응집도(Cohesion) ↑**
- 독립적인 **컴파일**이 가능
- 다른 모듈에 **호출되거나 삽입**될 수 있음

#### 단위 모듈 구현 순서
```text
단위 기능 명세서 작성
→ 입·출력 기능 구현
→ 알고리즘 구현
```

> ⭐ `단위 모듈 = 하나의 기능을 수행하는 작은 모듈`  
> ⭐ `독립성 ↑ = 결합도 ↓ + 응집도 ↑`  
> ⭐ 구현 순서 → `명세 → 입출력 → 알고리즘`


### 2. 단위 기능 명세서 작성
- 설계 과정에서 작성한 **기능 및 코드 명세서**, 설계 지침 등을 이용하여 **단위 기능을 명세화**하는 단계
- 복잡한 시스템을 단순하게 구현하기 위한 **추상화 작업**이 필요
- 대형 시스템을 분해하여
  - **단위 기능별로 구분**
  - 각 기능을 **계층적으로 구성**

  하는 **구조화 과정**을 거침
- 모듈이 독립적으로 운용되고 한 모듈 내부의 정보가 다른 모듈에 영향을 주지 않도록 **정보 은닉(Information Hiding)**의 원리를 고려

> ⭐ `단위 기능 명세 = 추상화 + 구조화 + 정보 은닉`


### 3. 입·출력 기능 구현
- 단위 기능 명세서에서 정의한
  - **데이터 형식**
  - **연동**

  에 따라 입·출력 기능을 구현
- 단위 모듈 간 연동 또는 외부와의 통신을 위한 **입·출력 데이터**를 구현

#### 구현 시 고려사항
- 사용자 인터페이스가
  - **CLI(Command Line Interface)**
  - **GUI(Graphical User Interface)**

  중 어떤 방식인지 고려
- 입·출력 기능 구현 시 네트워크나 외부 장치와의 입·출력을 위해 필요한 경우 **Open Source API**를 이용하여 간단하게 구현 가능

> ⭐ `입·출력 기능 = 명세서의 데이터 형식·연동 방식 구현`  
> ⭐ `사용자 인터페이스 = CLI / GUI`


### 4. IPC(Inter-Process Communication)
- **IPC** - 운영체제에서 **프로세스 간 통신을 구현하기 위해 사용하는 대표적인 프로그래밍 인터페이스**
- 복수의 프로세스를 수행하여 이뤄지는 **프로세스 간 통신까지 구현 가능**

#### IPC의 대표적인 방법

| 방식 | 핵심 |
|---|---|
| **Shared Memory** | 다수의 프로세스가 공유 가능한 **메모리**를 구성하여 프로세스 간 통신 수행 |
| **Socket** | 네트워크 소켓을 이용하여 **네트워크를 경유하는 프로세스 간 통신** 수행 |
| **Semaphores** | 공유 자원에 대한 **접근 제어**를 통해 프로세스 간 통신 수행 |
| **Pipes & Named Pipes** | 선입선출 형태의 **Pipe 메모리**를 여러 프로세스가 공유하여 통신 |
| **Message Queuing** | 메시지가 발생하면 이를 전달하는 형태로 프로세스 간 통신 수행 |

#### Pipes & Named Pipes
- `Pipe`라고 하는 **FIFO 형태의 메모리**를 이용
- 여러 프로세스가 공유하여 통신
- 하나의 프로세스가 Pipe를 이용 중이면 다른 프로세스는 접근할 수 없음

> ⭐ `IPC = 프로세스 간 통신`  
> ⭐ `Shared Memory / Socket / Semaphore / Pipe / Message Queue`


### 5. 알고리즘 구현
- 입·출력 데이터를 바탕으로 **단위 기능별 요구사항을 구현**하는 단계
- 구현된 단위 기능들이 **사용자의 요구사항과 일치하는지 확인하는 과정**이 필요
- 구현되는 모듈은 기능에 따라 여러 종류로 구분

#### 모듈 종류

| 모듈 | 핵심 |
|---|---|
| **디바이스 드라이버 모듈** | 하드웨어 주변 장치의 동작을 구현 |
| **네트워크 모듈** | 네트워크 장비 및 데이터 통신을 위한 기능 구현 |
| **파일 모듈** | 컴퓨터 내부의 데이터 구조 영역에 접근하는 방법 구현 |
| **메모리 모듈** | 파일을 프로세스의 가상 메모리에 매핑·해제하는 방법 및 프로세스 사이 통신 기능 구현 |
| **프로세스 모듈** | 하나의 프로세스 안에서 다른 프로세스를 생성하는 방법 구현 |

> ⭐ 모듈 종류 → `디바이스 / 네트워크 / 파일 / 메모리 / 프로세스`

## SECTION 035. 단위 모듈 테스트

### 1. 단위 모듈 테스트의 개요
- **단위 모듈 테스트** - 프로그램의 단위 기능을 구현하는 모듈이 **정해진 기능을 정확히 수행하는지 검증**하는 것
- **단위 테스트(Unit Test)**라고도 함
- 테스트 기법
  - **화이트박스 테스트**
  - **블랙박스 테스트**
- 단위 모듈 테스트를 수행하기 위해서는 모듈을 **독립적으로 실행할 수 있는 환경과 테스트 데이터**가 준비되어야 함
- 단위 모듈 자체의 오류는 쉽게 발견하고 수정할 수 있음
- 하지만 단위 모듈 테스트의 기준은 **단위 모듈에 대한 코드**이므로 **시스템 수준의 오류는 찾아내기 어려움**

> ⭐ `단위 모듈 테스트 = Unit Test`  
> ⭐ `화이트박스 + 블랙박스`  
> ⭐ `모듈 오류는 찾기 쉽지만 시스템 수준 오류는 찾기 어려움`



### 2. 테스트 케이스(Test Case)
- **테스트 케이스(Test Case)** - 구현된 소프트웨어가 사용자의 요구사항을 정확하게 준수했는지 확인하기 위해 설계된
  - 입력값
  - 실행 조건
  - 기대 결과

  등으로 구성된 **테스트 항목에 대한 명세서**
- 단위 모듈 테스트 전에
  - 입력 데이터
  - 테스트 조건
  - 예상 결과

  등을 **모듈 테스트 케이스**로 작성
- 테스트 케이스 없이 수행하는 직관적인 테스트는 특정 요소의 검증이 누락되거나 불필요한 검증이 반복되어 **오류를 발견하지 못할 수 있음**

> ⭐ `Test Case = 입력 + 조건 + 예상 결과`

### 3. ISO/IEC/IEEE 29119-3 테스트 케이스 구성 요소

| 구성 요소 | 의미 |
|---|---|
| **식별자(Identifier)** | 항목 식별자, 일련번호 |
| **테스트 항목(Test Item)** | 테스트 대상(모듈 또는 기능) |
| **입력 명세(Input Specification)** | 입력 데이터 또는 테스트 조건 |
| **출력 명세(Output Specification)** | 테스트 케이스 수행 시 예상되는 출력 결과 |
| **환경 설정(Environmental Needs)** | 필요한 하드웨어나 소프트웨어 환경 |
| **특수 절차 요구(Special Procedure Requirement)** | 테스트 케이스 수행 시 특별히 요구되는 절차 |
| **의존성 기술(Inter-case Dependencies)** | 테스트 케이스 간의 의존성 |

> ⭐ 테스트 케이스 구성 → `식별자 / 항목 / 입력 / 출력 / 환경 / 특수 절차 / 의존성`


### 4. 테스트 시나리오(Test Scenario)
- **테스트 시나리오** - 여러 개의 테스트 케이스를 적용하는 **순서에 따라 묶은 집합**
- 테스트 케이스를 적용하는 **구체적인 절차를 명세한 문서**

> ⭐ `Test Scenario = 여러 Test Case의 실행 흐름`

### 5. 테스트 프로시저(Test Procedure)
- 테스트 프로시저 - **테스트 케이스의 실행 순서를 명세한 절차**
- **Test Script**라고도 함

> ⭐ `Test Procedure = 실행 순서 / Test Script`


### 6. 테스트 프로세스
- **테스트 프로세스** - 테스트를 위해 수행하는 모든 작업이 테스트의 목적과 조건을 달성할 수 있도록 **도와주는 과정**
- 총 **5단계**

#### ① 계획 및 제어 단계
- 테스트 목표를 달성하기 위한 **계획 수립**
- 테스트가 제대로 진행되도록 **제어**

#### ② 분석 및 설계 단계
- 테스트 목표를 구체화
- **테스트 시나리오와 테스트 케이스 작성**

#### ③ 구현 및 실현 단계
- 효과적인 테스트 수행을 위해 테스트 케이스들을 조합하여 **테스트 프로시저에 명세**
- 모듈의 환경에 적합한 **단위 테스트 도구를 이용하여 테스트 수행**

#### ④ 평가 단계
- 테스트가 계획과 목표에 맞게 수행되었는지 **평가하고 기록**

#### ⑤ 완료 단계
- 이후 테스트의 참고 자료와 증거 자료로 활용할 수 있도록
  - 테스트 수행 과정
  - 산출물

  을 **기록 및 저장**

> ⭐ 테스트 프로세스 → `계획·제어 → 분석·설계 → 구현·실현 → 평가 → 완료`

## SECTION 036. 개발 지원 도구

### 1. 통합 개발 환경(IDE; Integrated Development Environment)
- **통합 개발 환경(IDE)** - 코딩, 디버그, 컴파일, 배포 등 프로그램 개발과 관련된 모든 작업을 **하나의 프로그램에서 처리할 수 있도록 제공하는 소프트웨어적인 개발 환경**
- 기존에는
  - 편집기(Editor)
  - 컴파일러(Compiler)
  - 디버거(Debugger)

  등을 각각 따로 사용했지만, 이를 하나로 묶어 제공
- 통합 개발 환경을 지원하는 도구는 플랫폼, 운영체제, 언어별로 다양하게 존재

> ⭐ `IDE = Editor + Compiler + Debugger + Deployment 등을 통합`


### 2. 대표적인 통합 개발 환경

| 프로그램 | 개발사 | 플랫폼 | 운영체제 | 지원 언어 |
|---|---|---|---|---|
| **Eclipse** | Eclipse Foundation, IBM | 크로스 플랫폼 | Windows, Linux, MacOS 등 | Java, C, C++, PHP, JSP, Python 등 |
| **Visual Studio** | Microsoft | Win32, Win64 | Windows | Basic, C, C++, Python 등 |
| **Xcode** | Apple | Mac, iPhone | MacOS, iOS | C, C++, C#, Java, Python, AppleScript 등 |
| **Android Studio** | Google | Android | Windows, Linux, MacOS | Java, C, C++ |
| **IDEA** | JetBrains(이전 IntelliJ) | 크로스 플랫폼 | Windows, Linux, MacOS | Java, JSP, XML, Go, Kotlin, PHP 등 |

> ⭐ `Eclipse·IDEA = Cross Platform`  
> ⭐ `Visual Studio = Microsoft`  
> ⭐ `Xcode = Apple`  
> ⭐ `Android Studio = Google`

### 3. IDE의 대표적인 기능

| 기능 | 핵심 |
|---|---|
| **코딩(Coding)** | C, Java, Python 등의 프로그래밍 언어로 프로그램 작성 |
| **컴파일(Compile)** | 고급 언어로 작성된 프로그램을 컴퓨터가 이해할 수 있는 저급 언어로 번역 |
| **디버깅(Debugging)** | 소프트웨어나 하드웨어의 오류나 잘못된 동작(Bug)을 찾아 수정 |
| **배포(Deployment)** | 소프트웨어를 최종 사용자에게 전달 |

> ⭐ `IDE 기능 = Coding / Compile / Debugging / Deployment`

### 4. 빌드 도구
- **빌드(Build)** - 소스 코드 파일들을 컴퓨터에서 실행할 수 있는 **제품 소프트웨어로 변환하는 과정 또는 결과물**
- **빌드 도구** - 소스 코드를 실행 가능한 소프트웨어로 변환하는 과정에 필요한
  - 전처리(Preprocessing)
  - 컴파일(Compile)

  등의 작업을 수행하는 소프트웨어
- 대표적인 빌드 도구
  - **Ant**
  - **Maven**
  - **Gradle**

> ⭐ `Build = Source Code → 실행 가능한 Software`


### 5. Ant
- **Apache Software Foundation**에서 개발
- **Java 프로젝트의 공식적인 빌드 도구**로 사용
- **XML 기반 빌드 스크립트** 사용
- 자유도가 높고 유연성이 있어 다양한 빌드 환경에 대응 가능
- 정해진 규칙이나 표준이 없어 개발자가 대부분 직접 정의
- 스크립트의 재사용이 어려움

> ⭐ `Ant = Apache + Java + XML + 자유도 높음`


### 6. Maven
- Ant와 동일하게 **Apache Software Foundation**에서 개발
- **Ant의 대안**으로 개발
- 규칙이나 표준이 존재하여 **예외 사항만 기록**
- 컴파일과 빌드를 동시에 수행 가능
- **의존성(Dependency)**을 설정하여 라이브러리 관리

> ⭐ `Maven = 규칙·표준 + Dependency 관리`


### 7. Gradle
- 기존 **Ant와 Maven을 보완**하여 개발된 빌드 도구
- 한스 도커(Hans Dockter)의 오픈 소스 소프트웨어 그룹에 의해 제작
- **Android Studio의 공식 빌드 도구**
- Maven과 동일하게 **의존성** 활용
- **Groovy 기반 빌드 스크립트** 사용

> ⭐ `Gradle = Ant + Maven 보완`  
> ⭐ `Android Studio 공식 Build Tool`  
> ⭐ `Groovy 기반`


### 8. Ant / Maven / Gradle 비교

| 도구 | 핵심 |
|---|---|
| **Ant** | Apache / Java / XML / 자유도 높음 / 개발자가 직접 정의 |
| **Maven** | Apache / 규칙·표준 존재 / Dependency 관리 |
| **Gradle** | Ant·Maven 보완 / Android Studio 공식 / Groovy / Dependency |

> ⭐ `Ant = XML`  
> ⭐ `Maven = 표준·의존성`  
> ⭐ `Gradle = Groovy·Android`


### 9. 기타 협업 도구
- **협업 도구** - 개발에 참여하는 사람들이 서로 다른 작업 환경에서도 원활하게 프로젝트를 수행할 수 있도록
  - 일정
  - 업무 진행 상황
  - 정보

  등을 공유하는 도구

#### 협업 도구의 종류
