# 03. 제품 소프트웨어 패키징

## SECTION 037. 소프트웨어 패키징

### 1. 소프트웨어 패키징의 개요
- **소프트웨어 패키징(Software Packaging)** - 모듈별로 생성한 실행 파일들을 묶어 **배포용 설치 파일**로 만드는 것
- 개발자가 아니라 **사용자 중심**으로 진행
- 소스 코드는 향후 관리를 고려하여 **모듈화**하여 패키징
- 사용자가 소프트웨어를 쉽게 사용할 수 있도록 **사용 환경을 이해**하고, 다양한 환경에서 실행할 수 있도록 **일반적인 배포 형태**로 패키징

> ⭐ `소프트웨어 패키징 = 실행 파일들을 묶어 배포용 설치 파일 생성`  
> ⭐ `개발자 중심 X → 사용자 중심 O`

### 2. 패키징 시 고려사항
- 사용자의 시스템 환경
  - **운영체제(OS)**
  - **CPU**
  - **메모리**

  등에 필요한 최소 환경을 정의
- 사용자 인터페이스(UI)는 사용자가 눈으로 직접 확인할 수 있도록 **시각적인 자료와 함께 제공**
- 소프트웨어는 단순히 패키징하여 배포하는 것으로 끝나는 것이 아니라, 하드웨어와 함께 관리되는 **Managed Service** 형태를 고려
- 사용자에게 배포되는 소프트웨어는 내부 콘텐츠의 **암호화 및 보안**을 고려
- 다른 여러 콘텐츠 및 단말기 간 **DRM 연동** 고려
- 사용자의 편의성을 위한 **복잡성 및 비효율성 문제** 고려
- 제품 소프트웨어 종류에 적합한 **암호화 알고리즘** 적용

> ⭐ 패키징 고려 → `환경 / UI / Managed Service / 보안 / DRM / 사용자 편의 / 암호화`

### 3. 패키징 작업 순서

```text
기능 식별
→ 모듈화
→ 빌드 진행
→ 사용자 환경 분석
→ 패키징 및 적용 시험
→ 패키징 변경 개선
→ 배포
```

#### ① 기능 식별
- 작성된 코드의 **기능을 확인**

#### ② 모듈화
- 확인된 기능 단위로 코드를 **분류**

#### ③ 빌드 진행
- 모듈 단위별로 **실행 파일 생성**

#### ④ 사용자 환경 분석
- 웹, 모바일, PC 등 소프트웨어가 사용될 환경과
  - 운영체제
  - CPU
  - RAM

  등의 **최소 운영 환경을 정의**

#### ⑤ 패키징 및 적용 시험
- 빌드된 실행 파일들을 정의된 환경에 맞게 내용물에 맞춰 **패키징**
- 정의된 환경과 동일한 환경에서 패키징 결과를 테스트하여
  - 소프트웨어에 대한 **불편 사항**
  - 기능상의 **문제**

  를 확인

#### ⑥ 패키징 변경 개선
- 확인된 불편 사항을 반영하기 위해 **패키징 변경 및 개선**

#### ⑦ 배포
- 배포 수행 시 오류가 발생하면 해당 개발자에게 전달하여 **수정 요청**

> ⭐ 패키징 작업 순서 → `기모빌환패변배`  
> ⭐ `기능 식별 → 모듈화 → 빌드 → 환경 분석 → 시험 → 개선 → 배포`

### 4. 패키징 주기
- 패키징 주기는 소프트웨어 개발 기업에 따라 다름
- 짧은 개발 주기를 반복하는 애자일 기법은 보통 **2~4주 내에서 지정**
- 각 주기가 끝날 때마다 **패키징 수행**

### 5. 패키징 배포 방법
- **온라인 배포**
  - 별도로 마련한 운영 서버에 설치 및 사용 매뉴얼과 함께 배포 파일 등록
  - 고객이 지정된 경로에서 사용할 수 있도록 함
- **오프라인 배포**
  - `CD-ROM`, `DVD`, `USB` 등에 설치 및 사용자 매뉴얼과 함께 배포 파일 제공

## SECTION 038. 디지털 저작권 관리(DRM)

### 1. 저작권의 개요
- **저작권** - 소설, 시, 논문, 강연, 음악, 연극, 무용, 회화, 서예, 건축물, 사진, 영상, 지도, 도표, 컴퓨터 프로그램 저작물 등에 대해 **창작자가 가지는 배타적 독점적 권리**
- 타인의 침해를 받지 않고 저작물을 관리·이용할 수 있도록 보호

### 2. DRM(Digital Rights Management)의 개요
- **디지털 저작권 관리(DRM)** - 저작권자가 배포한 디지털 콘텐츠가 저작권자가 의도한 용도로만 사용되도록
  - 디지털 콘텐츠의 생성
  - 유통
  - 이용

  까지의 전 과정에 걸쳐 **사용되는 디지털 콘텐츠 관리 및 보호 기술**
- 원본 콘텐츠가 아날로그인 경우 디지털로 변환 후 **패키저(Packager)**가 DRM 패키징 수행
- 콘텐츠의 크기가 작은 경우
  - 사용자가 콘텐츠를 요청하는 시점에 **실시간 패키징**
- 콘텐츠의 크기가 큰 경우
  - 미리 **패키징을 수행한 후 배포**
- 패키징 시
  - 콘텐츠에는 **암호화된 저작권자의 전자서명**
  - 저작권자가 설정한 라이선스 정보

  가 포함
- 라이선스 정보는 **클리어링 하우스(Clearing House)**에 등록
- 사용자는 콘텐츠 사용을 위해 클리어링 하우스에 등록된 라이선스를 통해
  - 사용자 인증
  - 사용 권한 확인

  을 수행
- 종량제 방식 적용 가능
  - 실제 사용량을 측정하여 사용한 만큼 요금 부과

> ⭐ `DRM = 디지털 콘텐츠 생성 → 유통 → 이용 전 과정의 저작권 보호`  
> ⭐ `라이선스 = Clearing House에 등록`

### 3. DRM의 흐름 및 구성 요소

```text
콘텐츠 제공자
   ↓ 콘텐츠 등록
콘텐츠 배포자
   ↓ 콘텐츠 유통
콘텐츠 소비자

Clearing House
↔ 라이선스 발급·등록·요금 처리

DRM Controller
Security Container
```

#### 구성 요소

| 구성 요소 | 핵심 |
|---|---|
| **클리어링 하우스(Clearing House)** | 저작권에 대한 **사용 권한 / 라이선스 발급 / 암호화된 키 관리 / 사용량에 따른 결제 관리** |
| **콘텐츠 제공자(Contents Provider)** | 콘텐츠를 제공하는 **저작권자** |
| **패키저(Packager)** | 콘텐츠를 메타 데이터와 함께 **배포 가능한 형태로 묶어 암호화** |
| **콘텐츠 배포자(Contents Distributor)** | 암호화된 콘텐츠를 **유통**하는 곳 또는 사람 |
| **콘텐츠 소비자(Customer)** | 콘텐츠를 구매하여 사용하는 주체 |
| **DRM 컨트롤러(DRM Controller)** | 배포된 콘텐츠의 **이용 권한 통제** |
| **보안 컨테이너(Security Container)** | 콘텐츠 원본을 **안전하게 유통하기 위한 전자적 보안 장치** |

> ⭐ `Clearing House = 권한·라이선스·키·결제`  
> ⭐ `Packager = 콘텐츠 암호화 포장`  
> ⭐ `DRM Controller = 이용 권한 통제`

### 4. DRM 기술 요소

| 기술 요소 | 핵심 |
|---|---|
| **암호화(Encryption)** | 콘텐츠 및 라이선스를 암호화하고 전자서명할 수 있는 기술 |
| **키 관리(Key Management)** | 콘텐츠를 암호화한 키에 대한 저장 및 분배 기술 |
| **암호화 파일 생성(Packager)** | 콘텐츠를 암호화된 콘텐츠로 생성하는 기술 |
| **식별 기술(Identification)** | 콘텐츠에 대한 식별 체계 표현 기술 |
| **저작권 표현(Right Expression)** | 라이선스의 내용 표현 기술 |
| **정책 관리(Policy Management)** | 라이선스 발급 및 사용에 대한 정책 표현 및 관리 |
| **크랙 방지(Tamper Resistance)** | 크랙에 의한 콘텐츠 사용 방지 기술 |
| **인증(Authentication)** | 라이선스 발급 및 사용의 기준이 되는 사용자 인증 기술 |

> ⭐ DRM 기술 요소 → `암·키·패·식·권·정·크·인`

## SECTION 039. 소프트웨어 설치 매뉴얼 작성

### 1. 소프트웨어 설치 매뉴얼의 개요
- **소프트웨어 설치 매뉴얼** - 개발 초기부터 적용된 기준이나 사용자가 소프트웨어를 설치하는 과정에 필요한 내용을 기록한 **설명서 및 안내서**
- 설치 매뉴얼은 **사용자 기준**으로 작성
- 설치 시작부터 완료까지의 전 과정을 **빠짐없이 순서대로 설명**
- 설치 과정에서 표시될 수 있는
  - 오류 메시지
  - 예외 상황

  에 대한 내용을 별도로 분류하여 설명
- 기본적으로
  - 목차 및 개요
  - 서문
  - 기본 사항

  등이 포함
- 목차에는 전체 설치 과정을 순서대로 요약 후 관련 내용의 **페이지 번호**를 함께 기술
- 개요에는 설치 매뉴얼의
  - 주요 특징
  - 구성
  - 설치 방법
  - 순서

  등을 기술

> ⭐ `설치 매뉴얼 = 설치 시작 → 완료까지 사용자 기준으로 순서대로 작성`

### 2. 서문
서문에는 다음 내용을 기술

#### 문서 이력
- 버전
- 작성자
- 작성일
- 검토자
- 일시
- 검수인
- 변경 내용 등

#### 설치 매뉴얼의 주석
- **주의 사항**
  - 설치 도중 사용자가 반드시 알아야 하는 중요한 내용
- **참고 사항**
  - 설치에 영향을 미칠 수 있는 사용자 환경이나 상황에 관한 내용

#### 설치 도구의 구성
- `exe`, `dll`, `ini`, `chm` 등 **설치 관련 파일** 설명
- 폴더 및 설치 프로그램 실행 파일 설명
- 설치 과정 및 결과가 기록되는 **log 폴더** 설명

> ⭐ `서문 = 문서 이력 + 주의/참고 + 설치 파일·폴더 구성`

### 3. 설치 환경 체크 항목

| 항목 | 내용 |
|---|---|
| **사용자 환경** | CPU, Memory, OS 등 |
| **응용 프로그램** | 설치 전 다른 응용 프로그램 종료 |
| **업그레이드 버전** | 업그레이드 이전 버전의 존재 여부 확인 |
| **백업 폴더 확인** | 데이터 저장 폴더를 확인하여 설치 시 폴더 이동 |
| **기타** | 설치에 필요한 추가 환경 확인 |

### 4. 기본 사항
- 소프트웨어와 관련하여 기본적으로 설명해야 할 항목

| 항목 | 설명 |
|---|---|
| **소프트웨어 개요** | 소프트웨어의 주요 기능 및 UI / UI 및 화면 설명 |
| **설치 관련 파일** | 설치에 필요한 파일 설명 (`exe`, `ini`, `log` 등) |
| **설치 아이콘(Installation)** | 설치 아이콘 설명 |
| **프로그램 삭제** | 설치된 소프트웨어 삭제 방법 |
| **관련 추가 정보** | 라이선스 정보 / 제작사 정보 등 추가 정보 |

### 5. 설치 매뉴얼 작성 순서

```text
기능 식별
→ UI 분류
→ 설치 파일 / 백업 파일 확인
→ Uninstall 절차 확인
→ 이상 Case 확인
→ 최종 매뉴얼 적용
```

#### ① 기능 식별
- 소프트웨어 개발 목적과 주요 기능을 **흐름 순으로 정리**

#### ② UI 분류
- 설치 매뉴얼을 작성할 순서대로 **UI를 분류**

#### ③ 설치 파일 / 백업 파일 확인
- 폴더 위치
- 설치 파일
- 백업 파일

  등의 개별적인 기능을 확인하여 기록

#### ④ Uninstall 절차 확인
- 직접 Uninstall을 수행하며 그 순서를 단계별로 자세히 기록

#### ⑤ 이상 Case 확인
- 설치 과정에서 발생할 수 있는 다양한 Case를 만들어 확인
- 해당 Case에 대한 대처법을 자세하게 기록

#### ⑥ 최종 매뉴얼 적용
- 설치가 완료된 화면과 메시지를 **캡처하여 추가**
- 완성된 매뉴얼을 검토하고 고객 지원에 대한 내용을 기록

> ⭐ 설치 매뉴얼 순서 → `기UI설언이최`

## SECTION 040. 소프트웨어 사용자 매뉴얼 작성

### 1. 소프트웨어 사용자 매뉴얼의 개요
- **소프트웨어 사용자 매뉴얼** - 사용자가 소프트웨어를 사용하는 과정에서 필요한 내용을 문서로 기록한 **설명서 및 안내서**
- 사용자 매뉴얼은 **사용자가 소프트웨어 사용에 필요한 절차와 환경 등의 제반 사항을 모두 포함**
- 소프트웨어 배포 후 발생할 수 있는
  - 오류 대처
  - 기능 업그레이드

  등 변경 사항을 빠르게 반영
- **개별적으로 동작 가능한 컴포넌트 단위**로 매뉴얼 작성 가능
- 컴포넌트가 수행되는 명세서와 **컴포넌트 구현 설계서**를 토대로 작성
- 사용자 매뉴얼에는
  - 목차 및 개요
  - 서문
  - 기본 사항

  등이 기본적으로 포함
- 목차에는 매뉴얼 전체 내용을 순서대로 요약한 뒤 관련 내용의 페이지 번호를 함께 기술
- 개요에는 소프트웨어의
  - 주요 특징
  - 매뉴얼 구성
  - 실행 방법
  - 사용법
  - 항목별 점검 기준
  - 항목별 설정 방법

  등을 기술

> ⭐ `사용자 매뉴얼 = 설치 이후 실제 사용 방법 중심`

## SECTION 041. 소프트웨어 버전 등록

### 1. 소프트웨어 패키징의 형상 관리
- **형상 관리(SCM; Software Configuration Management)** - 소프트웨어 개발 과정에서 **소프트웨어의 변경 사항을 관리**하기 위해 개발된 일련의 활동
- 소프트웨어 변경의 원인을 알아내고 제어
- 적절히 변경되고 있는지 확인하여 해당 담당자에게 통보
- 소프트웨어 개발의 **전 단계에 적용**
- 유지보수 단계에서도 수행
- 개발 전체 비용을 줄이고 개발 과정의 방해 요인을 최소화하여 **보증 기능을 제공**
- 관리 대상
  - 소스 코드뿐만 아니라
  - 프로젝트 계획
  - 분석서
  - 설계서
  - 프로그램
  - 테스트 케이스

  등도 포함
- 변경 사항을 추적하여 **가시성(Visibility)**과 **추적성(Traceability)** 확보
- 대표 도구
  - `Git`
  - `CVS`
  - `Subversion`

> ⭐ `형상 관리 = 개발 전 과정의 변경 사항 관리·추적`  
> ⭐ `소스 코드만 관리하는 것 X`

### 2. 형상 관리의 중요성
- 지속적인 소프트웨어 변경 사항을 **체계적으로 추적하고 통제**
- 제품 소프트웨어의 **무절제한 변경 방지**
- 제품 소프트웨어에서 발견된 **버그나 수정 사항 추적**
- 소프트웨어는 형태가 없어 가시성이 결핍되므로 **진행 정도 확인 기능 필요**
- 소프트웨어 배포를 효율적으로 관리
- 여러 명의 개발자가 동시에 개발 가능

### 3. 형상 관리 기능

| 기능 | 핵심 |
|---|---|
| **형상 식별** | 형상 관리 대상에 이름과 관리 번호를 부여하고 계층(Tree) 구조로 분류하여 수정·추적이 쉽게 함 |
| **버전 제어** | 소프트웨어 업그레이드나 유지보수 과정에서 생성된 다른 버전의 형상 항목을 관리하고 특정 절차·도구를 결합 |
| **형상 통제(변경 관리)** | 식별된 형상 항목에 대한 변경 요구를 검토하여 현재 기준선(Base Line)이 유지되도록 조정 |
| **형상 감사** | 기준선의 무결성을 평가하기 위해 확인·검증·검열 과정을 통해 공식적으로 승인 |
| **형상 기록(상태 보고)** | 형상의 식별·통제·감사 작업 결과를 기록·관리하고 보고서를 작성 |

> ⭐ 형상 관리 기능 → `식·버·통·감·기`  
> ⭐ `식별 → 버전 → 통제 → 감사 → 기록`

### 4. 소프트웨어 버전 등록 관련 주요 기능

| 기능 | 설명 |
|---|---|
| **저장소(Repository)** | 최신 버전 파일들과 변경 내역에 대한 정보를 저장 |
| **가져오기(Import)** | 버전 관리가 되고 있지 않은 새로운 파일을 저장소에 **처음 등록** |
| **체크아웃(Check-Out)** | 프로그램 수정 작업을 위해 **저장소에서 파일을 받아옴** |
| **체크인(Check-In)** | 체크아웃한 파일의 수정 완료 후 저장소의 파일을 **새로운 버전으로 갱신** |
| **커밋(Commit)** | 체크인 시 이전에 갱신된 내용이 있으면 충돌을 알리고 `diff`로 수정 후 갱신 |
| **동기화(Update)** | 저장소의 최신 소스와 자신의 작업 공간을 **동기화** |

> ⭐ `Import = 최초 등록`  
> ⭐ `Check-Out = 받아오기`  
> ⭐ `Check-In = 수정한 파일 반영`  
> ⭐ `Update = 최신 상태 동기화`

### 5. 소프트웨어 버전 등록 과정

```text
가져오기(Import)
→ 인출(Check-Out)
→ 예치(Commit)
→ 동기화(Update)
→ 차이(Diff)
```

#### 가져오기(Import)
- 개발자가 저장소에 **신규 파일 추가**

#### 인출(Check-Out)
- 수정 작업을 진행할 개발자가 저장소에 추가된 파일을 **자신의 작업 공간으로 인출**

#### 예치(Commit)
- 인출한 파일을 수정한 후 설명을 붙여 저장소에 **예치**

#### 동기화(Update)
- Commit 수행 후 개발자가 자신의 작업 공간을 저장소와 동기화
- 이때 기존 개발자가 추가했던 파일이 전달됨

#### 차이(Diff)
- 새로운 개발자가 추가된 파일의 수정 기록(Change Log)을 확인
- 이전 개발자가 처음 추가한 파일과 이후 변경된 파일의 차이를 확인

> ⭐ 버전 등록 순서 → `가인예동차`

## SECTION 042. 소프트웨어 버전 관리 도구

### 1. 공유 폴더 방식
- 버전 관리 자료가 **로컬 컴퓨터의 공유 폴더에 저장**되어 관리되는 방식
- 개발자는 개발이 완료된 파일을 약속된 공유 폴더에 매일 복사
- 담당자는 공유 폴더의 파일을 자기 PC로 복사한 후 컴파일하여 이상 유무 확인
- 오류가 확인되면 파일을 등록한 개발자에게 수정 의뢰
- 파일에 이상이 없다면 각 개발자가 동작 여부를 다시 확인
- 잘못 복사하거나 다른 위치로 복사하는 상황에 대비하여 파일의 변경 사항을 **데이터베이스에 기록**
- 종류
  - `SCCS`
  - `RCS`
  - `PVCS`
  - `QVCS`

> ⭐ `공유 폴더 = 로컬 공유 폴더에 파일을 직접 복사하여 관리`

### 2. 클라이언트/서버 방식
- 버전 관리 자료가 **중앙 시스템(서버)**에 저장되어 관리
- 서버의 자료를 개발자의 로컬 PC(클라이언트)로 복사하여 작업 후 변경 내용을 서버에 반영
- 모든 버전 관리는 **서버에서 수행**
- 하나의 파일을 서로 다른 개발자가 작업할 경우 **경고 메시지 출력**
- 서버에 문제가 생기면 서버가 복구될 때까지 다른 개발자와의 협업 및 버전 관리 작업이 중단될 수 있음
- 종류
  - `CVS`
  - `SVN(Subversion)`
  - `CVSNT`
  - `Clear Case`
  - `CMVC`
  - `Perforce`

> ⭐ `Client/Server = 중앙 저장소 1개`

### 3. 분산 저장소 방식
- 버전 관리 자료가
  - **하나의 원격 저장소**
  - **분산된 개발자 PC의 로컬 저장소**

  에 함께 저장되어 관리되는 방식
- 개발자는 로컬 저장소에서 작업을 수행한 후 변경 내용을 먼저 로컬에 반영한 뒤 **원격 저장소에 반영**
- 로컬 저장소에서 버전 관리가 가능하므로 원격 저장소에 문제가 생겨도 **로컬에서 작업 가능**
- 종류
  - `Git`
  - `GNU arch`
  - `DCVS`
  - `Bazaar`
  - `Mercurial`
  - `TeamWare`
  - `BitKeeper`
  - `Plastic SCM`

> ⭐ `분산 = 원격 저장소 + 개발자별 로컬 저장소`  
> ⭐ `Git = 분산 저장소 방식`

### 4. 버전 관리 방식 비교

| 방식 | 저장 위치 | 핵심 |
|---|---|---|
| **공유 폴더** | 로컬 공유 폴더 | 파일 직접 복사 |
| **클라이언트/서버** | 중앙 서버 | 중앙에서 통합 관리 |
| **분산 저장소** | 원격 + 로컬 | 로컬에서도 버전 관리 가능 |

### 5. Subversion(SVN)
- **CVS를 개선한 버전 관리 도구**
- 클라이언트/서버 구조
- 서버(저장소, Repository)에는
  - 최신 버전 파일
  - 변경 내역

  이 관리
- 서버 자료를 클라이언트로 복사한 후 작업하고 변경 내용을 서버에 반영(**Commit**)
- 모든 개발 작업은 `trunk` 디렉터리에서 수행
- 추가 작업은 `branches` 디렉터리 안에 별도의 디렉터리를 만들어 작업한 후
  - `trunk` 디렉터리와 **병합(Merge)**
- `Commit`할 때마다 **Revision이 1씩 증가**
- 대부분의 운영체제에서 사용 가능
- 오픈 소스이며 무료 사용 가능
- CVS의 단점이었던
  - 파일·디렉터리 이름 변경
  - 이동

  등이 가능

> ⭐ `SVN = CVS 개선 / Client-Server / trunk·branches / Commit마다 Revision +1`

### 6. SVN 주요 명령어

| 명령어 | 의미 |
|---|---|
| **add** | 새로운 파일이나 디렉터리를 버전 관리 대상으로 등록 |
| **commit** | 버전 관리 대상 클라이언트의 소스 파일을 서버의 소스 파일에 적용 |
| **update** | 서버의 최신 commit 이력을 클라이언트 소스 파일에 적용 |
| **checkout** | 버전 관리 정보와 소스 파일을 서버에서 클라이언트로 받아옴 |
| **lock / unlock** | 서버의 소스 파일이나 디렉터리를 잠그거나 해제 |
| **import** | 아무것도 없는 서버 저장소에 맨 처음 소스 파일 저장 |
| **export** | 버전 관리 관련 정보를 제외한 순수 소스 파일만 서버에서 받아옴 |
| **info** | 지정 파일의 위치나 마지막 수정 일자 등에 대한 정보 표시 |
| **diff** | 지정 파일이나 경로에 대해 이전 리비전과의 차이 표시 |
| **merge** | 다른 디렉터리에서 작업된 버전 관리 내역을 기본 개발 작업과 병합 |

> ⭐ SVN 명령 핵심  
> `add 등록 / commit 서버 반영 / update 최신화 / checkout 받아오기 / diff 차이 / merge 병합`

### 7. Git
- **리누스 토발즈(Linus Torvalds)**가 2005년 리눅스 커널 개발에 사용하기 위해 개발
- **분산 버전 관리 시스템**
- 저장소가
  - **지역(로컬) 저장소**
  - **원격 저장소**

  로 구분
- **지역 저장소**
  - 개발자가 실제 개발을 진행하는 장소
  - 버전 관리 수행
- **원격 저장소**
  - 여러 사람이 협업을 위해 버전을 공동 관리하는 장소
  - 자신의 버전 관리 내역을 반영하거나 다른 개발자의 변경 내용을 가져옴
- 버전 관리가 지역 저장소에서 진행되므로 **신속한 처리 가능**
- 원격 저장소나 네트워크에 문제가 있어도 **작업 가능**
- **브랜치(Branch)**를 이용하면 기본 버전 관리 흐름에 영향을 주지 않으면서 다양한 형태의 기능 테스팅 가능
- 파일의 변경 내용을 **스냅샷(Snapshot)**으로 저장
- 스냅샷은 이전 스냅샷의 포인터를 가지므로 버전의 흐름을 파악할 수 있음

> ⭐ `Git = 분산 버전 관리 / Local + Remote / Snapshot / Branch`

### 8. Git 주요 명령어

| 명령어 | 의미 |
|---|---|
| **add** | 작업 내용을 지역 저장소에 저장하기 위해 **Staging Area**에 추가 |
| **commit** | 작업 내용을 지역 저장소에 저장 |
| **branch** | 새로운 브랜치 생성 또는 삭제 |
| **checkout** | 지정한 브랜치로 이동 / HEAD 포인터가 해당 브랜치를 가리키게 함 |
| **merge** | 지정한 브랜치의 변경 내역을 현재 HEAD가 가리키는 브랜치에 병합 |
| **init** | 지역 저장소 생성 |
| **remote add** | 원격 저장소에 연결 |
| **push** | 로컬 저장소의 변경 내용을 원격 저장소에 반영 |
| **fetch** | 원격 저장소의 변경 이력을 지역 저장소로 가져와 반영 |

> ⭐ `add = Stage / commit = Local 저장 / push = Remote 반영 / fetch = Remote → Local`

### 9. SVN vs Git

| 구분 | SVN | Git |
|---|---|---|
| **방식** | 클라이언트/서버 | **분산 저장소** |
| **저장소** | 중앙 서버 중심 | Local + Remote |
| **Commit** | 서버 저장소에 반영 | 우선 **로컬 저장소**에 저장 |
| **오프라인 작업** | 제한적 | 로컬 버전 관리 가능 |
| **특징** | Revision 번호 | Snapshot / Branch |

> ⭐ `SVN = 중앙`  
> ⭐ `Git = 분산`

## SECTION 043. 빌드 자동화 도구

### 1. 빌드 자동화 도구의 개요
- **빌드(Build)** - 소스 코드 파일들을 컴파일한 후 여러 개의 모듈을 묶어 **실행 파일로 만드는 과정**
- **빌드 자동화 도구** - 빌드를 포함하여
  - 테스트
  - 배포

  를 자동화하는 도구
- 애자일 환경에서는 하나의 작업이 마무리될 때마다 모든 단위로 나눠 개발된 코드를 지속적으로 통합하는 **지속적 통합(Continuous Integration)** 개발 환경에서 빌드 자동화 도구를 유용하게 활용
- 대표적인 빌드 자동화 도구
  - `Ant`
  - `Make`
  - `Maven`
  - `Gradle`
  - `Jenkins`
- 이 중 **Jenkins와 Gradle이 가장 대표적**

> ⭐ `빌드 자동화 = Build + Test + Deploy 자동화`  
> ⭐ `CI(지속적 통합) 환경에서 유용`

### 2. Jenkins
- Java 기반의 **오픈 소스 형태**
- 가장 많이 사용되는 빌드 자동화 도구
- **서블릿 컨테이너에서 실행되는 서버 기반 도구**
- `SVN`, `Git` 등 대부분의 형상 관리 도구와 연동 가능
- 친숙한 **Web GUI** 제공
- 여러 대의 컴퓨터를 이용한 **분산 빌드·테스트 가능**

> ⭐ `Jenkins = Java + Open Source + Web GUI + 형상 관리 연동 + 분산 빌드`

### 3. Gradle
- **Groovy를 기반**으로 한 오픈 소스 형태의 자동화 도구
- **Android 앱 개발 환경에서 사용**
- 안드로이드뿐만 아니라 플러그인 설정에 따라
  - Java
  - C/C++
  - Python

  등의 언어도 빌드 가능
- Groovy를 사용해서 만든 **DSL(Domain Specific Language)**을 스크립트 언어로 사용
- 실행할 처리 명령들을 모아 **Task**로 만든 후 태스크 단위로 실행
- 이전에 사용했던 태스크를 재사용하거나 다른 시스템의 태스크를 공유할 수 있도록 **빌드 캐시 기능**을 지원하여 빌드 속도 향상 가능

> ⭐ `Gradle = Groovy + DSL + Task + Build Cache`  
> ⭐ `Android 개발에서 대표적으로 사용`

### 4. Jenkins vs Gradle

| 구분 | Jenkins | Gradle |
|---|---|---|
| **기반** | Java | Groovy |
| **형태** | 서버 기반 빌드 자동화 도구 | 오픈 소스 빌드 자동화 도구 |
| **특징** | Web GUI / SCM 연동 / 분산 빌드 | DSL / Task / Build Cache |
| **활용** | 지속적 통합·자동 빌드 | Android 등 다양한 빌드 환경 |
