# 04. 애플리케이션 테스트 관리

## SECTION 044. 애플리케이션 테스트

### 1. 애플리케이션 테스트의 개요
- **애플리케이션 테스트** - 애플리케이션에 잠재되어 있는 **결함을 찾아내는 일련의 행위 또는 절차**
- 개발된 소프트웨어가 고객의 요구사항을 만족시키는지 **확인(Validation)**하고, 기능을 정확하게 수행하는지 **검증(Verification)**함
- 테스트 전에 개발 소프트웨어의 유형을 분류하고 특성을 정리하여 **중점적으로 테스트할 사항을 결정**

> ⭐ `Validation = 사용자 요구사항 만족 여부`  
> ⭐ `Verification = 기능을 정확히 수행하는지 여부`

---

### 2. 소프트웨어의 분류
- 소프트웨어는 사용 목적이나 제공 방식 등에 따라 다양하게 분류됨

#### 산업 범용 소프트웨어
- 특정 산업에 국한되지 않고 여러 분야에서 공통적으로 사용하는 소프트웨어
- **시스템 소프트웨어**
  - 하드웨어 전체를 제어하고 운영하는 소프트웨어
  - 운영체제, 컴파일러 등
- **미들웨어**
  - 운영체제와 응용 프로그램 사이에서 서비스를 제공
- **응용 소프트웨어**
  - 특정 업무를 처리하기 위한 소프트웨어

#### 산업 특화 소프트웨어
- 자동차, 항공, 조선, 건설 등의 **특정 산업에서 요구되는 기능을 구현한 소프트웨어**

#### 서비스 제공 소프트웨어
- 소프트웨어 자체를 판매하는 것이 아니라 **특정 사용자가 필요로 하는 기능을 구현하여 제공**
- 유형
  - **신규 개발 소프트웨어** - 새로운 서비스 제공을 위해 개발
  - **기능 개선 소프트웨어** - 사용자 편의성·업무 프로세스 등 기존 서비스 기능 개선
  - **추가 개발 소프트웨어** - 업무·산업 환경 변화, 법·제도 개정 등으로 새로운 기능 추가
  - **시스템 통합 소프트웨어** - 시스템별 서비스를 통합하여 One-Stop 서비스 제공

> ⭐ `서비스 제공 SW = 신규 개발 / 기능 개선 / 추가 개발 / 시스템 통합`

---

### 3. 애플리케이션 테스트의 필요성
- 프로그램 실행 전에 오류를 발견하여 **예방 가능**
- 프로그램이 사용자의 요구사항이나 기대 수준을 만족하는지 반복적으로 테스트하여 **제품 신뢰도 향상**
- 개발 초기부터 테스트하면 단순한 오류를 발견할 수 있어 **개발 완료 후 오류 수정 비용을 줄일 수 있음**
- 효과적인 테스트를 통해 최소한의 시간과 노력으로 많은 결함을 찾을 수 있음

> ⭐ `테스트 = 오류 예방 + 품질·신뢰도 향상 + 수정 비용 감소`

---

### 4. 애플리케이션 테스트의 기본 원리
- 테스트는 소프트웨어에 **잠재적인 결함이 있음을 밝히는 활동**
- 결함이 없다고 증명할 수는 없으므로 **완벽한 테스트는 불가능**
- 테스트는 가능한 **작은 부분에서 시작하여 점점 확대**
- 동일한 테스트 케이스를 반복하면 새로운 결함을 찾는 능력이 떨어지므로 테스트 케이스를 지속적으로 보완해야 함
- 소프트웨어의 특징·테스트 환경 등에 따라 테스트 결과가 달라질 수 있음
- 개발자가 아닌 **별도의 팀에서 수행**하는 것이 효과적
- 테스트는 개발 초기부터 계획하여 수행하는 것이 좋음

#### 파레토 법칙(Pareto Principle)
- 애플리케이션의 **20%에 해당하는 코드에서 전체 결함의 약 80%가 발견**된다는 법칙

> ⭐ `Pareto = 20% 코드 → 80% 결함`

#### 살충제 패러독스(Pesticide Paradox)
- 동일한 테스트 케이스를 반복하면 더 이상 새로운 결함을 발견하기 어려워지는 현상
- 새로운 결함을 찾기 위해 테스트 케이스를 **지속적으로 개선·보완**

> ⭐ `같은 테스트 반복 → 결함 발견 능력 ↓ = 살충제 패러독스`

#### 오류-부재의 궤변(Absence of Errors Fallacy)
- 소프트웨어의 결함을 모두 제거했더라도 **사용자의 요구사항을 만족하지 못하면 품질이 높은 소프트웨어라고 할 수 없음**

> ⭐ `결함 0개 ≠ 좋은 소프트웨어`  
> ⭐ `사용자 요구 충족이 중요`

## SECTION 045. 애플리케이션 테스트의 분류

### 1. 프로그램 실행 여부에 따른 테스트

| 구분 | 핵심 | 종류 |
|---|---|---|
| **정적 테스트(Static Test)** | 프로그램을 **실행하지 않고** 소스 코드·문서를 분석 | 워크스루, 인스펙션, 코드 검사 |
| **동적 테스트(Dynamic Test)** | 프로그램을 **직접 실행하여** 오류 확인 | 화이트박스, 블랙박스 |

> ⭐ `정적 = 실행 X`  
> ⭐ `동적 = 실행 O`

---

### 2. 테스트 기반(Test Bases)에 따른 테스트

| 구분 | 핵심 | 종류 |
|---|---|---|
| **명세 기반 테스트** | 사용자 요구사항에 대한 명세를 바탕으로 테스트 케이스 작성 | 동등 분할, 경계값 분석 |
| **구조 기반 테스트** | 소프트웨어 내부의 논리 흐름을 바탕으로 테스트 케이스 작성 | 구문 기반, 결정 기반, 조건 기반 |
| **경험 기반 테스트** | 테스터의 경험을 기반으로 수행 | 에러 추정, 체크 리스트, 탐색적 테스팅 |

> ⭐ `명세 = 요구사항`  
> ⭐ `구조 = 내부 로직`  
> ⭐ `경험 = 테스터 경험`

---

### 3. 시각에 따른 테스트

#### 검증(Verification) 테스트
- **개발자의 시각**
- 제품 생산 과정을 테스트
- 제품이 **명세대로 완성되었는지** 확인

#### 확인(Validation) 테스트
- **사용자의 시각**
- 생산된 제품의 결과를 테스트
- 제품이 **사용자의 요구사항을 만족하는지** 확인

> ⭐ `Verification = 개발자 / 명세대로 만들었나?`  
> ⭐ `Validation = 사용자 / 원하는 제품인가?`

---

### 4. 목적에 따른 테스트

| 종류 | 핵심 |
|---|---|
| **회복(Recovery) 테스트** | 시스템에 결함을 주어 **올바르게 복구되는지** 확인 |
| **안전(Security) 테스트** | 불법적인 소프트웨어·시스템 접근으로부터 **보호 가능한지** 확인 |
| **강도(Stress) 테스트** | 과도한 정보량·빈번한 명령 등 **과부하 상황에서도 정상 작동하는지** 확인 |
| **성능(Performance) 테스트** | 실시간 성능이나 전체적인 효율성 진단 / 응답시간·처리량 확인 |
| **구조(Structure) 테스트** | 소프트웨어 내부의 논리적인 경로와 소스 코드 복잡도 평가 |
| **회귀(Regression) 테스트** | 변경·수정된 코드에 **새로운 결함이 발생하지 않았는지** 확인 |
| **병행(Parallel) 테스트** | 변경된 소프트웨어와 기존 소프트웨어에 동일 데이터를 입력하여 **결과 비교** |

> ⭐ `Recovery = 복구`  
> ⭐ `Security = 보안`  
> ⭐ `Stress = 과부하`  
> ⭐ `Performance = 성능`  
> ⭐ `Regression = 수정 후 재검사`  
> ⭐ `Parallel = 신·구 결과 비교`

## SECTION 046. 테스트 기법에 따른 애플리케이션 테스트

### 1. 화이트박스 테스트(White Box Test)
- 모듈의 원시 코드를 오픈한 상태에서 **원시 코드의 논리적인 모든 경로를 테스트**
- 설계된 절차에 초점을 둔 **구조적 테스트**
- 프로시저 설계의
  - 제어 구조
  - 조건
  - 반복

  등에 초점을 맞춤
- 모든 문장을 한 번 이상 실행하여 수행
- 프로그램의 논리 구조를 직접 확인하므로 **구조 기반 테스트**에 해당

> ⭐ `White Box = 내부 구조·논리 경로 검사`

---

### 2. 화이트박스 테스트의 종류

#### 기초 경로 검사(Base Path Testing)
- 대표적인 화이트박스 테스트 기법
- 테스트 케이스 설계자가 절차적 설계의 **논리적 복잡성**을 측정하여 실행 경로의 기본 집합을 정의

#### 제어 구조 검사(Control Structure Testing)

| 종류 | 핵심 |
|---|---|
| **조건 검사(Condition Testing)** | 프로그램 모듈 내 논리적 조건을 테스트 |
| **루프 검사(Loop Testing)** | 반복 구조에 초점을 맞춰 실시 |
| **데이터 흐름 검사(Data Flow Testing)** | 변수의 정의와 사용 위치에 초점을 맞춰 테스트 |

> ⭐ `제어 구조 검사 = 조건 / 루프 / 데이터 흐름`

---

### 3. 화이트박스 테스트의 검증 기준(Coverage)

| 검증 기준 | 핵심 |
|---|---|
| **문장 검증 기준(Statement Coverage)** | 소스 코드의 **모든 문장이 한 번 이상 수행**되도록 테스트 |
| **분기/결정 검증 기준(Branch/Decision Coverage)** | 결정 조건의 **True / False** 결과가 모두 수행되도록 테스트 |
| **조건 검증 기준(Condition Coverage)** | 개별 조건식의 **True / False** 결과가 모두 수행되도록 테스트 |
| **분기/조건 검증 기준(Branch/Condition Coverage)** | 분기 조건과 개별 조건의 **True / False** 결과가 모두 수행되도록 테스트 |

> ⭐ `Statement = 모든 문장`  
> ⭐ `Branch = 결정 결과 T/F`  
> ⭐ `Condition = 개별 조건 T/F`

---

### 4. 블랙박스 테스트(Black Box Test)
- 소프트웨어가 수행할 특정 기능을 알기 위해 **각 기능이 완전히 작동되는지 확인**
- 프로그램 구조를 보지 않고 **요구사항·기능 명세를 기반**으로 수행
- **기능 테스트**라고도 함
- 소프트웨어 인터페이스에서 실시
- 부정확하거나 누락된 기능, 인터페이스 오류, 자료 구조·외부 DB 접근 오류, 행위·성능 오류, 초기화·종료 오류 등을 발견하기 위해 사용

> ⭐ `Black Box = 내부 코드 X / 기능·입출력 중심`

---

### 5. 블랙박스 테스트의 종류

#### 동치 분할 검사(Equivalence Partitioning Testing)
- 입력 자료를 **동등한 종류의 클래스로 분할**
- 각 클래스의 대표값을 테스트 케이스로 선정

#### 경계값 분석(Boundary Value Analysis)
- 입력 조건의 **경계값에서 오류 발생 확률이 높다**는 점을 이용
- 입력 조건의 경계값을 테스트 케이스로 선정

#### 원인-효과 그래프 검사(Cause-Effect Graphing Testing)
- 입력 데이터 간 관계와 출력에 영향을 미치는 상황을 분석하여
  **효용성이 높은 테스트 케이스**를 선정

#### 오류 예측 검사(Error Guessing)
- 과거 경험이나 테스터의 감각으로 테스트
- 다른 블랙박스 기법으로 찾아내기 어려운 오류를 발견

#### 비교 검사(Comparison Testing)
- 여러 버전의 프로그램에 **동일한 테스트 자료**를 제공하여 결과가 동일한지 확인

> ⭐ 블랙박스 → `동경원오비`  
> `동치 / 경계 / 원인-효과 / 오류 예측 / 비교`

## SECTION 047. 개발 단계에 따른 애플리케이션 테스트

### 1. 개발 단계에 따른 애플리케이션 테스트
- 소프트웨어 개발 단계에 따라
  - **단위 테스트**
  - **통합 테스트**
  - **시스템 테스트**
  - **인수 테스트**

  로 구분
- 개발 단계와 테스트 단계를 연결하여 표현한 것 → **V-모델**

```text
요구사항  ───────────── 인수 테스트
  분석    ───────────── 시스템 테스트
   설계   ───────────── 통합 테스트
   구현   ───────────── 단위 테스트
```

> ⭐ `구현 → 단위`  
> ⭐ `설계 → 통합`  
> ⭐ `분석 → 시스템`  
> ⭐ `요구사항 → 인수`

---

### 2. 단위 테스트(Unit Test)
- 코딩 직후 소프트웨어 설계의 **최소 단위인 모듈이나 컴포넌트에 초점**
- 인터페이스, 외부 I/O, 자료 구조, 독립적 기초 경로, 오류 처리 경로, 경계 조건 등을 검사
- 사용자의 요구사항을 기반으로 한 **기능성 테스트를 최우선**
- 구조 기반 테스트와 명세 기반 테스트로 나누어 수행

#### 단위 테스트로 발견 가능한 오류
- 알고리즘 오류에 따른 원치 않는 결과
- 탈출구가 없는 반복문의 사용
- 틀린 계산 수식에 의한 잘못된 결과

#### 단위 테스트 방법

| 방법 | 핵심 | 목적 |
|---|---|---|
| **구조 기반 테스트** | 프로그램 내부 구조·복잡도를 검증하는 White Box | 제어 흐름, 조건 결정 |
| **명세 기반 테스트** | 목적·실행 코드 기반의 Black Box | 동등 분할, 경계값 분석 |

---

### 3. 통합 테스트(Integration Test)
- 단위 테스트가 완료된 모듈들을 **결합하여 하나의 시스템으로 완성하는 과정에서 테스트**
- 모듈 또는 통합 컴포넌트 간 **상호 작용 오류를 검사**

---

### 4. 시스템 테스트(System Test)
- 개발된 소프트웨어가 **컴퓨터 시스템에서 완벽하게 수행되는지 검증**
- 실제 사용 환경과 유사한 환경에서 테스트하는 것이 좋음

#### 기능적 요구사항
- 요구사항 명세서
- 비즈니스 절차
- 유스케이스 등

  명세를 기반으로 **블랙박스 테스트**

#### 비기능적 요구사항
- 성능
- 회복
- 보안 등

  시스템의 품질 특성을 테스트

> ⭐ `System Test = 기능 + 비기능 요구사항 모두 확인`

---

### 5. 인수 테스트(Acceptance Test)
- 개발한 소프트웨어가 **사용자의 요구사항을 충족하는지** 중점을 두고 테스트
- 사용자가 직접 테스트
- 문제가 없으면 사용자가 소프트웨어를 인수하고 프로젝트 종료

#### 인수 테스트의 종류

| 종류 | 핵심 |
|---|---|
| **사용자 인수 테스트** | 사용자가 시스템 사용의 적절성 여부 확인 |
| **운영상의 인수 테스트** | 시스템 관리자가 백업/복원, 재난 복구, 사용자 관리, 정기 점검 등을 확인 |
| **계약 인수 테스트** | 계약상의 인수·검수 조건 준수 여부 확인 |
| **규정 인수 테스트** | 정부 지침, 법규, 규정 등에 맞게 개발되었는지 확인 |
| **알파 테스트** | 개발자의 장소에서 사용자와 개발자가 함께 수행 / 통제된 환경 |
| **베타 테스트** | 실제 사용자가 개발자 없이 실제 환경에서 수행 / 발견 문제를 개발자에게 보고 |

> ⭐ `Alpha = 개발자 장소 + 함께`  
> ⭐ `Beta = 실제 사용자 + 개발자 없이`

---

## SECTION 048. 통합 테스트

### 1. 통합 테스트(Integration Test)
- 단위 테스트가 끝난 모듈을 통합하는 과정에서 발생하는 **오류 및 결함을 찾는 테스트**
- 통합 방식
  - **비점진적 통합**
  - **점진적 통합**

#### 비점진적 통합 방식
- 단계 없이 모든 모듈을 한 번에 결합하여 테스트
- 규모가 작은 소프트웨어에 유리

#### 점진적 통합 방식
- 모듈을 단계적으로 통합하여 테스트
- 오류 수정이 쉽고 인터페이스 관련 오류를 완전히 테스트할 가능성이 높음
- 종류
  - 하향식
  - 상향식
  - 혼합식

> ⭐ `점진적 = 하향식 / 상향식 / 혼합식`

---

### 2. 하향식 통합 테스트(Top Down Integration Test)
- 프로그램의 **상위 모듈에서 하위 모듈 방향**으로 통합하며 테스트
- 깊이 우선 또는 너비 우선 방식 사용
- 아직 개발되지 않은 하위 모듈 대신 **스텁(Stub)** 사용

#### 절차
1. 주요 제어 모듈을 테스트 드라이버로 사용하고 종속 모듈은 Stub으로 대체
2. 깊이 우선 또는 너비 우선 방식에 따라 하위 모듈의 Stub을 한 번에 하나씩 실제 모듈로 교체
3. 모듈이 통합될 때마다 테스트
4. 새로운 오류가 발생하지 않음을 보장하기 위해 **회귀 테스트**

> ⭐ `Top-Down = 상 → 하 / Stub 필요`

---

### 3. 상향식 통합 테스트(Bottom Up Integration Test)
- 프로그램의 **하위 모듈에서 상위 모듈 방향**으로 통합하며 테스트
- 가장 하위 단계의 모듈부터 통합
- 상위 모듈 역할을 대신하는 **드라이버(Driver)** 필요

#### 절차
1. 하위 모듈을 클러스터(Cluster)로 결합
2. 상위 모듈의 입·출력을 확인하기 위한 Driver 작성
3. 통합된 클러스터 단위로 테스트
4. 테스트 완료 후 상위 구조로 이동하며 Driver를 실제 모듈로 교체

> ⭐ `Bottom-Up = 하 → 상 / Driver 필요`

---

### 4. Stub과 Driver 비교

| 구분 | **Driver** | **Stub** |
|---|---|---|
| 역할 | 테스트 대상 **하위 모듈을 호출**하고 매개변수를 전달하며 결과 확인 | 테스트 대상 상위 모듈이 호출하는 **하위 모듈 역할을 임시 대체** |
| 필요 시점 | 상위 모듈이 없을 때 | 하위 모듈이 없을 때 |
| 사용 방식 | **상향식(Bottom-Up)** | **하향식(Top-Down)** |

> ⭐ `Stub = 하위 대신`  
> ⭐ `Driver = 상위 대신`

---

### 5. 혼합식 통합 테스트
- 하위 수준에서는 **상향식**
- 상위 수준에서는 **하향식**
- 두 방식을 혼합하여 최적의 테스트 지원
- **샌드위치(Sandwich)식 통합 테스트**라고도 함

> ⭐ `혼합식 = Sandwich`

---

### 6. 회귀 테스트(Regression Testing)
- 통합 테스트로 인해 변경된 프로그램에서 **새로운 오류가 발생하지 않았는지 확인하기 위해 기존 테스트를 반복**
- 수정·변경된 모듈이나 컴포넌트에서 새로운 오류가 발생하지 않았음을 보증
- 모든 테스트 케이스를 반복하면 시간·비용이 많이 들 수 있으므로 대표적인 테스트 케이스를 선정하여 수행

#### 회귀 테스트 케이스 선정 방법
- 애플리케이션의 모든 기능을 수행할 수 있는 대표 테스트 케이스
- 변경으로 인해 영향을 받을 가능성이 높은 기능의 테스트 케이스
- 실제 수정이 발생한 모듈이나 컴포넌트에 사용하는 테스트 케이스

> ⭐ `Regression = 수정 후 기존 기능에 새 오류가 없는지 재시험`

---

## SECTION 049. 테스트 케이스 / 테스트 시나리오 / 테스트 오라클

### 1. 테스트 케이스(Test Case)
- 구현된 소프트웨어가 사용자의 요구사항을 정확하게 준수했는지 확인하기 위해 설계된
  - 입력값
  - 실행 조건
  - 기대 결과

  등으로 구성된 테스트 항목 명세서
- 테스트 목표·방법을 결정하고 테스트 케이스를 작성
- 시스템 설계 단계에서 작성하는 것이 가장 이상적

> ⭐ `Test Case = 입력값 + 실행 조건 + 기대 결과`

---

### 2. 테스트 케이스 작성 순서

```text
1. 테스트 계획 검토 및 자료 확보
2. 위험 평가 및 우선순위 결정
3. 테스트 요구사항 정의
4. 테스트 구조 설계 및 테스트 방법 결정
5. 테스트 케이스 정의
6. 테스트 케이스 타당성 확인 및 유지보수
```

#### ① 테스트 계획 검토 및 자료 확보
- 테스트 대상 범위와 접근 방법 확인
- 시스템 요구사항·기능 명세 검토

#### ② 위험 평가 및 우선순위 결정
- 결함 위험 정도에 따라 우선순위 결정
- 우선순위에 맞춰 테스트할 항목 결정

#### ③ 테스트 요구사항 정의
- 테스트 대상 시스템의 사용자 요구사항·기능 등을 분석

#### ④ 테스트 구조 설계 및 테스트 방법 결정
- 테스트 케이스 형식과 분류 방법 결정
- 테스트 절차·장비·도구·테스트 문서화 방법 결정

#### ⑤ 테스트 케이스 정의
- 요구사항에 따라 입력값, 실행 조건, 예상 결과 등을 기술

#### ⑥ 타당성 확인 및 유지보수
- 기능 또는 환경 변화에 따라 테스트 케이스를 검토
- 유효성 판단

> ⭐ 작성 순서 → `계위요구정타`

---

### 3. 테스트 시나리오(Test Scenario)
- 테스트 케이스를 적용하는 **순서에 따라 여러 테스트 케이스를 묶은 집합**
- 테스트 케이스의 동작 순서를 정하는 구체적인 절차를 명세한 문서
- 테스트 수행 절차를 미리 정하여 테스트 항목을 빠짐없이 수행할 수 있도록 함

> ⭐ `Test Scenario = 여러 Test Case의 실행 순서`

---

### 4. 테스트 시나리오 작성 시 유의 사항
- 시스템·모듈·항목 등 여러 개의 시나리오로 분리하여 작성
- 사용자 요구사항과 설계 문서 등을 토대로 작성
- 각 시나리오는
  - 테스트할 순서
  - 분류
  - 테스트 데이터
  - 테스트 케이스
  - 예상 결과
  - 확인 항목

  등을 포함
- **유스케이스(Use Case)** 간 업무 흐름이 정상적인지 테스트할 수 있도록 작성
- 개발된 모듈 또는 프로그램 간 연계가 정상적으로 동작하는지 확인할 수 있도록 상세하게 작성

---

### 5. 테스트 오라클(Test Oracle)
- 테스트 결과가 올바른지 판단하기 위해 **사전에 정의된 참 값을 대입하여 비교하는 기법 및 활동**
- 테스트 결과가 정상인지 판단하기 위해 예상 결과를 계산하거나 확인
- 모든 테스트 케이스에 적용할 수 있는 오라클을 만들기 어려움
- 수학적 기법이나 자동화 기능을 활용 가능

> ⭐ `Test Oracle = 실제 결과와 비교할 "참값" 제공`

---

### 6. 테스트 오라클의 종류

| 종류 | 핵심 |
|---|---|
| **참(True) 오라클** | 모든 테스트 케이스의 입력값에 대해 **기대 결과를 모두 제공** |
| **샘플링(Sampling) 오라클** | 특정 테스트 케이스의 입력값에 대해서만 **기대 결과 제공** |
| **휴리스틱(Heuristic) 오라클** | 샘플링 오라클을 개선 / 특정 입력은 정확한 결과, 나머지는 추정 처리 |
| **일관성(Consistent) 검사 오라클** | 애플리케이션 변경 전·후 테스트 결과가 **동일한지 확인** |

> ⭐ `True = 전부`  
> ⭐ `Sampling = 일부`  
> ⭐ `Heuristic = 일부 정확 + 나머지 추정`  
> ⭐ `Consistent = 변경 전후 비교`

---

## SECTION 050. 테스트 자동화 도구

### 1. 테스트 자동화의 개요
- 반복적으로 수행하던 테스트 절차를 **스크립트 형태로 구현하여 자동 수행**
- 사람이 직접 수행하는 작업을 줄여 쉽고 효율적으로 테스트 가능
- **휴먼 에러(Human Error)** 감소
- 테스트 정확성 유지
- 테스트 품질 향상

> ⭐ `테스트 자동화 = 반복 테스트를 Script로 자동 수행`

---

### 2. 테스트 자동화 도구의 장점 / 단점

#### 장점
- 반복 작업 자동화 → **인력·시간 절감**
- 향상된 테스트 품질 보장
- 사용자의 요구사항을 충실히 검증 가능
- 테스트 결과에 대한 객관적인 평가 기준 제공
- 테스트 결과를 다양한 표시 형태로 제공
- UI가 없는 서비스도 정밀 테스트 가능

#### 단점
- 도구 사용 방법에 대한 교육·학습 필요
- 도구별 테스트 프로세스에 맞는 별도의 **커스터마이징 필요**
- 비공개 상용 도구는 **구매·유지 비용** 필요

> ⭐ `장점 = 시간·인력 절감 / 반복 정확성`  
> ⭐ `단점 = 학습 / 커스터마이징 / 비용`

---

### 3. 테스트 자동화 수행 시 고려사항
- 테스트 절차를 고려하여 **재사용·측정이 불가능한 테스트 프로그램은 제외**
- 모든 테스트 과정을 자동화할 수 없으므로 용도에 맞는 적절한 도구 선택
- 도구 환경 설정 및 습득 기간을 고려하여 프로젝트 일정 계획
- 초기 자동화 도입 시 테스트 엔지니어의 **투입 시기**를 계획

---

### 4. 테스트 자동화 도구의 유형

#### 정적 분석 도구(Static Analysis Tools)
- 프로그램을 **실행하지 않고** 분석
- 소스 코드에 대한
  - 코딩 표준
  - 코딩 스타일
  - 코드 복잡도
  - 남아 있는 결함

  등을 발견
- 작성된 소스 코드를 이해하고 있어야 분석 가능

#### 테스트 케이스 생성 도구(Test Case Generation Tools)
- 자료 흐름, 기능, 입력 도메인 등을 분석하여 **테스트 데이터를 생성**

대표 방식
- **자료 흐름도** - 소스 코드의 자료 흐름 분석
- **기능 테스트** - 주어진 기능의 모든 가능 상태 파악
- **입력 도메인 분석** - 입력 데이터의 도메인을 분석하여 테스트 데이터 생성
- **랜덤 테스트** - 입력값을 무작위로 생성

#### 테스트 실행 도구(Test Execution Tools)
- **스크립트 언어를 이용하여 테스트 실행**
- 테스트 데이터와 수행 방법을 포함한 Script 작성

##### 데이터 주도 접근 방식
- 스프레드시트 등에 테스트 데이터를 저장하고 이를 읽어 실행
- 동일 테스트를 다양한 데이터로 반복 가능

##### 키워드 주도 접근 방식
- 테스트 수행 동작을 나타내는 **키워드**와 테스트 데이터를 분리하여 저장
- 키워드를 이용해 테스트 정의 가능

#### 성능 테스트 도구(Performance Test Tools)
- 애플리케이션의 처리량, 응답 시간, 경과 시간 등을 인위적으로 적용한 가상 사용자를 통해 측정

#### 테스트 통제 도구(Test Control Tools)
- 테스트 계획 및 관리, 테스트 수행, 결함 관리 등을 지원

#### 테스트 하네스 도구(Test Harness Tools)
- 테스트가 실행될 환경을 **시뮬레이션**
- 컴포넌트·모듈을 테스트하는 환경의 일부분 또는 전체를 지원

> ⭐ 자동화 도구 → `정적 분석 / 케이스 생성 / 실행 / 성능 / 통제 / 하네스`

---

### 5. 테스트 하네스(Test Harness) 구성 요소

| 구성 요소 | 핵심 |
|---|---|
| **테스트 드라이버(Test Driver)** | 하위 모듈을 호출하고 매개변수를 전달하며 결과를 출력 |
| **테스트 스텁(Test Stub)** | 제어 모듈이 호출하는 하위 모듈 역할을 임시 수행 |
| **테스트 슈트(Test Suites)** | 테스트 대상 컴포넌트·시스템에 사용되는 테스트 케이스의 집합 |
| **테스트 케이스(Test Case)** | 입력값·실행 조건·기대 결과 등으로 구성 |
| **테스트 스크립트(Test Script)** | 자동화된 테스트 실행 절차에 대한 명세 |
| **목 오브젝트(Mock Object)** | 사전에 사용자의 행위를 조건부로 입력해 두고 상황에 맞는 예정된 행위를 수행하는 객체 |

> ⭐ `Harness = Driver / Stub / Suites / Case / Script / Mock Object`

## SECTION 051. 결함 관리

### 1. 결함(Fault)의 정의
- **결함(Fault)** - 오류 발생, 작동 실패 등과 같이 소프트웨어가 개발자가 설계한 것과 **다르게 동작하거나 다른 결과가 발생하는 것**
- 사용자가 예상한 결과와 실제 결과가 다르거나, 업무 내용의 불일치 등으로 변경이 필요한 부분도 포함

> ⭐ `Fault = 예상 결과 ≠ 실제 결과`

---

### 2. 결함 관리 프로세스

```text
결함 관리 계획
→ 결함 기록
→ 결함 검토
→ 결함 수정
→ 결함 재확인
→ 결함 상태 추적 및 모니터링
→ 최종 결함 분석 및 보고서 작성
```

#### ① 결함 관리 계획
- 전체 프로세스의 일정·인력·업무 프로세스 확보 계획 수립

#### ② 결함 기록
- 테스터가 발견한 결함을 결함 관리 DB에 등록

#### ③ 결함 검토
- 등록된 결함을 테스터·프로그램 리더·QA 담당자 등이 검토하여 결함 여부 확인

#### ④ 결함 수정
- 개발자가 전달받은 결함 수정

#### ⑤ 결함 재확인
- 테스터가 수정 내용을 확인하고 다시 테스트

#### ⑥ 결함 상태 추적 및 모니터링
- 결함 관리 DB를 이용하여 프로젝트별 결함 유형·발생률 등 추적
- 결함 상태 변화 모니터링

#### ⑦ 최종 결함 분석 및 보고서 작성
- 결함 정보를 분석하여 보고서 작성 후 결함 관리 종료

> ⭐ `계 → 기 → 검 → 수 → 재 → 추 → 보`

---

### 3. 결함 상태 추적
- 테스트에서 발견된 결함은 해결될 때까지 **상태 변화를 지속적으로 추적·관리**

#### 결함 관련 측정 지표

| 지표 | 핵심 |
|---|---|
| **결함 분포** | 모듈 또는 컴포넌트의 특정 속성에 해당하는 결함 수 측정 |
| **결함 추세** | 테스트 진행 시간에 따른 결함 수의 추이 분석 |
| **결함 에이징** | 특정 결함 상태가 지속되는 시간 측정 |

> ⭐ `분포 = 어디에 많은가`  
> ⭐ `추세 = 시간에 따라 어떻게 변하나`  
> ⭐ `에이징 = 얼마나 오래 남아 있나`

---

### 4. 결함 추적 순서

| 상태 | 의미 |
|---|---|
| **결함 등록(Open)** | 테스터 또는 QA 담당자에 의해 결함 등록 |
| **결함 검토(Reviewed)** | 등록된 결함을 테스터·QA·프로그램 리더 등이 검토 |
| **결함 할당(Assigned)** | 결함을 수정할 개발자와 해결 담당자에게 할당 |
| **결함 수정(Resolved)** | 개발자가 결함 수정을 완료 |
| **결함 조치 보류(Deferred)** | 수정이 불가능하거나 연기된 상태 |
| **결함 종료(Closed)** | 재시험 결과 결함이 해결되어 QA 담당자가 종료 승인 |
| **결함 해지(Clarified)** | 검토 결과 결함이 아니라고 판단 |

> ⭐ 기본 흐름 → `Open → Reviewed → Assigned → Resolved → Closed`  
> ⭐ `Deferred = 보류` / `Clarified = 결함 아님`

---

### 5. 결함 분류

| 분류 | 핵심 |
|---|---|
| **시스템 결함** | 시스템 다운, 애플리케이션 작동 정지, 응답 시간 지연, DB 오류 등 |
| **기능 결함** | 사용자 요구사항 미반영, 기능 미구현, 잘못된 비즈니스 프로세스, 스크립트 오류 등 |
| **GUI 결함** | UI 비일관성, 데이터 타입 표시 오류, 잘못된 커서·메시지 등 |
| **문서 결함** | 사용자 요구사항·기능 요구사항과 불일치한 문서, 사용자 이해를 방해하는 문서 내용 등 |

> ⭐ `결함 분류 = 시스템 / 기능 / GUI / 문서`

### 6. 테스트 단계별 유입 결함
- **기획 시 유입되는 결함**
  - 사용자 요구사항 표준 미준수
  - 요구사항 불명확·불완전·불일치
- **설계 시 유입되는 결함**
  - 설계 표준 미준수
  - 기능 설계 불명확·불완전·불일치
- **코딩 시 유입되는 결함**
  - 코딩 표준 미준수
  - 기능 불일치·불완전
  - 데이터·인터페이스 결함 등
- **테스트 부족으로 유입되는 결함**
  - 테스트 시 테스트 완료 기준 미준수
  - 테스트팀과 개발팀 의사소통 부족
  - 개발자 코딩 실수 등

### 7. 결함 심각도

|---|---|

> ⭐ `High = 시스템 핵심 영향`  
> ⭐ `Low = UI·표시 등 영향 적음`

- 일반적으로
  - `Critical`
  - `High`
  - `Medium`
  - `Low`

  등으로 분류

> ⭐ `심각도 = 영향 크기`  
> ⭐ `우선순위 = 얼마나 빨리 고칠 것인가`

## SECTION 052. 복잡도

### 1. 복잡도의 개요
- **복잡도(Complexity)** - 시스템·시스템 구성 요소 또는 소프트웨어의 **복잡한 정도**
- 시스템 또는 소프트웨어를 어느 정도 수준까지 테스트해야 하는지 또는 개발하는 데 어느 정도의 자원이 필요한지 예측하는 데 사용
- 복잡도가 높으면 장애 가능성이 커질 수 있으므로 정밀한 테스트로 오류 제거 필요
- 주요 측정 방법
  - **LOC(Line of Code)**
  - **순환 복잡도(Cyclomatic Complexity)**

> ⭐ `복잡도 ↑ → 오류·장애 가능성 ↑`

---

### 2. 시간 복잡도
- 알고리즘 실행 시간, 즉 알고리즘을 수행하기 위해 **프로세스가 수행하는 연산 횟수를 수치화한 것**
- 시간 복잡도가 낮을수록 실행시간이 짧고, 높을수록 길어짐
- 알고리즘의 실행시간은 하드웨어 성능이나 언어 종류에 따라 달라질 수 있으므로 **점근 표기법** 사용

---

### 3. 점근 표기법

| 표기법 | 핵심 |
|---|---|
| **빅오(Big-O)** | 실행시간의 **최악의 경우**를 표현 |
| **세타(Big-Θ)** | 실행시간의 **평균적인 경우**를 표현 |
| **오메가(Big-Ω)** | 실행시간의 **최상의 경우**를 표현 |

> ⭐ `O = 최악`  
> ⭐ `Θ = 평균`  
> ⭐ `Ω = 최상`

---

### 4. 빅오 표기법(Big-O Notation)
- 알고리즘 실행시간이 **최악일 때**를 표현
- 입력값 증가에 따른 알고리즘의 성능을 예측할 때 사용

#### 대표 시간 복잡도

| 시간 복잡도 | 핵심 / 대표 예 |
|---|---|
| **O(1)** | 입력 크기와 관계없이 일정 / Stack의 Push·Pop |
| **O(log n)** | 단계가 진행될수록 대상이 절반씩 감소 / Binary Tree, Binary Search |
| **O(n)** | 입력 수만큼 반복 / 단일 for문 |
| **O(n log n)** | n번 처리하며 각 단계가 log n / Heap Sort, 2-Way Merge Sort |
| **O(n²)** | 이중 반복 구조 / 삽입·쉘·선택·버블 정렬 등의 경우 |
| **O(2ⁿ)** | 입력이 증가할수록 수행량이 지수적으로 증가 / Fibonacci Sequence |

#### 효율 좋은 순서
```text
O(1)
< O(log n)
< O(n)
< O(n log n)
< O(n²)
< O(2ⁿ)
```

> ⭐ `왼쪽일수록 효율적`

---

### 5. 순환 복잡도(Cyclomatic Complexity)
- 한 프로그램의 **논리적인 복잡도를 측정하기 위한 척도**
- **맥케이브 순환도(McCabe's Cyclomatic)** 또는 **맥케이브 복잡도**라고도 함
- 제어 흐름도 이론을 기초로 함
- 순환 복잡도를 이용하면 계산된 값은 프로그램의 **독립적인 경로 수**를 의미
- 모든 경로가 한 번 이상 수행되었음을 보장하기 위한 **최소 테스트 횟수의 상한선** 설정 가능

#### 계산 방법 1
- 제어 흐름도에서 **화살표로 구분되는 영역의 수**

#### 계산 방법 2
```text
V(G) = E - N + 2
```

- `E` = 화살표(Edge)의 수
- `N` = 노드(Node)의 수

> ⭐ `Cyclomatic = 영역 수`  
> ⭐ `V(G) = E - N + 2`

## SECTION 053. 애플리케이션 성능 개선

### 1. 소스 코드 최적화
- **소스 코드 최적화** - 나쁜 코드(Bad Code)를 배제하고 **클린 코드(Clean Code)**로 작성하는 것

#### 클린 코드(Clean Code)
- 누구나 쉽게 이해하고 수정·추가할 수 있는
  - 단순한 코드
  - 명료한 코드

  를 의미

#### 나쁜 코드(Bad Code)

##### 스파게티 코드(Spaghetti Code)
- 코드의 로직이 서로 복잡하게 얽혀 이해하기 어려운 코드

##### 외계인 코드(Alien Code)
- 아주 오래되었거나 참고문서·개발자가 없어 유지보수 작업이 어려운 코드

> ⭐ `Spaghetti = 로직이 복잡하게 얽힘`  
> ⭐ `Alien = 오래되고 자료·개발자 없어 유지보수 어려움`

---

### 2. 클린 코드 작성 원칙

| 원칙 | 핵심 |
|---|---|
| **가독성** | 누구든지 코드를 쉽게 읽을 수 있도록 작성 / 이해하기 쉬운 용어·들여쓰기 |
| **단순성** | 코드를 간단하게 작성 / 한 번에 한 가지 처리 / 클래스·메소드·함수 최소 단위 |
| **의존성 배제** | 코드가 다른 모듈에 미치는 영향을 최소화 / 코드 변경 시 다른 부분 영향 방지 |
| **중복성 최소화** | 코드의 중복 최소화 / 중복된 코드는 삭제하고 공통 코드 사용 |
| **추상화** | 상위 클래스·메소드에서는 간략하게 애플리케이션 특성 표현, 상세 내용은 하위에서 구현 |

> ⭐ 클린 코드 원칙 → `가단의중추`  
> `가독성 / 단순성 / 의존성 배제 / 중복 최소 / 추상화`

---

### 3. 소스 코드 최적화 유형

#### 클래스 분할 배치
- 하나의 클래스는 **하나의 역할만 수행**
- 응집도를 높이고 크기를 작게 작성

#### 느슨한 결합(Loosely Coupled)
- 인터페이스 클래스를 이용하여 추상화된 자료구조와 메소드를 구현
- 클래스 간 **의존성을 최소화**

> ⭐ `응집도 ↑ / 결합도 ↓`

---

### 4. 소스 코드 작성 규칙
- **코딩 함수 준수**
  - 코드 작성 시 일정한 형식을 준수
- **전역 변수 사용**
  - 가능한 한 최소화
- **복잡성이 높은 중복 함수 사용 지양**
- 호출하는 함수와 호출되는 함수의 위치를 이해하기 쉽게 배치
- 지역 변수는 가능한 한 해당 블록 가까이에 선언
- **좋은 이름 사용**
  - 변수·함수 이름은 기억하기 쉬운 이름
  - 발음하기 쉬운 용어
  - 접두어·약어 사용 시 규칙 정의
- **적절한 주석문 사용**
  - 중요한 코드에 주석 사용
  - 소스 코드 자체가 이해하기 쉽다면 불필요한 주석은 줄임

---

### 5. 소스 코드 품질 분석 도구
- 소스 코드의
  - 코딩 스타일
  - 코딩 표준
  - 코드 복잡도
  - 메모리 누수 현상
  - 스레드 결함

  등을 발견하기 위해 사용하는 도구

#### 정적 분석 도구
- 작성된 소스 코드를 **실행하지 않고 분석**
- 코딩 표준이나 코딩 스타일, 결함 등을 확인
- 개발 초기 단계에서 사용
- 개발된 소스 코드의 품질을 검증하는 차원에서 사용
- 자료 흐름이나 논리 흐름을 분석하여 비정상적인 패턴을 찾을 수 있음

대표 도구
- `pmd`
- `cppcheck`
- `SonarQube`
- `checkstyle`
- `ccm`
- `cobertura`

> ⭐ `정적 = 실행 X`

#### 동적 분석 도구
- 작성된 소스 코드를 **실행하여 분석**
- 코드에 존재하는
  - 메모리 누수
  - 스레드 결함

  등을 분석

대표 도구
- `Avalanche`
- `Valgrind`

> ⭐ `동적 = 실행 O`

---

### 6. 소스 코드 품질 분석 도구의 종류

| 도구 | 핵심 |
|---|---|
| **pmd** | 소스 코드의 미사용 변수, 최적화되지 않은 코드 등 결함 유발 가능 코드 검사 |
| **cppcheck** | C/C++ 코드의 메모리 누수, 오버플로우 등 분석 |
| **SonarQube** | 중복 코드, 복잡도, 코딩 설계 등을 분석하는 소스 분석 플랫폼 |
| **checkstyle** | Java 소스 코드가 코딩 표준을 따르고 있는지 검사 / 규칙 확장 가능 |
| **ccm** | 다양한 언어의 코드 복잡도를 분석 |
| **cobertura** | Java 코드의 소스 코드 복잡도·테스트 커버리지 측정 |
| **Avalanche** | Valgrind 프레임워크 및 STP 기반으로 프로그램 결함·취약점 분석 |
| **Valgrind** | 프로그램 내 존재하는 메모리·스레드 결함 등을 분석 |

> ⭐ `pmd~cobertura = 정적 분석 계열`  
> ⭐ `Avalanche / Valgrind = 동적 분석`
