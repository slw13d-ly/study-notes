# 03. 소프트웨어 개발 보안 구축

## SECTION 145. Secure SDLC

### 1. Secure SDLC의 개요
- **Secure SDLC** - 보안상 안전한 소프트웨어를 개발하기 위해 **SDLC에 보안 강화를 위한 프로세스를 포함한 것**
- 소프트웨어 유지보수 단계에서 보안 이슈를 해결하는 데 드는 비용을 최소화하기 위해 등장
- 요구사항 분석, 설계, 구현, 테스트, 유지보수 등 **SDLC 전체 단계에 걸쳐 보안 활동을 수행**

> ⭐ `Secure SDLC = SDLC 전 단계에 보안 활동을 통합`

---

### 2. Secure SDLC의 대표적인 방법론

| 방법론 | 핵심 |
|---|---|
| **CLASP** | Secure Software사에서 개발 / SDLC 초기 단계부터 보안을 강화하기 위한 방법론 / 활동 중심·역할 기반 프로세스 |
| **SDL** | Microsoft에서 안전한 소프트웨어 개발을 위해 기존 SDLC를 개선한 방법론 / 전통적인 나선형 모델 기반 |
| **Seven Touchpoints** | SW 보안의 모범사례를 SDLC에 통합 / 설계·개발 과정의 산출물에 위험 분석·테스트 수행 |

> ⭐ `CLASP / SDL / Seven Touchpoints`

---

### 3. 요구사항 분석 단계의 보안 활동
- 요구사항 분석 단계에서 **보안 항목에 해당하는 요구사항을 식별**
- 전송되는 정보가 가지는 **보안 수준을 보안 요소별 등급으로 분류**
- 조직의 정보보호 정책을 참고하여
  - 적용 가능한 보안 정책 항목
  - 요구 수준
  - 세부 내용

  등을 문서화

> ⭐ `요구 분석 = 보안 요구사항 식별 + 보안 수준 분류 + 정책 문서화`

---

### 4. 주요 보안 요소

| 보안 요소 | 핵심 |
|---|---|
| **기밀성(Confidentiality)** | 인가된 사용자에게만 정보·자원 접근 허용 / 정보 노출 방지 |
| **무결성(Integrity)** | 시스템 내 정보가 인가된 사용자만 수정 가능 |
| **가용성(Availability)** | 인가된 사용자가 언제든지 자원을 사용할 수 있어야 함 |
| **인증(Authentication)** | 사용자가 합법적인 사용자인지 확인 |
| **부인 방지(Non-Repudiation)** | 데이터 송·수신자가 송·수신 사실을 부인할 수 없도록 증거 제공 |

> ⭐ 보안 3대 요소 → `기밀성 / 무결성 / 가용성`  
> ⭐ 추가 요소 → `인증 / 부인 방지`

---

### 5. 설계 단계에서의 보안 활동
- 요구사항 분석 단계에서 식별된 보안 요구사항을 **소프트웨어 설계서에 반영**
- 발생할 수 있는 위험을 식별하고
  - 보안대책
  - 소요예산
  - 사고 발생 시 영향 범위·대응책

  등을 수립
- 네트워크·서버·물리적 보안·개발 프로그램 등 **환경별 보안 기준을 수립하여 설계에 반영**

#### 환경별 보안 예
- **네트워크** - 외부 사이버 공격 방지를 위한 네트워크 분리·방화벽 등
- **서버** - 안전한 운영체제 사용, 보안 업데이트, 외부 접속 점검
- **물리적 보안** - 출입 통제, 개발 공간 제한, 폐쇄회로 등 감시 설비
- **개발 프로그램** - 허가되지 않은 프로그램 통제, 지속적인 데이터 무결성 검사

> ⭐ `설계 = 위험 식별 → 보안 대책 수립 → 설계서 반영`

---

### 6. 구현 단계에서의 보안 활동
- **표준 코딩 정의서와 소프트웨어 개발 보안 가이드**를 준수하여 개발
- 개발 과정 중 지속적인 **단위 테스트(Unit Test)**를 통해 보안 취약점 최소화
- 코드 점검·소스 코드 진단을 통해 **소스 코드 안정성 확보**

#### 시큐어 코딩(Secure Coding)
- 구현 단계에서 발생 가능한 보안 취약점을 최소화하기 위해 **보안 요소를 고려하여 코딩하는 것**
- 보안 취약점을 사전에 대응하여 안정성·신뢰성 확보
- 개발자의 지속적인 보안 교육 필요

> ⭐ `Secure Coding = 구현 단계에서 보안 취약점을 예방하는 코딩`

---

### 7. 테스트 단계에서의 보안 활동
- 설계 단계에서 작성한 보안 설계서를 기반으로 **보안 사항이 정확히 반영되었는지 점검**
- 동적 분석 도구 또는 모의 침투 테스트 등을 통해 설계 단계에서 식별된 위협 해결 여부 검증
- 구현 단계에서 새롭게 발생한 위험·취약점도 점검
- 테스트 결과 발견된 취약점은 개발자에게 전달하여 수정

> ⭐ `테스트 = 보안 설계 반영 여부 + 취약점 검증`

---

### 8. 유지보수 단계에서의 보안 활동
- 이전 과정에서 수행했어도 발생할 수 있는 보안 사고를 식별
- 사고 발생 시 원인을 해결하고 **보안 패치를 실시**

> ⭐ `유지보수 = 보안 사고 식별 + 원인 해결 + Patch`

---

## SECTION 146. 세션 통제

### 1. 세션 통제의 개요
- **세션(Session)** - 서버와 클라이언트의 연결
- **세션 통제** - 세션의 연결·연결로 인해 발생하는 정보를 관리하는 것
- 세션 통제는 요구사항 분석 및 설계 단계에서 진단해야 하는 보안 점검 항목
- 주요 보안 약점
  - 불충분한 세션 관리
  - 잘못된 세션에 의한 정보 노출

> ⭐ `세션 통제 = Server ↔ Client 연결 정보 관리`

---

### 2. 불충분한 세션 관리
- 일정한 규칙이 존재하는 **세션ID가 발급되거나 타임아웃이 너무 길게 설정된 경우** 발생
- 공격자가 세션ID를 추측·획득하면 정상 사용자처럼 시스템 기능을 이용하거나 중요 정보에 접근 가능

#### 세션 하이재킹(Session Hijacking)
- 서버에 접속 중인 클라이언트의 **세션 정보를 가로채는 공격**
- 대표 방식
  - 비정상적 연결을 RST 패킷 등으로 종료시키고 공격자가 연결
  - 정상 서버와 상호 간의 동기화된 시퀀스 번호를 이용
- 탐지 방법
  - 비동기화 상태 탐지
  - ACK Storm 탐지
  - 패킷의 유실·재전송 증가 탐지
  - 예상하지 못한 접속의 리셋 탐지

> ⭐ `Session Hijacking = 정상 사용자의 Session 탈취`

---

### 3. 잘못된 세션에 의한 정보 노출
- 다중 스레드(Multi-Thread) 환경에서 **멤버 변수에 정보를 저장**할 때 발생 가능
- 싱글톤 패턴에서 발생하는 레이스 컨디션으로 동기화 오류가 발생하거나 멤버 변수의 정보가 노출될 수 있음
- **멤버 변수 대신 지역 변수 사용** 또는 변수 범위 제한으로 예방

> ⭐ `잘못된 세션 정보 노출 → 멤버 변수보다 지역 변수 사용`

---

### 4. 세션 설계 시 고려 사항
- 시스템의 **모든 페이지에서 로그아웃 가능**하도록 UI 구성
- 로그아웃 요청 시 해당 세션이 **완전히 제거**
- 세션 타임아웃
  - 중요도가 높으면 **2~5분**
  - 중요도가 낮으면 **15~30분**
- 이전 세션이 종료되지 않으면 새 세션이 생성되지 못하도록 설계
- 중복 로그인을 허용하지 않는 경우 중복 접근에 대한 세션 관리 정책 수립
- 패스워드 변경 시 활성화된 세션을 삭제하고 재할당

---

### 5. 세션ID 관리 방법
- 안전한 서버에서 **최소 128비트 길이**로 생성
- 예측이 불가능하도록 안전한 난수 알고리즘 사용
- 세션ID가 노출되지 않도록 **URL Rewrite 기능을 사용하지 않는 방향**으로 설계
- 로그인 시 로그인 전의 세션ID를 삭제하고 **새로 재할당**
- 장기간 접속 중인 세션ID도 **주기적으로 재할당**

> ⭐ `Session ID = 128bit 이상 + 예측 불가 + 재할당`

---

## SECTION 147. 입력 데이터 검증 및 표현

### 1. 입력 데이터 검증 및 표현의 개요
- 입력 데이터로 인해 발생하는 문제를 예방하기 위해 구현 단계에서 검증해야 하는 보안 점검 항목
- 입력 데이터에 대한 검증 체계를 갖추고 검증되지 않은 데이터가 처리되지 않도록 구현
- 입력값이 지정된 자료형에 맞는지 확인하고 **허용된 문자 집합(Character Set)**을 사용

> ⭐ `입력 검증 = 외부 입력을 신뢰하지 말고 검증 후 처리`

---

### 2. 입력 데이터 검증 및 표현의 주요 보안 약점

| 보안 약점 | 핵심 |
|---|---|
| **SQL 삽입(SQL Injection)** | 입력값에 SQL을 삽입하여 DB 정보를 유출·조작 |
| **경로 조작 및 자원 삽입** | 입력값을 이용해 서버 내부 경로·자원에 접근 또는 수정·삭제 |
| **크로스사이트 스크립팅(XSS)** | 웹 페이지에 악의적인 Script를 삽입하여 사용자 정보 탈취·비정상 기능 수행 |
| **운영체제 명령어 삽입** | 외부 입력값으로 시스템 명령어 실행을 유도해 권한 탈취·시스템 장애 유발 |
| **위험한 형식 파일 업로드** | 실행 가능한 파일·악성 파일 등을 업로드하여 시스템 손상 |
| **신뢰되지 않는 URL 주소로 자동접속 연결** | 입력값으로 외부 사이트 주소를 조작하여 피싱 사이트 등으로 연결 |
| **메모리 버퍼 오버플로** | 할당된 메모리 범위를 넘어서 데이터를 저장해 인접 정보·리턴 주소 등을 변경 |

> ⭐ 입력 검증 주요 약점 → `SQL 삽입 / 경로 삽입 / XSS / 명령어 삽입 / 위험 파일 / URL / Buffer Overflow`

---

### 3. 메모리 버퍼 오버플로(Buffer Overflow)
- 연속된 메모리 공간을 사용하는 프로그램에서 **할당된 범위를 넘어선 위치에 자료를 저장**하여 발생
- 인접 데이터나 복귀 주소(Return Address)가 변경되어
  - 비정상 동작
  - 공격자의 악성 코드 실행

  가능
- 예방
  - 버퍼 크기를 충분히 설정
  - 설정 범위 내에서만 데이터를 사용하도록 검사

> ⭐ `Buffer Overflow = 메모리 경계 초과 쓰기`

---

## SECTION 148. 보안 기능

### 1. 보안 기능의 개요
- 구현 단계에서 코딩하는
  - 인증
  - 접근제어
  - 기밀성
  - 암호화

  등을 올바르게 구현하기 위한 보안 점검 항목
- 각 보안 기능은 **서비스 환경이나 취급 데이터에 맞게 처리**
- 사용자별 중요도를 구분하여 차별화된 인증 방법 적용
- 인증된 사용자에게 기능·데이터별 접근 권한을 부여
- 중요 정보의 변조·삭제·오남용을 막기 위해 안전한 암호화 기술 적용

> ⭐ `보안 기능 = 인증 + 접근제어 + 기밀성 + 암호화`

---

### 2. 보안 기능의 주요 보안 약점

| 보안 약점 | 핵심 |
|---|---|
| **적절한 인증 없이 중요 기능 허용** | 중요 정보·기능에 인증 없이 접근 가능 |
| **부적절한 인가** | 접근 권한 검사가 없거나 부적절하여 권한이 없는 기능 수행 가능 |
| **중요 자원에 대한 잘못된 권한 설정** | 권한 설정 오류로 중요 자원을 읽거나 수정 가능 |
| **취약한 암호화 알고리즘 사용** | 안전하지 않은 알고리즘을 사용하여 암호 해독 가능 |
| **중요정보 평문 저장 및 전송** | 중요 정보를 암호화하지 않고 저장·전송하여 노출 가능 |
| **하드코드된 비밀번호** | 소스 코드 내부에 비밀번호를 직접 작성하여 노출 위험 |

> ⭐ `인증 / 인가 / 권한 / 암호 알고리즘 / 평문 / 하드코딩` 확인

---

### 3. 하드코드된 비밀번호
- 소스 코드 내부에 패스워드가 직접 입력되어 있으면 프로그램을 분석하여 비밀번호를 알아낼 수 있음
- 비밀번호는 별도 파일 등에 안전하게 저장하고 암호화하여 사용하는 방식으로 예방

> ⭐ `Password를 Source Code에 직접 쓰지 않기`

---

## SECTION 149. 에러처리

### 1. 에러처리의 개요
- 소프트웨어 실행 중 발생할 수 있는 **오류(Error)를 어떻게 정의하고 처리할지** 점검하는 보안 항목
- 에러 처리 구문이 없거나 오류를 공통적으로만 묶어서 처리하면
  - 프로그램 중단
  - 예기치 못한 문제

  발생 가능
- 주요 약점
  - 오류 메시지를 통한 정보 노출
  - 오류 상황 대응 부재
  - 부적절한 예외처리

> ⭐ `Error Handling = 오류는 처리하되 내부 정보는 노출하지 않기`

---

### 2. 오류 메시지를 통한 정보 노출
- 오류 메시지에
  - 실행 환경
  - 사용자 정보
  - 디버깅 정보

  등이 포함되면 공격자가 내부 정보를 획득할 수 있음
- 예외 처리에서 예외 이름이나 **Stack Trace**를 그대로 출력하면 내부 구조를 쉽게 파악할 수 있음
- 외부 사용자가 보는 오류 메시지는 **최소한의 정보만 제공**

> ⭐ `Stack Trace 등 상세 오류 정보를 사용자에게 그대로 보여주지 않기`

---

### 3. 오류 상황 대응 부재
- 예외처리를 하지 않아 오류 발생 시 프로그램 실행이 중단되거나 의도하지 않은 동작이 발생하는 약점
- 오류가 발생할 수 있는 부분에 예외처리 구문을 작성하고 제어문을 활용하여 대응

---

### 4. 부적절한 예외처리
- 함수의 반환값 또는 오류를 세분화해 처리하지 않고 **광범위한 예외로 한 번에 처리**하거나 누락된 예외가 존재할 때 발생
- 모든 오류를 무조건 하나의 예외 구문으로 묶지 않도록 주의
- 반환값을 확인하여 오류 처리를 명확하게 수행

> ⭐ `Exception은 필요한 범위로 구체적으로 처리`

---

## SECTION 150. 코드 오류

### 1. 코드 오류의 개요
- 구현 단계에서 개발자의 코딩 실수로 발생하는 오류
- 보안 점검 대상
  - 널 포인터 역참조
  - 부적절한 자원 해제
  - 해제된 자원 사용
  - 초기화되지 않은 변수 사용 등

---

### 2. 널 포인터(Null Pointer) 역참조
- 널 포인터가 가리키는 메모리에 어떤 값을 저장할 때 발생하는 보안 약점
- 반환값을 확인하지 않아 `NULL`을 참조하면 비정상 종료 가능
- 동적으로 할당된 메모리 주소를 가리키는 포인터가 NULL인지 확인 후 사용

> ⭐ `Null Pointer = 사용 전에 NULL 여부 검사`

---

### 3. 부적절한 자원 해제
- 사용한 자원을 반환하는 코드를 누락하거나 오류로 인해 해제하지 못하여 발생
- Heap Memory, Socket 등의 자원이 계속 점유되면 **자원 부족** 발생 가능
- 프로그램에서 사용한 자원은 반드시 해제하도록 구현
- 예외가 발생해도 자원이 반환되도록 작성

> ⭐ `Resource = 사용 후 반드시 Release`

---

### 4. 해제된 자원 사용
- 이미 사용이 끝나 반환된 메모리를 다시 참조할 때 발생
- 반환된 메모리에 접근하면
  - 예측하지 못한 값
  - 오류
  - 시스템 장애

  가능
- 반환된 메모리를 가리키는 포인터를 초기화하여 예방

> ⭐ `Free된 메모리를 다시 참조하지 않기`

---

### 5. 초기화되지 않은 변수 사용
- 변수 선언 후 값을 부여하지 않고 사용할 때 발생
- 이전에 메모리에 저장되어 있던 값이 남아 있으면 의도하지 않은 결과 발생 가능
- 변수 선언 시 할당된 메모리를 **초기화**

> ⭐ `변수 = 선언 후 초기값 부여`

---

## SECTION 151. 캡슐화

### 1. 캡슐화의 개요
- 중요한 데이터와 기능을 외부에서 불필요하게 접근하거나 잘못 사용하지 못하도록 **정보를 은닉하는 것**
- 잘못된 캡슐화는 정보 노출 등의 보안 문제를 유발
- 주요 보안 약점
  - 잘못된 세션에 의한 정보 노출
  - 제거되지 않고 남은 디버그 코드
  - 시스템 데이터 정보 노출
  - Public 메소드로부터 반환된 Private 배열
  - Private 배열에 Public 데이터 할당

> ⭐ `Encapsulation = 필요한 정보만 공개하고 내부 정보는 숨김`

---

### 2. 잘못된 세션에 의한 정보 노출
- Multi-Thread 환경에서 멤버 변수에 정보를 저장할 때 발생 가능
- 싱글톤 패턴의 레이스 컨디션으로 동기화 오류 및 정보 노출 가능
- 멤버 변수보다 지역 변수를 활용하여 예방

---

### 3. 제거되지 않고 남은 디버그 코드
- 개발 중 버그 수정·결과 확인을 위한 디버그 코드가 제거되지 않고 남아 발생
- 중요 정보가 디버그 코드로 인해 노출 가능
- 소프트웨어 배포 전 코드 검사를 통해 불필요한 디버그 코드 제거

> ⭐ `배포 전 Debug Code 제거`

---

### 4. 시스템 데이터 정보 노출
- 시스템 내부 정보를 시스템 메시지 등을 통해 외부로 출력하도록 코딩했을 때 발생
- 사용자에게는 필요한 **최소한의 정보만 제공**

---

### 5. Public 메소드로부터 반환된 Private 배열
- 클래스 내부에서만 접근 가능한 `Private` 배열을 `Public` 메소드가 그대로 반환하면 **외부에서 배열의 주소에 접근 가능**
- 예방
  - Private 배열을 별도 메소드로 조작
  - 동일한 형태의 **복제본을 반환**
  - 배열의 값만 전달

> ⭐ `Private 배열 자체 Reference를 외부로 반환하지 않기`

---

### 6. Private 배열에 Public 데이터 할당
- Public으로 선언된 데이터 또는 메소드의 파라미터를 **Private 배열에 직접 저장**할 때 발생
- 외부의 Public 데이터가 변경되면 Private 배열까지 변경될 수 있음
- 예방
  - 참조값(Reference)이 아닌 값을 직접 저장
  - 필요 시 복제본 사용

> ⭐ `외부 객체의 Reference를 Private 영역에 그대로 저장하지 않기`

---

### 7. 접근 지정자(접근 제어자)

| 지정자 | 클래스 내부 | 패키지 내부 | 하위 클래스 | 패키지 외부 |
|---|---:|---:|---:|---:|
| **Public** | O | O | O | O |
| **Protected** | O | O | O | X |
| **Default** | O | O | X | X |
| **Private** | O | X | X | X |

> ⭐ 접근 범위 → `Public > Protected > Default > Private`

---

## SECTION 152. 암호 알고리즘

### 1. 암호 알고리즘의 개요
- 패스워드, 주민번호, 은행계좌 등 중요 정보를 보호하기 위해 평문을 **암호화된 문장으로 변환**하는 방법
- 해시(Hash)를 사용하는 단방향 암호화와
  - 개인키
  - 공개키

  를 사용하는 양방향 암호화가 있음

```text
암호화 방식
├─ 양방향
│  ├─ 개인키
│  │  ├─ Stream 방식
│  │  └─ Block 방식
│  └─ 공개키
└─ 단방향
   └─ HASH
```

> ⭐ `양방향 = 복호화 가능`  
> ⭐ `단방향 Hash = 복호화 불가`

---

### 2. 개인키 암호화(Private Key Encryption)
- **동일한 키**로 데이터를 암호화하고 복호화
- 대칭 암호 기법 또는 비밀키 암호 기법이라고도 함
- 데이터베이스 사용자 A가 암호화 알고리즘 E와 개인키 K로 평문 M을 암호화하면, 사용자 B도 같은 개인키 K로 복호화

#### 특징
- 암호화 대상이 `n`명일 때 필요한 키의 개수
```text
n(n-1) / 2
```
- 암호화·복호화 속도가 빠름
- 알고리즘이 비교적 단순
- 공개키 방식보다 파일 크기가 작음
- 사용자가 증가할수록 관리할 키 수가 많아짐

#### 종류
- **블록 암호화**
  - DES
  - SEED
  - AES
  - ARIA
  - IDEA
- **스트림 암호화**
  - LFSR
  - RC4

> ⭐ `개인키 = 같은 Key / 빠름 / 키 관리 어려움`

---

### 3. 공개키 암호화(Public Key Encryption)
- 암호화할 때 **Public Key**
- 복호화할 때 **Secret Key**
- 비대칭 암호 기법이라고도 함
- 공개키로 암호화된 정보는 해당 비밀키를 가진 사용자만 복호화 가능

#### 특징
- 암호화 대상이 `n`명일 때 필요한 키의 개수
```text
2n
```
- 대표 알고리즘 → **RSA**
- 비밀키를 사용하여
  - 인증
  - 전자서명

  등에 활용 가능
- 키 분배가 용이하고 관리할 키 개수가 적음
- 개인키 방식보다 암·복호화 속도가 느림
- 알고리즘이 복잡
- 파일 크기가 큼

> ⭐ `공개키 = Public으로 암호화 / Secret으로 복호화`  
> ⭐ `키 수 = 2n`

---

### 4. PKI(Public Key Infrastructure)
- 공개키 암호 시스템을 안전하게 사용·관리하기 위한 **정보 보호 표준 방식**
- ITU-T의 X.509 방식 또는 비X.509 방식으로 구분

#### X.509 방식
- 인증기관에서 발행하는 **인증서 기반**
- 상호 인증 제공

#### 비X.509 방식
- 국가별·지역별로 맞게 보완·개발

> ⭐ `PKI = 공개키 기반 인증·관리 인프라`

---

### 5. 주요 양방향 암호 알고리즘

| 알고리즘 | 핵심 |
|---|---|
| **SEED** | 1999년 KISA가 개발한 블록 암호 / 블록 128비트 / 키 128·256비트 |
| **ARIA** | 2004년 국가정보원·산학연이 개발 / AES 규격과 유사 / 블록 128비트 / 키 128·192·256비트 |
| **DES** | 1975년 미국 NBS에서 발표 / 블록 64비트 / 키 56비트 / 3DES로 강화 가능 |
| **AES** | 2001년 NIST가 발표 / DES 대체 / 블록 128비트 / 키 128·192·256비트 |
| **RSA** | 1978년 Rivest, Shamir, Adleman이 제안 / 큰 수의 소인수분해 어려움을 이용 / 공개키 암호 |
| **ECC** | 타원 곡선 암호 / RSA보다 짧은 키로 유사 수준 보안 제공 가능 |
| **Rabin** | 소인수분해의 어려움에 안정성 근거를 둔 암호 알고리즘 |

> ⭐ `DES 56bit / AES 128·192·256 / ARIA 128·192·256`

---

### 6. 해시(Hash)
- 임의 길이의 입력 데이터나 메시지를 **고정 길이의 값이나 키로 변환**
- 해시 알고리즘을 **해시 함수**
- 변환된 값·키를 **해시값 또는 해시키**
- 무결성 검증 등 다양한 분야에서 사용
- **복호화가 거의 불가능한 단방향 암호화 함수**

#### 주요 해시 함수

| 알고리즘 | 핵심 |
|---|---|
| **SHA 시리즈** | 미국 NSA가 설계 / SHA-0, SHA-1, SHA-2(SHA-224/256/384/512) 등 |
| **MD5** | MD4를 대체하기 위해 개발 / 블록 512비트 / 키 128비트 |
| **N-NASH** | 1989년 일본 NTT가 발표 / 블록·키 128비트 |
| **SNEFRU** | 1990년 R. C. Merkle 제안 / 32비트 프로세서 구현 목적 / 128·256비트 출력 |

> ⭐ `Hash = 고정 길이 값 / 단방향 / 무결성 검증`
