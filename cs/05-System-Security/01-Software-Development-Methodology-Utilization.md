# 01. 소프트웨어 개발 방법론 활용

## SECTION 126. 소프트웨어 개발 방법론

### 1. 소프트웨어 개발 방법론의 개요
- **소프트웨어 개발 방법론** - 소프트웨어 개발, 유지보수 등에 필요한 여러 작업들의 수행 방법과 작업 순서를 체계적으로 정리한 것
- 소프트웨어 개발 생산성과 품질 향상을 목적으로 함
- 대표적인 소프트웨어 개발 방법론
  - 구조적 방법론
  - 정보공학 방법론
  - 객체지향 방법론
  - 컴포넌트 기반(CBD) 방법론
  - 애자일 방법론
  - 제품 계열 방법론

> ⭐ `개발 방법론 = 개발 절차·작업 방법을 체계화 → 생산성·품질 향상`


### 2. 구조적 방법론
- 정형화된 분석 절차에 따라 사용자 요구사항을 파악하고 문서화하는 **처리 중심 방법론**
- 1960년대까지 가장 많이 적용된 방법론
- 쉬운 이해 및 검증이 가능한 프로그램 코드를 생성하는 것이 목적
- 복잡한 문제를 해결하기 위해 **분할과 정복(Divide and Conquer)** 원리 적용

#### 구조적 방법론 절차
```text
타당성 검토
→ 계획
→ 요구사항
→ 설계
→ 구현
→ 시험
→ 운용/유지보수
```

> ⭐ `구조적 = 처리 중심 + 분할과 정복`


### 3. 정보공학 방법론
- 정보 시스템 개발을 위해
  - 계획
  - 분석
  - 설계
  - 구축

  에 정형화된 기법을 상호 연관성 있게 통합·적용하는 **자료 중심 방법론**
- 대규모 정보 시스템 구축에 적합
- 기업의 주요 자료를 중심으로 설계
- 주요 도구
  - ERD(Entity-Relationship Diagram) 등

#### 정보공학 방법론 절차
```text
정보 전략 계획 수립
→ 업무 영역 분석
→ 업무 시스템 설계
→ 업무 시스템 구축
```

> ⭐ `정보공학 = 자료(Data) 중심 + 대규모 정보 시스템`


### 4. 객체지향 방법론
- 현실 세계의 개체(Entity)를 **객체(Object)**로 표현
- 객체의 속성과 메소드로 소프트웨어를 구현
- 객체지향 기법을 통해 시스템을 분석·설계
- 주요 모델링 도구
  - Package Diagram
  - State Transition Diagram 등

#### 객체지향 방법론 절차
```text
요구 분석
→ 설계
→ 구현
→ 테스트 및 검증
→ 인도
```

> ⭐ `객체지향 = 현실 세계의 개체를 Object로 모델링`


### 5. 컴포넌트 기반(CBD; Component Based Design) 방법론
- 기존 시스템이나 소프트웨어를 구성하는 **컴포넌트(Component)를 조합하여 새로운 애플리케이션을 만드는 방법론**
- 컴포넌트의 **재사용성(Reusability)**이 가능하여 시간과 노력 절감
- 새로운 기능을 추가하는 것이 간단하여 **확장성 향상**
- 유지보수 비용 감소
- 생산성 및 품질 향상

#### CBD 절차
```text
개발 준비
→ 분석
→ 설계
→ 구현
→ 테스트
→ 전개
→ 인도
```

> ⭐ `CBD = Component 재사용 → 생산성·확장성·유지보수성 향상`


### 6. 애자일(Agile) 방법론
- ‘민첩한’, ‘기민한’이라는 의미
- 고객의 요구사항 변화에 유연하게 대응할 수 있도록 **일정한 주기를 반복하면서 개발**
- 소규모 프로젝트, 고도로 숙련된 개발자, 급변하는 요구사항에 적합
- 대표 방법론
  - XP(eXtreme Programming)
  - Scrum
  - Crystal
  - FDD(Feature Driven Development) 등

#### 애자일 절차
```text
사용자 스토리
→ 계획
→ 개발
→ 승인 테스트
      ↑ 반복 주기
```

> ⭐ `Agile = 짧은 반복 주기 + 변화 대응`


### 7. 제품 계열 방법론
- 특정 제품에 적용하고 싶은 **공통된 기능을 정의하여 개발**
- 임베디드 소프트웨어 개발에 적합
- 영역공학과 응용공학으로 구분

#### 영역공학(Domain Engineering)
- 영역 분석, 영역 설계, 핵심 자산을 구현하는 영역
- 재사용 가능한 핵심 자산 개발

#### 응용공학(Application Engineering)
- 제품 요구 분석, 제품 설계, 제품을 구현하는 영역
- 핵심 자산을 이용하여 실제 제품 개발

> ⭐ `제품 계열 = 공통 핵심 자산 개발 + 제품별 재사용`  
> ⭐ `영역공학 = 핵심 자산 / 응용공학 = 실제 제품`

## SECTION 127. S/W 공학의 발전적 추세

### 1. 소프트웨어 재사용의 개요
- **소프트웨어 재사용(Software Reuse)** - 이미 개발되어 인정받은 소프트웨어의 전체 또는 일부를 다른 소프트웨어 개발이나 유지보수에 다시 사용하는 것
- 기존 소프트웨어를 이용하여
  - 생산성 향상
  - 품질 향상
  - 개발 시간·비용 절감

  가능

#### 재사용의 장점
- 개발 시간과 비용 단축
- 소프트웨어 품질 향상
- 생산성 향상
- 프로젝트 실패 위험 감소
- 시스템 구축 방법에 대한 지식 공유
- 시스템 명세·설계·코드 등의 문서 공유

> ⭐ `Reuse = 검증된 SW를 다시 사용 → 시간·비용↓ 품질·생산성↑`


### 2. 소프트웨어 재사용 방법

| 방법 | 핵심 |
|---|---|
| **합성 중심(Composition-Based)** | 전자 칩과 같은 **소프트웨어 부품(블록)을 조립**하여 새로운 소프트웨어 작성 / 블록 구성 방법 |
| **생성 중심(Generation-Based)** | 추상화된 형태의 명세를 구체화하여 프로그램을 만드는 방법 / **패턴 구성 방법** |

> ⭐ `합성 중심 = 부품 조립`  
> ⭐ `생성 중심 = 추상 명세 → 구체 프로그램`


### 3. 소프트웨어 재공학(Reengineering)
- 새로운 요구에 맞도록 기존 시스템을 이용해 **더 나은 시스템으로 재구성**
- 유지보수 비용이 증가하는 소프트웨어를 분석하고 개선하여
  - 품질 향상
  - 생산성 향상
  - 수명 연장

  을 목적으로 함
- 기존 소프트웨어를 폐기하지 않고 활용하므로 **예방(Preventive) 유지보수** 측면에서 소프트웨어 위기를 해결하는 방법

#### 재공학의 장점
- 품질 향상
- 생산성 증가
- 소프트웨어 수명 연장
- 오류 감소


### 4. 재공학의 주요 활동

| 활동 | 핵심 |
|---|---|
| **분석(Analysis)** | 기존 소프트웨어의 명세서를 확인하여 **동작 이해·재공학 대상 선정** |
| **재구성(Restructuring)** | 기존 구조를 향상시키기 위해 **코드 재구성** / 기능과 외적 동작은 변경하지 않음 |
| **역공학(Reverse Engineering)** | 기존 소프트웨어를 분석해 **상위 수준의 정보(설계·명세 등)를 추출** |
| **이식(Migration)** | 기존 소프트웨어를 **다른 운영체제나 하드웨어 환경에서도 사용할 수 있도록 변환** |

> ⭐ `Reverse Engineering = 코드 → 설계·명세 등 상위 정보`


### 5. CASE(Computer Aided Software Engineering)
- 소프트웨어 개발 과정에서 사용하는
  - 요구 분석
  - 설계
  - 구현
  - 검사

  등의 작업을 **컴퓨터와 전용 소프트웨어 도구로 자동화**
- 소프트웨어 개발의 전 단계에 활용 가능

#### CASE의 장점
- 소프트웨어 개발 기간 단축
- 개발 비용 절감
- 생산성 향상
- 품질 향상
- 소프트웨어 유지보수 용이
- 소프트웨어 모듈 재사용성 향상
- 소프트웨어 개발 기법을 실제 작업에 적용하기 쉬움
- 시스템 명세서, 보고서 등 문서 작성이 쉬움

#### CASE 주요 기능
- S/W 생명 주기 전 단계 연결
- 다양한 소프트웨어 개발 모형 지원
- 그래픽 지원
- 모델 간 모순 검사
- 자료 흐름도 작성 등

> ⭐ `CASE = 개발 전 과정 자동화 지원 도구`

## SECTION 128. 상향식 비용 산정 기법

### 1. 상향식 비용 산정 기법의 개요
- 프로젝트의 **세부 작업 단위별로 비용을 산정한 후 전체 비용을 계산**하는 방법
- 대표 기법
  - LOC
  - 개발 단계별 인월수(Effort Per Task)

> ⭐ `상향식 = 작은 작업부터 계산 → 전체 비용 합산`


### 2. LOC(Line of Code) 기법
- 소프트웨어 각 기능의 **원시 코드 라인 수**를
  - 낙관치
  - 중간치(기대치)
  - 비관치

  로 측정하여 예측치를 구하고 비용 산정
- 측정이 쉽고 이해하기 쉬워 많이 사용
- 생산성, 개발 기간, 개발 인원 등을 계산 가능

#### LOC 예측치
```text
예측치 = (낙관치 + 4 × 기대치 + 비관치) / 6
```

#### 산정 공식
```text
노력(인월) = 개발 기간 × 투입 인원
            = LOC / 1인당 월평균 생산 코드 라인 수

개발 비용 = 노력(인월) × 단위 비용(1인당 월평균 인건비)

개발 기간 = 노력(인월) / 투입 인원

생산성 = LOC / 노력(인월)
```

> ⭐ LOC 계산은 `노력 → 비용·기간·생산성` 공식 연결해서 암기


### 3. 개발 단계별 인월수(Effort Per Task) 기법
- LOC 기법을 보완한 기법
- 각 기능을 구현하는 데 필요한 노력을 **소프트웨어 생명 주기의 각 단계별로 산정**
- LOC보다 더 정확한 비용 산정 가능

> ⭐ `Effort Per Task = 생명 주기 단계별 필요한 인월수 계산`

## SECTION 129. 수학적 산정 기법

### 1. 수학적 산정 기법의 개요
- **경험적 추정 모형 / 실험적 추정 모형**이라고도 함
- 비용을 자동으로 산정하기 위해 공식으로 표현
- 유사한 프로젝트를 기반으로 경험적으로 유도된 공식 사용
- 대표 기법
  - COCOMO
  - Putnam
  - 기능 점수(FP)

> ⭐ `수학적 산정 = COCOMO / Putnam / FP`

### 2. COCOMO 모형
- **Boehm**이 제안
- 원시 프로그램의 규모인 **LOC(원시 코드 라인 수)**를 이용하여 개발 비용을 산정
- 비교적 작은 규모의 프로젝트 기록을 분석하여 얻은 공식 사용
- 비용 산정 결과는 프로젝트를 완성하는 데 필요한 **노력(Man-Month)**으로 나타냄
- 개발 유형에 따라 모드를 구분

> ⭐ `COCOMO = Boehm + LOC + Man-Month`


### 3. COCOMO 소프트웨어 개발 유형

#### 조직형(Organic Mode)
- **5만(50KDSI) 라인 이하**의 비교적 작은 소프트웨어
- 일괄 자료 처리, 과학기술 계산 등
- 개발 경험이 있는 소규모 개발 조직에 적합

```text
노력(MM) = 2.4 × (KDSI)^1.05
개발 기간(TDEV) = 2.5 × (MM)^0.38
```

#### 반분리형(Semi-Detached Mode)
- 조직형과 내장형의 중간
- 약 **30만(300KDSI) 라인 이하**
- 컴파일러, 인터프리터 등
- 개발 경험이 섞여 있는 중간 규모 프로젝트

```text
노력(MM) = 3.0 × (KDSI)^1.12
개발 기간(TDEV) = 2.5 × (MM)^0.35
```

#### 내장형(Embedded Mode)
- 최대형 규모의 트랜잭션 처리 시스템, 운영체제 등
- **30만(300KDSI) 라인 이상**
- 하드웨어·소프트웨어·운영 조건이 강하게 결합된 프로젝트

```text
노력(MM) = 3.6 × (KDSI)^1.20
개발 기간(TDEV) = 2.5 × (MM)^0.32
```

> ⭐ `COCOMO 모드 = 조직형 → 반분리형 → 내장형`  
> ⭐ 규모·복잡도도 같은 순서로 증가


### 4. Putnam 모형
- 소프트웨어 생명 주기의 **전 과정 동안 사용될 노력의 분포를 가정**
- **Putnam**이 제안
- **생명 주기 예측 모형**이라고도 함
- 시간에 따른 함수로 표현되는 **Rayleigh-Norden 곡선**의 노력 분포를 기초로 함
- 대형 프로젝트의 노력 분포 산정에 이용
- 자동화 추정 도구 → **SLIM**

> ⭐ `Putnam = Rayleigh-Norden + 생명 주기 노력 분포 + SLIM`


### 5. 기능 점수(FP; Function Point) 모형
- **Albrecht**가 제안
- 소프트웨어의 기능을 증대시키는 요인별로 가중치를 부여
- 요인별 가중치를 합산하여 **총 기능 점수**를 구한 후 영향도를 이용하여 비용 산정

#### 기능 점수 공식
```text
FP = 총 기능 점수 × [0.65 + (0.01 × 총 영향도)]
```

#### 기능별 가중치

| 소프트웨어 기능 증대 요인 | 단순 | 보통 | 복잡 |
|---|---:|---:|---:|
| **자료 입력(입력 양식)** | 3 | 4 | 6 |
| **정보 출력(출력 보고서)** | 4 | 5 | 7 |
| **명령어(사용자 질의 수)** | 3 | 4 | 6 |
| **데이터 파일** | 7 | 10 | 15 |
| **외부 루틴과의 인터페이스** | 5 | 7 | 10 |

> ⭐ FP 가중치 → `입력 3·4·6 / 출력 4·5·7 / 질의 3·4·6 / 파일 7·10·15 / 인터페이스 5·7·10`

#### 자동화 추정 도구
- **SLIM** - Rayleigh-Norden 곡선과 Putnam 예측 모델 기반
- **ESTIMACS** - 다양한 프로젝트와 개인별 요소를 수용하도록 FP 모형 기반

## SECTION 130. 프로젝트 일정 계획

### 1. 프로젝트 일정 계획의 개요
- 프로젝트 프로세스를 구성하는 **소작업을 파악**하고
  - 작업 순서
  - 일정

  등을 정하는 작업
- 개발 기간 지연을 방지하고 프로젝트를 계획대로 진행하도록 일정 관리
- 소프트웨어 개발 프로젝트는 개발 기간의 시작과 끝을 정하고 여러 작업을 조정하여 일정 수립
- 대표 일정 계획 도구
  - WBS
  - PERT/CPM
  - 간트 차트

> ⭐ `일정 계획 = 작업 분해 + 순서 + 기간 + 자원 조정`


### 2. PERT(Program Evaluation and Review Technique)
- 프로젝트에 필요한 전체 작업의 **상호 관계를 네트워크로 표현**
- 각 작업별
  - 낙관치
  - 기대치
  - 비관치

  를 이용하여 작업 기간 산정
- 작업별 종료 시기를 결정하는 데 사용
- 작업 예측치와 평방 편차를 계산하여 일정 예측

#### 작업 예측치
```text
(비관치 + 4 × 기대치 + 낙관치) / 6
```

#### 평방 편차
```text
[(비관치 - 낙관치) / 6]²
```

> ⭐ `PERT = 3점 추정(낙관·기대·비관) + 네트워크`


### 3. CPM(Critical Path Method, 임계 경로 기법)
- 프로젝트 완성에 필요한 작업을 나열하고 **작업에 필요한 소요 기간을 예측**
- 노드와 간선으로 구성된 네트워크 사용
- 작업의 전후 관계를 이용해 **임계 경로(Critical Path)**를 찾음
- **임계 경로** - 시작부터 종료까지의 여러 경로 중 **가장 긴 경로**
- 임계 경로에 있는 작업이 지연되면 전체 프로젝트 일정도 지연
- 일정 단축을 위해 임계 경로 작업을 집중 관리
- 효과적인 프로젝트 통제 가능
- 병행 작업 가능
- 자원 할당 가능

> ⭐ `CPM = 가장 긴 경로 = Critical Path`  
> ⭐ `임계 경로의 작업 지연 → 프로젝트 전체 지연`


### 4. 간트 차트(Gantt Chart)
- 프로젝트 각 작업의 시작·종료 시점을 **막대 도표**로 표시
- 시간선(Time-Line) 차트라고도 함

#### 장점
- 작업 진행 상황과 완료 여부 파악이 쉬움
- 사용자와 의사소통 및 일정 조정에 유리
- 작업 예정 시간과 실제 작업 시간을 비교 가능
- 작업별 일정 관리가 쉬움

#### 특징
- CPM 네트워크의 데이터를 이용하여 막대 형태로 작성 가능
- 자원 배치 계획 및 인력 계획에 활용
- 진행 상황을 확인할 수 있으나 **작업 간 의존 관계는 명확하게 표현하기 어려움**
- 계획 수립 또는 수정 시 주관적 수치에 의존할 수 있음

> ⭐ `Gantt = 시간축 + 막대 그래프`  
> ⭐ `작업 일정은 잘 보이지만 작업 간 의존 관계 표현은 약함`

## SECTION 131. 소프트웨어 개발 방법론 결정

### 1. 소프트웨어 개발 방법론 결정의 개요
- 프로젝트 관리와 재사용 현황을 소프트웨어 개발 방법론에 반영
- 선정된 소프트웨어 개발 방법론이 프로젝트에 적합한지 검토하고 최종 결정
- 프로젝트의
  - 특징
  - 요구사항
  - 규모
  - 비용
  - 일정
  - 조직

  등을 고려

### 2. 프로젝트 관리

| 관리 영역 | 주요 내용 |
|---|---|
| **범위 관리** | 작업의 범위를 결정하고 계획 수립·변경 관리 |
| **비용 관리** | 예산 산정, 비용 산정, 예산 편성 |
| **인력 관리** | 프로젝트 팀 조직, 인적 자원 확보·관리 |
| **위험 관리** | 위험 식별, 위험 분석 및 평가, 위험 관리 계획·감시·조치 |
| **품질 관리** | 품질 계획, 품질 보증, 품질 통제 |



### 3. 소프트웨어 개발 방법론 결정 절차

```text
프로젝트 관리와 재사용 현황 분석
→ 개발 방법론 후보 선정
→ 개발 기준 설정
→ 방법론 최종 결정
→ 관련자에게 방법론 교육
```

#### 개발 기준 예
- 개발 업무
- 기술
- 운영·유지보수
- 프로젝트 규모와 중요도
- 조직 규모
- 목적 등

> ⭐ `프로젝트 특성과 재사용 현황을 분석 → 가장 적합한 방법론 결정`

## SECTION 132. 소프트웨어 개발 표준

### 1. 소프트웨어 개발 표준의 개요
- 소프트웨어 개발 단계에서 수행하는 **품질 관리에 사용되는 국제 표준**
- 대표적인 소프트웨어 개발 표준
  - ISO/IEC 12207
  - CMMI
  - SPICE

> ⭐ `개발 표준 = ISO/IEC 12207 / CMMI / SPICE`

### 2. ISO/IEC 12207
- ISO에서 만든 소프트웨어 **생명 주기 프로세스 국제 표준**
- 소프트웨어의
  - 개발
  - 운영
  - 유지보수

  등을 체계적으로 관리하기 위한 생명 주기 프로세스를 정의

#### ISO/IEC 12207 기본 생명 주기 프로세스

| 구분 | 주요 프로세스 |
|---|---|
| **기본 생명 주기 프로세스** | 획득, 공급, 개발, 운영, 유지보수 |
| **지원 생명 주기 프로세스** | 품질 보증, 검증, 확인, 활동 검토, 감사, 문서화, 형상 관리, 문제 해결 |
| **조직 생명 주기 프로세스** | 관리, 기반 구조, 훈련, 개선 |

> ⭐ `12207 = 기본 / 지원 / 조직 생명 주기 프로세스`


### 3. CMMI(Capability Maturity Model Integration)
- **소프트웨어 개발 조직의 업무 능력 및 조직의 성숙도를 평가하는 모델**
- 미국 카네기멜론대학교 소프트웨어 공학연구소(SEI)에서 개발
- 조직의 프로세스 성숙도를 **5단계**로 구분

| 단계 | 이름 | 핵심 |
|---|---|---|
| **1** | 초기(Initial) | 정의된 프로세스가 거의 없음 / 작업자 능력에 의존 |
| **2** | 관리(Managed) | 규칙화된 프로세스 / 특정 프로젝트 내 프로세스 정의·수행 |
| **3** | 정의(Defined) | 조직의 표준 프로세스를 활용하여 업무 수행 |
| **4** | 정량적 관리(Quantitatively Managed) | 프로젝트를 **정량적으로 관리 및 통제** |
| **5** | 최적화(Optimizing) | 지속적 개선을 위해 프로세스를 관리 |


### 4. SPICE(Software Process Improvement and Capability dEtermination)
- 소프트웨어 프로세스를 평가하기 위한 국제 표준
- 공식 명칭 → **ISO/IEC 15504**
- 소프트웨어 프로세스 개선 및 능력 평가 기준

#### SPICE 프로세스 범주

| 범주 | 핵심 |
|---|---|
| **고객-공급자(Customer-Supplier)** | 소프트웨어 개발·인도·고객 지원 관련 프로세스 |
| **공학(Engineering)** | 시스템·소프트웨어 개발 및 유지보수 |
| **지원(Support)** | 문서화, 형상 관리, 품질 보증, 검증 등 지원 |
| **관리(Management)** | 프로젝트 관리·품질 및 위험 관리 |
| **조직(Organization)** | 조직 차원의 프로세스 개선, 인력 관리, 기반 구조 등 |

#### SPICE 수행 능력 단계

| Level | 단계 | 핵심 |
|---|---|---|
| **0** | 불완전(Incomplete) | 프로세스가 구현되지 않았거나 목적을 달성하지 못함 |
| **1** | 수행(Performed) | 프로세스가 수행되고 목적 달성 |
| **2** | 관리(Managed) | 프로세스 수행이 계획·감시·조정되며 산출물이 관리 |
| **3** | 확립(Established) | 정의된 표준 프로세스를 사용하여 수행 |
| **4** | 예측(Predictable) | 프로세스가 정의된 범위 내에서 일관되게 수행 |
| **5** | 최적화(Optimizing) | 지속적인 개선을 통해 업무 목적 만족 |

## SECTION 133. 소프트웨어 개발 방법론 테일러링

### 1. 테일러링(Tailoring)의 개요
- 프로젝트 상황 및 특성에 맞도록 **정의된 소프트웨어 개발 방법론의 절차·사용 기법 등을 수정·보완하는 작업**
- 관리적 측면
  - 최단 기간에 안정적인 프로젝트 수행
- 기술적 측면
  - 최적화된 기술 요소를 도입하여 프로젝트 특성에 맞는 방법론 구성

#### 테일러링 절차
```text
프로젝트 특징 정의
→ 표준 프로세스 선정 및 검증
→ 상위 수준의 커스터마이징
→ 세부 커스터마이징
→ 테일러링 문서화
```

> ⭐ `Tailoring = 표준 방법론을 프로젝트에 맞게 수정`

### 2. 테일러링 고려사항

#### 내부적 기준
- **목표 환경** - 시스템의 개발 환경과 유형이 서로 다른 경우
- **요구사항** - 요구사항의 생명 주기가 다르거나 적용 방법·절차가 다른 경우
- **프로젝트 규모** - 비용·인력·기간 등 프로젝트 규모가 서로 다른 경우
- **보유 기술** - 프로세스, 개발 방법론, 산출물, 구성원의 능력 등이 다른 경우

#### 외부적 기준
- **법적 제약사항** - 프로젝트별로 적용할 IT Compliance가 다른 경우
- **표준 품질 기준** - 금융·제조 등 분야별 품질 표준이 다른 경우

> ⭐ `내부 = 목표 환경 / 요구사항 / 규모 / 기술`  
> ⭐ `외부 = 법적 제약 / 품질 표준`


### 3. 소프트웨어 개발 방법론 테일러링 기법

#### 프로젝트 규모와 복잡도에 따른 테일러링
- 가장 일반적인 방식
- 프로젝트 규모와 복잡도에 따라
  - 활동
  - 작업
  - 산출물
  - 절차

  등을 축소·확대

#### 프로젝트 구성원에 따른 테일러링
- 프로젝트 참여자의
  - 기술적 숙련도
  - 방법론 이해 정도

  를 고려하여 테일러링 수준 결정

#### 팀 내 방법론 지원에 따른 테일러링
- 프로젝트 수행 시 각 팀에서 수행해야 할 업무를 세분화하고
- 팀의 지원 수준과 역할을 고려하여 방법론 조정

#### 자동화에 따른 테일러링
- 프로젝트 수행 시 작업 부담을 줄이기 위해 **자동화 도구를 활용**
- 중간 단계의 산출물을 자동 생성하거나 작업을 지원

> ⭐ 테일러링 기법 → `규모·복잡도 / 구성원 / 팀 지원 / 자동화`

## SECTION 134. 소프트웨어 개발 프레임워크

### 1. 소프트웨어 개발 프레임워크의 개요
- **프레임워크(Framework)** - 소프트웨어 개발에 공통적으로 사용되는 **구성 요소와 아키텍처를 일반화하여 제공하는 반제품 형태의 소프트웨어 시스템**
- 개발에 필요한 기반 구조와 공통 기능을 미리 제공
- 선행 사업자의 기술에 의존하지 않는 표준화된 개발 기반을 이용하여
  - 사업자 종속성 완화
  - 품질 향상

  가능
- 이미 검증된 라이브러리·컴포넌트를 사용하여 개발 속도와 품질 향상
- 예
  - 전자정부 프레임워크
  - Spring Framework
  - .NET Framework 등

> ⭐ `Framework = 공통 구조·기능을 미리 제공하는 반제품 SW`

### 2. 프레임워크의 특성

| 특성 | 핵심 |
|---|---|
| **모듈화(Modularity)** | 캡슐화를 통해 모듈화를 강화하고 설계·구현 변경에 따른 영향을 최소화 |
| **재사용성(Reusability)** | 반복적으로 사용되는 일반적 컴포넌트를 정의하여 재사용성 향상 |
| **확장성(Extensibility)** | 다형성을 통해 애플리케이션이 프레임워크의 인터페이스를 확장 가능 |
| **제어의 역흐름(Inversion of Control)** | 개발자가 관리하던 객체·제어 흐름을 **프레임워크가 관리** |

> ⭐ `IoC = 제어권이 개발자 → Framework로 이동`


### 3. 스프링 프레임워크(Spring Framework)
- **Java 플랫폼을 위한 오픈 소스 경량 애플리케이션 프레임워크**
- 동적인 웹 사이트 개발을 위한 다양한 서비스 제공
- 전자정부 표준 프레임워크의 기반 기술로 사용

> ⭐ `Spring = Java + 오픈 소스 + 경량 Framework`


### 4. 전자정부 프레임워크
- 우리나라 공공부문 정보화 사업에서 효율적인 정보 시스템 구축을 지원하기 위해 필요한 **기능 및 아키텍처를 제공**
- 개발 프레임워크의 표준 정립으로 응용 소프트웨어의
  - 표준화
  - 품질
  - 재사용성

  향상
- 오픈 소스 기반으로 공개·활용 가능

> ⭐ `전자정부 프레임워크 = 공공 정보화 + 표준화 + 재사용`


### 5. .NET Framework
- Windows 프로그램 개발 및 실행 환경을 제공하는 **Microsoft의 Windows용 프레임워크**
- 코드 실행을 관리하는 **CLR(Common Language Runtime)** 제공
- CLR은
  - 메모리 관리
  - 유형 및 메모리 안전성
  - 보안
  - 네트워크 작업

  등을 지원

> ⭐ `.NET Framework = Microsoft + Windows + CLR`
